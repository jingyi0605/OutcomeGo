# Internationalization Language Support

Date: 2026-11-09.

This specification establishes one language-management model for the desktop, iOS, Android, CLI, and Web clients. The first release supports English and Simplified Chinese (`zh-CN`). Android already has a partial English/Chinese implementation; this work standardizes its locale identifiers, fallback rules, settings entry, and future catalog checks.

## Goals

- Every client uses the same canonical locale identifiers, with `en-US` as the default.
- Users can select the interface language from client settings and keep the choice across restarts.
- A missing translation falls back to English instead of rendering an empty value or a translation key.
- Dates, times, numbers, and plural rules use the selected locale's platform formatter.
- The interface language remains separate from transcription language, bot response language, and code highlighting language.
- Adding a language requires registering its metadata, adding a catalog, and passing coverage checks rather than adding language branches throughout the UI.

## Scope

The first phase covers the desktop, iOS, and Android application surfaces and the CLI's interactive setup and diagnostic surfaces. The landing and documentation site keeps its content routes independent; the first Web phase adds the shared registry and a language entry point before translating marketing, blog, and documentation content as separate publishing work.

Generated bot messages, user input, plugin names, and remote web content remain in their original language. Client-owned error codes and notifications can use stable translation keys; dynamic text without a key remains the server-provided text.

## Design

### Language model

The contracts package defines:

- `Locale`: currently `en-US` and `zh-CN`.
- `DEFAULT_LOCALE`: `en-US`.
- `normalizeLocale`: accepts full BCP 47 values and common language aliases, then falls back to the default for unknown values.
- `SUPPORTED_LOCALES` and display metadata: English is shown as `English`, and Simplified Chinese as `简体中文`.

Client translation functions use stable keys and a parameter object, for example `t("settings.language.title")` and `t("messages.count", { count })`. The English catalog is the complete baseline. Other catalogs may temporarily omit keys and fall back at runtime; tests must report those missing keys.

### Preference source and priority

Clients choose the active language in this order:

1. An explicitly saved client language preference.
2. The signed-in account language preference once server synchronization is available.
3. The first supported operating-system language.
4. `en-US`.

The first phase uses local persistence for an immediate offline-safe loop. Account synchronization is a follow-up that can use the same contract without making the signed-out startup path depend on the network.

Desktop stores a versioned renderer preference, iOS uses `AppStorage`, and Android keeps its existing settings store while persisting canonical locale tags. Changing the language refreshes visible UI in the current process.

### Platform implementation

- Desktop: use a small React `I18nProvider`, `useI18n`, and local catalogs. Migrate the application shell, settings, sign-in, and core chat actions first, then move through the remaining screens.
- iOS: use SwiftUI `LocalizedStringKey` and a String Catalog. The language selector controls the locale environment, and Foundation formatters receive the selected locale.
- Android: keep Android resource localization with `values/strings.xml` and `values-zh-rCN/strings.xml`; remove business-layer English/Chinese selection closures as screens are migrated. The setting maps to `en-US` and `zh-CN`.
- CLI: share the locale registry and allow a `--language` override for interactive commands. Non-interactive output keeps stable machine-readable identifiers.
- Landing: use route-level catalogs and set `<html lang>` from the active route. Documentation and blog translation remain separately maintained content.

### Dynamic text and formatting

Translation keys contain UI text. Text with counts, names, or error details uses parameters instead of concatenating translated fragments. Dates, times, numbers, and relative times pass the active locale to `Intl`, Foundation, or Android formatters.

For server errors, the contracts package maps stable error codes to translation keys. Unknown errors show the server's safe message. Bot messages and user content are never automatically translated.

## Compatibility and risks

The language preference affects presentation only. It does not change APIs, stored business data, or bot behavior. The English fallback keeps older clients and incomplete catalogs usable. Coverage checks must allow dynamic content and platform-specific strings to differ while preventing new fixed user-visible text from bypassing an already migrated catalog.

The worktree already contains uncommitted Android update and release-script changes. Internationalization changes must remain scoped to the files listed by this work and must not reset, clean, overwrite, or commit unrelated work. Verification should use package-level commands and must not start development servers.
