# 群聊实时语音对话技术方案

日期：2026 年 11 月 10 日。

状态：可进入实现规划评审。

本方案将现有的单 Bot 实时语音能力扩展到群聊频道，覆盖会话创建、参与成员选择、语音唤醒规则、持久化投递顺序、带说话人身份的 TTS、打断、循环限制、客户端改造、数据库迁移、测试、发布和验收标准。

现有的单 Bot 实时语音行为是兼容基线。没有提供群聊参与成员的客户端继续使用一个 Bot、一个会话和现有的直接消息路径。

## 决策

群聊实时语音采用一个经过认证的语音会话。会话绑定一个群聊频道，并保存用户在通话开始时选择的 Bot 参与成员快照。

一个会话同时只处理一个用户语音回合。一个回合可以产生零个或多个按顺序排列的 Bot 响应。现有群聊调度器继续负责持久化唤醒顺序、投递锁、重试和消息发布。语音群聊回合使用独立的回合模式，避免误触发现有的文本群聊成员互相追问流程。

服务端必须通过一个说话队列串行处理所有 TTS 输出。一个会话在任意时刻最多只有一个 Bot 持有说话租约。回合响应状态持久化，WebSocket 负责当前播放过程。重连后可以恢复字幕和响应状态，但不能重复播放已经播过的音频。

推荐的唤醒规则如下：

| 用户语音 | 被唤醒的 Bot |
| --- | --- |
| 明确点名一个或多个已选成员 | 只有被点名的已选成员 |
| 说出“所有人”“大家”或等价的 `@everyone` 指令 | 所有已选成员 |
| 没有点名成员 | 会话默认说话人，通常为第一个已选成员 |
| 点名了未选中的 Bot | 不临时加入该 Bot；由已选的默认说话人处理 |

这套规则保留实时通话的聚焦感，同时允许用户通过说出成员名称覆盖默认说话人。该规则必须使用语音专用解析器实现，因为当前文本群聊解析器在没有明确点名时会把所有符合条件的成员作为响应者。普通文本群聊行为不得因此改变。

第一版给每个解析出的 Bot 一次判断当前语音是否与自身相关的机会，Bot 最多发送一条用户可见答复。Bot 可以判断当前回合与自身无关，然后静默完成，不发送答复，也不发送“我没有补充”“好的”等填充性话术。每个用户语音仍然只产生一个语音群聊回合。Bot 的答复不会在同一语音回合中自动唤醒其他成员。这是防止循环的主要规则。

## 目标

- 允许用户从群聊频道发起实时语音。
- 允许用户选择参与本次通话的群聊成员。
- 在通话期间固定参与成员快照。
- 用户明确说出成员名称时，将语音回合路由给对应的已选 Bot。
- 继续以现有群聊历史和可见消息作为事实来源。
- 使用正确的 Bot 身份和声音逐个播放响应。
- 用户打断时停止或淘汰过期工作。
- 使重复的 STT 最终结果、重连、Worker 重试和 WebSocket 重试具备幂等性。
- 限制 Bot 响应数量，阻止 Bot 之间形成唤醒循环。
- 保持现有单 Bot 实时语音 API 和行为兼容。
- 优先完成桌面端，同时保持协议和契约可供 iOS、Android 后续接入。

## 范围

第一版包括：

- 服务端群聊语音会话创建和授权。
- 会话参与成员选择与成员快照持久化。
- 语音专用的成员点名和口语名称解析。
- 带已选响应者集合的群聊用户消息接收。
- 每个解析响应者一个有序的响应机会。
- 带说话人声音选择的 TTS 串行播放。
- 带 Bot 身份的语音字幕。
- 抢话、取消、过期回合淘汰、重试、重连和会话过期处理。
- 桌面端群聊实时语音界面。
- 契约、数据库、消息、服务端和桌面端测试。

第一版不包括：

- 多个人类用户同时发布麦克风音频的多人网络通话。
- 多个 Bot 独立音频流的混音。
- Bot 响应后自动发起 Bot 之间的讨论。
- 跨通话持久保存语音参与成员。
- 通话过程中使用语音指令修改参与成员集合。
- 对普通文本群聊路由的修改。
- Provider 侧的声音克隆或自动分配声音。
- 原始音频持久化。

通话进行中修改参与成员可以作为后续能力，但第一版必须使用固定参与成员快照，以保证授权、顺序和恢复行为确定。

## 用户体验

### 发起群聊通话

当当前频道是群聊时，群聊标题栏显示实时语音入口。用户点击后先打开参与成员面板，完成选择后才开始采集麦克风。

面板显示：

- 群聊中所有当前处于活跃状态的 Bot。
- Bot 名称、头像、标题和可用的配置声音。
- 是否参与本次通话的选择框。
- 已选成员中的默认说话人选择器。
- 未选择任何成员时的明确禁用状态。

初始默认选中全部活跃群聊成员。用户可以在开始前取消成员。第一个已选成员默认成为默认说话人，用户也可以选择其他已选成员。

客户端提交已选 Bot ID 和默认说话人 ID。服务端根据当前群聊成员关系校验，并保存校验后的参与成员快照。通话开始后，客户端必须使用服务端返回的参与成员列表，不得假设群聊在通话期间没有变化。

### 通话中的语音

通话界面显示：

- 用户转写文本。
- 当前说话人名称。
- 当前说话人头像。
- Bot 答复字幕。
- 当前通话的参与成员列表。
- 默认说话人标识。
- 当前状态：聆听、思考、说话、已打断或错误。

用户说出某个已选 Bot 的名称时，只有该 Bot 获得响应机会。用户说出多个已选 Bot 的名称时，按照会话顺序依次给这些 Bot 响应机会。用户说“所有人”时，所有已选 Bot 按会话顺序获得一次机会。没有点名时，只有默认说话人获得机会。

每个获得机会的 Bot 都可以判断当前话题与自身无关并保持静默。系统不能替它合成填充句子，也不能显示“该 Bot 跳过了本轮”之类的提示。Bot 在可见答复中提到其他成员时，也不会自动唤醒其他成员；用户必须在之后的语音中明确点名。

### 打断说话

当用户在 Bot 说话期间开始讲话时：

1. 服务端立即停止当前音频代际。
2. 取消当前 TTS 流。
3. 如果最终用户转写被接受，将当前 Bot run 标记为中断或过期。
4. 取消旧语音回合中尚未开始的响应机会。
5. 新的最终转写使用新的回合 ID 和新的幂等键开始。

VAD 检测到的噪音、咳嗽和无意义转写继续沿用现有行为：可以停止当前音频，但不会创建新的用户消息，也不会唤醒 Bot。

## 契约和数据模型

### 会话创建契约

在保持直接会话请求有效的前提下，给 `VoiceSessionCreateInput` 增加群聊字段：

```ts
type VoiceSessionCreateInput = {
  botId?: string;                 // 直接会话必填
  channelId: string;
  participantBotIds?: string[];   // 群聊会话必填
  defaultSpeakerBotId?: string;   // 可选；默认使用第一个参与成员
  clientPlatform: VoiceClientPlatform;
  clientInstanceId: string;
  timeZone?: string;
  provider?: VoiceProviderId;
};
```

服务端根据频道类型推断会话模式：

- `bot_dm` 要求 `botId`，拒绝 `participantBotIds`。
- `group` 要求一到六个 `participantBotIds`，允许提供 `defaultSpeakerBotId`。
- 其他频道类型返回 `voice_target_not_found`。

服务端响应增加：

```ts
type VoiceParticipantView = {
  botId: string;
  name: string;
  title: string;
  voice: string;
  ordinal: number;
  isDefaultSpeaker: boolean;
};
```

`VoiceSessionView` 增加：

```ts
mode: "direct" | "group";
participants: VoiceParticipantView[];
defaultSpeakerBotId: string | null;
activeSpeakerBotId: string | null;
```

现有直接客户端可以继续读取旧的 `botId` 和 `conversationId` 字段。新客户端在 `mode` 为 `group` 时应使用 `participants`。

### 服务端到客户端协议

给标识答复的语音消息增加说话人字段：

```ts
type VoiceSpeakerFields = {
  speakerBotId: string;
  speakerName: string;
};
```

以下消息携带说话人字段：

- `reply.message`；
- `audio.started`；
- 已知说话人时的 `audio.stopped`；
- 在适用时带响应摘要的 `turn.completed`。

如果客户端需要在字幕出现前更新头像，可以增加 `speaker.changed` 消息。第一版也可以直接从 `reply.message` 和 `audio.started` 推断当前说话人。

不增加第二套音频传输。一个 WebSocket 和一个输出流足以满足需求，因为串行化由服务端负责。

### 数据库变更

增加会话模式枚举：

```prisma
enum VoiceSessionMode {
  direct
  group
}
```

给 `VoiceSession` 增加默认值为 `direct` 的 `mode`。第一版迁移保留现有 `botId` 和 `conversationId`，保证直接会话兼容。群聊会话可以把默认说话人的 Bot 和 conversation 写入这两个字段作为兼容锚点，但群聊路由必须使用参与成员行，不能使用这两个字段决定响应者。

增加 `VoiceSessionParticipant`：

```prisma
model VoiceSessionParticipant {
  id          String       @id @default(uuid()) @db.Uuid
```

参与成员行保存通话开始时的 Bot 声音快照。通话期间修改 Bot 资料不得改变已经开始的说话人身份。

增加 `VoiceTurnResponse`：

```prisma
enum VoiceTurnResponseStatus {
  queued
  processing
  speaking
  completed
  silent
  skipped
  superseded
  failed
}
```

```prisma
model VoiceTurnResponse {
  id                  String                   @id @default(uuid()) @db.Uuid
  turnId              String                   @db.Uuid
  turn                VoiceTurn                @relation(fields: [turnId], references: [id], onDelete: Cascade)
  botId               String                   @db.Uuid
  bot                 Bot                      @relation(fields: [botId], references: [id], onDelete: Cascade)
  runId               String?                  @unique @db.Uuid
  run                 Run?                     @relation("VoiceTurnResponseRun", fields: [runId], references: [id], onDelete: SetNull)
  ordinal             Int
  status              VoiceTurnResponseStatus  @default(queued)
  assistantMessageIds String[]                 @default([])
  generation          Int                     @default(0)
  startedAt           DateTime?
  completedAt         DateTime?
  error               Json?
  createdAt           DateTime                 @default(now())
  updatedAt           DateTime                 @updatedAt

  @@unique([turnId, botId])
  @@unique([turnId, ordinal])
  @@index([turnId, status])
  @@index([botId, status, createdAt])
}
```

直接会话继续使用 `VoiceTurn.runId`。群聊语音回合使用每个 Bot 一行的响应记录。这样既不需要破坏现有直接会话关系，也可以持久化多个 Bot 的响应顺序和恢复状态。

`silent` 是一等的终态响应状态。当所有响应机会都进入终态后，父级 `VoiceTurn` 变为 `completed`，即使所有 Bot 都选择了 `silent`。一个静默完成的群聊语音回合是成功结果，不能因为没有助手消息而自动重试。

给 `ChannelRound` 增加模式：

```prisma
enum ChannelRoundMode {
  chat
  voice
}
```

已有数据默认使用 `chat`。语音回合使用 `voice`、`voiceTurnId` 和已经解析出的响应者快照。最终字段名称可以在实现阶段调整，但回合必须持久化：

- 来源语音会话；
- 来源语音回合；
- 已选响应者 ID；
- 回合预算；
- 完成后不创建成员互相追问回合的规则。

迁移应在最终结构确定后增加 `(sessionId, status, expiresAt)`、`(turnId, ordinal)` 和 `(channelId, mode, status, createdAt)` 等必要索引。

## 服务端流程

### 创建会话

`VoiceService.create` 应拆分为直接会话和群聊会话两个明确的校验路径：

1. 根据 `channelId` 加载频道，拒绝归档或不存在的频道。
2. 加载群聊当前活跃成员、Bot 资料和 conversation。
3. 校验请求中的参与成员 ID：
   - 去重并保留请求顺序；
   - 至少一个，最多六个；
   - 每个 ID 都必须属于当前群聊、对应活跃 Bot 且不是子代理身份；
   - 默认说话人必须属于参与成员集合。
4. 为会话确定 Provider。
5. 保存每个参与成员的声音快照。
6. 在一个事务中保存会话和参与成员行。
7. 返回会话视图和重连票据。

现有 owner session 的并发会话上限继续有效。上限按语音会话数计算，不按参与成员数计算。

### 接收群聊语音转写

增加语音专用接收方法，不要给公共群聊消息方法增加大量隐藏参数：

```ts
acceptGroupVoiceTranscript(input: {
  sessionId: string;
  turnId: string;
  text: string;
  durationMs: number;
  language?: string;
}): Promise<{
  accepted: boolean;
  userMessageId: string | null;
  responseIds: string[];
}>;
```

该方法必须：

1. 校验会话所有者并确认会话处于活跃状态。
2. 执行最大转写长度和有意义转写校验。
3. 锁定群聊执行和语音会话回合键。
4. 使用 `(sessionId, turnId)` 拒绝重复最终转写，但对重复请求返回原始接受结果。
5. 加载参与成员快照和当前群聊成员状态。
6. 根据语音专用唤醒规则解析响应者。
7. 在群聊中创建一条用户 `ChannelMessage`，并带上语音元数据：

   ```json
   {
     "type": "text",
     "voice": {
       "sessionId": "...",
       "turnId": "...",
       "durationMs": 1234,
       "provider": "..."
     }
   }
   ```

8. 创建一条 `VoiceTurn`，并为每个解析出的 Bot 创建一条 `VoiceTurnResponse` 响应机会。
9. 创建一个带有响应顺序的 `voice` 模式 `ChannelRound`。
10. 为所有已选群聊成员安排转录投影。
11. 如果新转写确认来自抢话，则取消或淘汰该会话当前活跃的旧语音回合。
12. 提交事务后再推进回合。
13. 异步推进语音回合。

消息 client id 必须稳定，例如 `voice:${sessionId}:${turnId}`。客户端因网络超时重试时，事务不能创建第二条用户消息、第二个回合或第二组响应。

### 语音专用群聊回合

可以给 `AgentMessaging.createGroupRound` 增加预解析响应者快照，也可以新增 `createVoiceGroupRound`。推荐新增独立方法，因为这样普通文本路由不会被语音参数污染。

语音回合必须：

- 使用用户最终转写已经解析出的响应者 ID；
- 保留参与成员顺序；
- 在推进时跳过已经失活或从群聊中移除的成员；
- 每个响应者最多创建一条投递；
- 没有可见 `SendToUser` 消息的投递视为成功的静默完成；
- 静默完成后不创建占位消息，也不创建 TTS 项目，并继续推进下一个响应机会；
- 不从 Bot 消息中的点名重新解析响应者；
- 第一版只使用一轮；
- 把会话和语音回合标识带入 run 上下文；
- 在投递完成后跳过普通成员互相追问回合。

`advanceRound` 只在文本行为会创建下一轮或唤醒其他成员的地方根据 `round.mode` 分支。投递锁、run 创建、可见性窗口、重试处理和 Outbox 发布应尽量共用。

目标 Bot 接收普通群聊提示词，并追加以下语音专用指令：

```text
你正在群聊中处理一个实时语音回合。
只能以自己的身份回答，保持内容简洁且完整。
先判断当前回合是否与你的职责和用户请求有关。
如果无关，请直接静默完成，不要调用 SendToUser。
不要发送填充性确认、道歉或“我跳过本轮”之类的话。
不要为了让其他成员响应而点名其他成员。
不要为当前回合创建成员追问。
如果当前回合相关，最多发送一条用户可见答复。
```

提示词还应说明用户点名了谁，以及当前 Bot 是否为默认说话人，不得暴露内部会话 ID 或数据库状态。

### 响应发布和语音投递

群聊 Bot 发送可见答复时：

- 频道消息通过现有群聊 Outbox 持久化；
- 消息元数据包含 `voice.sessionId`、`voice.turnId` 和 Bot 响应 ID；
- `VoiceReplySource` 使用响应 run ID 将消息路由到会话 sink；
- sink 使用该 Bot 的声音快照发送带说话人身份的字幕，并加入 TTS 队列；
- 一个没有可见 `SendToUser` 消息就完成的 run 将对应 `VoiceTurnResponse` 标记为静默完成，不产生字幕或音频；
- 已经写入聊天的答复即使音频被打断也保留；
- 重复的可见消息通知不能重复说出同一条消息。

现有 `VoiceReplySource` 以 run ID 为键，可以继续复用。群聊路径为每个响应 run 注册一个 sink。sink 必须从响应记录获取 Bot 身份，不能从会话的兼容主 Bot 字段推断。

## 说话队列和音频行为

当前实时连接通过 `ttsChain` 串行处理 TTS，但其 TTS pool 使用一个固定会话声音。群聊语音需要：

- 队列项目包含 `responseId`、`botId`、`voice`、文本、音频代际和消息类型；
- 任意时刻最多一个活动队列项目；
- 每个活动参与成员一个 `WarmTtsPool`，或者使用按声音键控的有界共享池；
- 抢话时取消当前项目；
- 真实答复到达后丢弃仍在队列中的进度播报；
- 已取消或已淘汰的响应不能合成音频；
- 每条字幕和音频开始事件都带说话人身份。

队列应在数据库 ordinal 之外使用递增的本地序号。数据库 ordinal 决定预期顺序，本地序号处理同一个 Bot 产生多个可见消息时的到达顺序，防止完成回调重排。

服务端不能等待后续 Bot 的响应后才开始前一个 Bot 的响应。服务端只需等待当前响应的可见消息和音频完成，再推进下一个响应机会。预期节奏如下：

```text
用户转写
  -> Bot A run
  -> Bot A 可见答复和音频，或 Bot A 静默完成
  -> Bot B run
  -> Bot B 可见答复和音频，或 Bot B 静默完成
```

第一版每个响应机会最多产生一条可见文本消息，也可以产生零条消息。现有 `GROUP_MAX_MESSAGES_PER_TURN` Outbox 限制仍作为最终保护，但语音策略应拒绝或抑制同一个 Bot 的第二条响应。静默完成是正常终态，不是失败，也不是要求 Bot 再说一句的理由。

## 唤醒路由

### 文本形式的点名

复用现有的有边界成员句柄规则：

- 完整名称；
- 去空格的完整名称；
- 名称的第一个词；
- `@everyone` 和 `@all`。

解析只针对当前最终用户转写，不扫描整个历史群聊记录。这样可以避免之前的一次点名影响之后的语音回合。

### 口语化名称

增加语音专用解析器，识别自然口语中的成员称呼。解析器应归一化：

- Unicode 规范化；
- 大小写；
- 标点；
- STT 常见的分词和空格差异；
- 可选的 `@` token；
- 后续可以支持的配置别名。

应支持以下形式：

- “Research，帮我总结一下。”；
- “问一下 Sales 对客户影响的看法。”；
- “QA，你能确认这个修复吗？”；
- “大家都说一下。”。

名称匹配应优先使用 Bot 的精确归一化名称和已配置别名。不能从更长单词中的偶然子串唤醒 Bot。出现歧义时应回退到默认说话人并记录诊断事件，不能推测性地唤醒多个 Bot。

### 成员关系变化

参与成员列表在会话创建时固定。如果已选 Bot 被移出群聊或变为非活跃状态：

- 该 Bot 尚未开始的待处理投递被跳过；
- 不再为该 Bot 创建新的投递；
- 客户端在下次会话刷新时，或通过专用控制消息，收到参与成员状态变化；
- 只要仍有一个参与成员，会话继续有效。

如果默认说话人被移除，服务端选择 ordinal 最小的剩余参与成员，并在会话状态中发送新的默认说话人。

## 取消、重试和重连

### 重复最终转写

最终 STT 事件必须使用 `(sessionId, turnId)` 只接受一次。重复最终结果返回原始接受结果，不能创建第二个用户消息、回合、run 或音频响应。

### 抢话

WebSocket 路径立即停止音频，但服务端等待最终 STT 结果后再创建新的群聊消息。如果最终转写有意义，则旧语音回合被淘汰。旧回合的活动 run 通过群聊文本抢占使用的同一运行时取消接口取消；其待处理投递和响应行标记为 `superseded`。

如果最终转写为空或没有意义，旧回合按照现有单 Bot 语音策略保持已完成或已中断，不创建新的群聊回合。

### Worker 失败

如果某个 Bot run 失败：

- 响应行记录失败；
- 群聊投递使用现有失败路径；
- 调度器推进到下一个响应机会；
- 只有在后续没有任何可能满足当前用户请求的响应时，客户端才收到简洁错误字幕；
- 通话本身继续保持有效。

失败的 Bot 不能无限重试。复用群聊重投递上限，并让响应行的幂等键包含投递尝试编号。

### 重连

重连票据继续授权同一个会话。新的 WebSocket 就绪后，服务端发送当前会话状态和活动回合摘要。不得重复问候，也不得重播已经完成的音频。尚未开始的响应可以继续；连接丢失时已经被打断的音频项目标记为中断，不自动重播，除非客户端明确重试回合。

### 会话过期

现有最大会话时长继续作为硬限制。会话过期时：

- 停止活动音频代际；
- 取消活动 TTS 流；
- 将排队响应标记为取消；
- 将会话标记为结束；
- 保留已经持久化的频道消息和转写。

## 循环防护和安全限制

以下规则是强制要求：

1. 只有用户最终 STT 转写可以创建语音回合。
2. Agent 消息、进度播报、反应和 Bot 之间的消息不能创建新的语音转写回合。
3. 语音回合不能创建普通文本成员互相追问回合。
4. Bot 输出中的成员点名不能自动唤醒其他参与成员。
5. 每个解析出的 Bot 最多获得一次响应机会，并且允许零条可见响应。
6. 第一版语音回合只执行一轮。
7. 群聊 Outbox 和十条消息预算继续作为最终持久化保护。
8. 一个会话不能同时有两个活动语音回合。
9. 响应幂等键防止可见消息和语音重复。
10. 抢话在新回合启动前淘汰旧回合的待处理响应。
11. Bot run 只能在当前群聊投递上下文中调用 `SendToUser`。
12. 语音群聊提示词明确告诉 Bot 不要发起成员追问。
13. Bot 如果判断当前回合无关，应直接静默完成，不得发送填充性答复。

增加以下指标和结构化事件：

- `voice.group.turn.created`；
- `voice.group.responders.resolved`；
- `voice.group.response.started`；
- `voice.group.response.completed`；
- `voice.group.response.silent`；
- `voice.group.response.skipped`；
- `voice.group.response.superseded`；
- `voice.group.speaker.changed`；
- `voice.group.loop_guard`；
- `voice.group.duplicate_final`。

事件应包含 session id、turn id、channel id、bot id、响应 ordinal 和安全的原因码，不得包含 Provider 密钥、原始音频或私有提示词内容。

## 客户端实现

### 桌面端

将桌面端入口从只对 `bot_dm` 显示，扩展为对 `bot_dm` 和 `group` 显示。

直接频道继续使用当前 `LiveVoiceLayer` 行为。群聊需要：

- 传入频道成员列表，而不是一个选中的 Bot；
- 在创建会话前打开参与成员选择器；
- 发送 `participantBotIds` 和 `defaultSpeakerBotId`；
- 显示参与成员标签和当前说话人；
- 用说话人名称更新字幕；
- 会话创建失败时重置选择器状态；
- 保持停止、最小化、静音、重试和重连行为不变。

Hook 可以从 `useLiveVoice(botId, channelId)` 演进为会话目标对象：

```ts
useLiveVoice({
  channelId,
  botId,
  participantBotIds,
  defaultSpeakerBotId,
});
```

传输仍然只有一个 WebSocket。渲染器不得为每个 Bot 创建一个 socket。

### iOS 和 Android

共享契约的扩展必须让原生客户端可以继续使用直接语音会话。第一版桌面端发布时，原生客户端可以暂时隐藏群聊语音入口，但必须继续解析扩展后的直接会话响应。

后续原生阶段增加：

- 参与成员选择；
- 带说话人身份的字幕；
- 当前说话人头像变化；
- 相同的开始、停止和打断语义。

原生客户端不需要知道群聊回合 ID 或 Worker run。

- “所有人”转写为所有已选 Bot 各提供一次机会。
- 未点名转写按推荐策略唤醒默认说话人。
- Bot 可以判断无关并静默完成。
- 静默完成不创建字幕、占位消息或音频。
- 静默完成不会阻止下一个响应机会执行。
- 已移除参与成员被跳过。
- 一个响应失败后推进到下一个响应机会。
- 响应重试不会重复频道消息。
- 群聊语音回合不会创建普通成员追问回合。
- 抢话会在新回合开始前取消旧回合待处理响应。
- 重连不会重播已完成音频。
- 关闭会话会取消活动和排队中的语音。

### 端到端客户端测试

- 语音开启时，群聊和直接 Bot 频道显示正确入口。
- 群聊开始通话前必须至少选择一个参与成员。
- 服务端返回的成员顺序反映在界面中。
- 字幕显示当前说话人。
- 两个 Bot 之间切换时头像更新。
- 停止、最小化、重试、麦克风静音和扬声器静音保持现有行为。
- 某个 Bot 静默时界面不出现无意义的系统提示。
- 连续点击开始不会创建第二个会话。

## 兼容性和迁移

迁移后必须仍然可以读取和关闭现有直接语音会话。旧客户端继续发送当前的 `botId` 结构。服务端对直接会话返回安全默认值：

- `mode: "direct"`；
- 一个代表现有 Bot 的参与成员；
- `defaultSpeakerBotId` 等于现有 Bot；
- 说话期间 `activeSpeakerBotId` 等于现有 Bot。

除语音回合之外，现有文本群聊频道、群聊路由、群聊回合数量和群聊提示词必须保持行为不变。实现必须使用语音专用模式或明确上下文标记，不能修改 `resolveGroupResponderIds` 的默认行为。

当前工作区包含与本方案无关的未提交修改。实现时只能修改本方案覆盖的文件，必须保留这些修改，除非另行请求，不得执行 reset、clean、commit 或打包操作。

## 运行和发布计划

通过服务端能力检查和客户端功能检查逐步发布：

1. 发布仍支持直接语音的数据库和服务端代码。
2. 只有服务端声明支持群聊语音时，才开放群聊会话创建。
3. 聚焦集成测试通过后，再开放桌面端群聊入口。
4. 监控会话创建失败、重复最终转写、响应淘汰、队列延迟、TTS 失败和循环保护事件。
5. 保留只关闭群聊语音而不影响直接语音的服务端开关。

回滚时应关闭群聊语音创建，继续保留现有直接语音。如果必须回滚迁移，在所有群聊会话结束前保留新增表；当仍有会话可能重连时，不得删除参与成员或响应数据。

## 验收标准

实现完成必须满足：

- 用户可以从群聊频道开始实时语音。
- 用户可以在通话开始前选择一个或多个活跃群聊 Bot。
- 服务端拒绝不属于当前群聊的选择成员。
- 用户明确说出已选 Bot 名称时，对应 Bot 获得响应机会。
- 用户说“所有人”时，所有已选 Bot 按确定顺序各获得一次机会。
- 用户没有点名时，使用文档规定的默认说话人策略。
- 每个解析出的 Bot 都可以判断无关并静默完成。
- 静默 Bot 不产生填充消息、字幕或音频。
- 静默 Bot 不阻塞后续已选响应者。
- Bot 答复继续出现在现有群聊历史中。
- 任意时刻最多一个 Bot 产生音频。
- 字幕和头像能够识别当前说话人。
- Bot 答复中的点名不会自动唤醒其他 Bot。
- 重复 STT 最终结果、重试和重连不会重复消息或语音。
- 抢话会停止当前音频并淘汰过期的待处理响应。
- 群聊语音回合不会形成无界成员追问链。
- 会话过期和主动停止会清理活动及排队资源。
- 现有直接语音会话和文本群聊行为保持兼容。
- 契约、消息、服务端和桌面端聚焦测试通过。
- 普通验证不会启动开发服务器、后端服务、前端服务器或渲染脚本。

## 实现前待确认事项

本方案不需要继续进行架构探索即可实现。以下产品选择会改变用户可见行为，应在编码前确认：

1. 未点名群聊语音是只给默认说话人，还是给所有已选成员。推荐只给默认说话人。
2. 参与成员选择器打开时是否默认选中全部活跃成员。推荐默认全选。
3. Bot 在第一次语音答复后是否可以再发送第二条可见消息。推荐不允许；每个解析出的 Bot 获得一次机会，可以发送零条或一条答复。
4. 第一版是否需要口语别名。推荐先支持精确归一化名称和常见称呼，后续再增加可配置别名。

如果没有记录其他决定，应按上述推荐值实现。
