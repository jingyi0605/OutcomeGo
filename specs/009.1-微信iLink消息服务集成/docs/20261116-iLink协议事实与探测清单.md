- **资料一致**：多个独立公开来源说法一致，尚未由本项目实测。
- **资料不一**：公开来源之间有出入，必须实测。
- **已实测**：任务 1.2 完成后填写，附日期和参考版本。

截至 2026-11-16，本文所有条目都还没有经过本项目实测。任务 1.2 的产出就是把每个探测项的「实测结论」填上。

**记录规则：** 不在仓库中写入任何真实的 bot token、用户标识、会话令牌、游标内容或聊天正文。样例一律使用占位符。

## 3. 协议事实（资料一致）

### 3.1 总体

- 业务基座地址 `https://ilinkai.weixin.qq.com`；登录后可能切换到账号专属域名。
- 媒体 CDN 基座地址 `https://novac2c.cdn.weixin.qq.com/c2c`。
- 全部业务接口为 HTTPS 加 JSON；接收使用长轮询，不是 WebSocket。
- bot 绑定在个人微信号上，一个微信号只能绑定一个 bot。
- 只支持单聊；bot 不能加入微信群。协议里存在 `group_id` 字段，但公开实现都只处理单聊。
- bot 不能主动发起会话，只能在用户来消息后回复。

### 3.2 接口

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `ilink/bot/get_bot_qrcode` | GET 或 POST（见 P1） | 申请登录二维码 |
| `ilink/bot/get_qrcode_status` | GET | 长轮询扫码状态，客户端超时约 35 秒 |
| `ilink/bot/getupdates` | POST | 长轮询收消息 |
| `ilink/bot/sendmessage` | POST | 发消息 |
| `ilink/bot/getuploadurl` | POST | 申请媒体上传参数 |
| `ilink/bot/getconfig` | POST | 取账户配置（输入中提示用的票据） |
| `ilink/bot/sendtyping` | POST | 输入中提示 |
| `ilink/bot/msg/notifystart` | POST | 通知开始监听（较新版本） |
| `ilink/bot/msg/notifystop` | POST | 通知停止监听（较新版本） |

### 3.3 请求头与公共请求体

| 请求头 | 说明 |
| --- | --- |
| `Content-Type: application/json` | 全部业务 POST |
| `AuthorizationType: ilink_bot_token` | 固定值 |
| `Authorization: Bearer <bot_token>` | 二维码确认后下发的凭据 |
| `X-WECHAT-UIN` | 随机 uint32 的十进制字符串再做 base64，每次请求重新生成 |
| `iLink-App-Id`、`iLink-App-ClientVersion` | 较新版本要求，取值来自官方包的声明字段 |
| `SKRouteTag` | 可选的路由标签 |

业务 POST 的请求体都带 `base_info`，其中 `channel_version` 为客户端版本；较新版本还带 `bot_agent`（自声明的客户端身份，只用于可观测）。

### 3.4 登录

- 二维码确认后返回 `bot_token`、`baseurl`、`ilink_bot_id`、`ilink_user_id`。其中 `ilink_user_id` 是扫码的微信用户。
- 状态查询可能返回切换基座地址的指示。
- 二维码过期后需要重新申请；官方实现自动刷新最多 3 次。
- 官方实现在申请二维码时会带上最多 10 个最近的本地 token。

### 3.5 接收

- `getupdates` 请求体为 `get_updates_buf` 加 `base_info`；首次请求传空字符串。
- 服务端挂起连接直到有消息或超时，默认约 35 秒；响应里的 `longpolling_timeout_ms` 是下一轮的建议超时。
- 客户端本地超时应视为空轮询。
- `get_updates_buf` 是不透明缓冲区，原样保存，不解码不修改；以 bot 账号为粒度保存。
- token 变化、重新扫码、会话过期时应清空本地游标。
- 响应体示意（值均为占位符）：

```json
{
  "ret": 0,
  "msgs": [
    {
      "message_id": 0,
      "client_id": "<client-id>",
      "create_time_ms": 0,
      "from_user_id": "<user>@im.wechat",
      "to_user_id": "<bot>@im.bot",
      "session_id": "<user>@im.wechat#<bot>@im.bot",
      "context_token": "<opaque>",
      "item_list": []
    }
  ],
  "get_updates_buf": "<opaque>",
  "longpolling_timeout_ms": 35000
}
```

- `message_id` 是 64 位无符号整数，必须无损解析。
- 消息内容在 `item_list` 中，一条消息可以同时包含文本和非文本项。官方实现允许没有 `context_token` 的入站消息，并会从混合项中提取文本。

### 3.6 发送与会话令牌

- 每条入站消息带 `context_token`；回复时必须原样回传，否则消息无法投递到正确的对话。
- 应以（账号，用户）为键缓存最近一次的令牌，不跨用户、不跨账号复用。
- 进程重启后如果没有恢复令牌，就失去回复能力；协议里没有单独"打开会话"的接口。
- 发送时带 `client_id`、消息类型（bot）、消息状态（finish）和 `item_list`。

### 3.7 媒体

- 全部媒体经 CDN 传输，内容用 AES-128-ECB（PKCS7）加密。
- 外发流程：`getuploadurl`（带明文大小、明文 MD5、密文大小、十六进制密钥、媒体类型）→ 本地加密 → 以 `application/octet-stream` 上传 → 从响应头 `x-encrypted-param` 取得下载引用 → 在 `sendmessage` 的媒体项中引用。
- 消息层只传引用，不传文件本体。
- 文字说明按官方做法作为独立的一条文本消息先发出。
- 入站语音可能带服务端转写文字。

### 3.8 错误

- `ret = 0` 表示业务成功；`ret` 或 `errcode` 非零都视为失败。
- `-14` 表示会话过期。官方实现在 `-14` 后对该账号暂停常规收发 1 小时。
- 建议的重连策略：普通失败等待 2 秒；连续 3 次失败后退避 30 秒。

## 4. 探测清单

每项在任务 1.2 中填写「实测结论」和日期。

| 编号 | 问题 | 公开资料的说法 | 可信程度 | 实测结论 |
| --- | --- | --- | --- | --- |
| P1 | 申请二维码用 GET 还是 POST；确认过程是否需要用户向客户端输入验证码或配对数字；二维码有效期多长 | 早期资料为 GET，较新版本为 POST 且带 `bot_type`；有资料提到"如出现配对数字需输入" | 资料不一 | 待填 |
| P2 | 扫码者之外的微信用户能否给该 bot 发消息；入站 `from_user_id` 是否等于登录返回的 `ilink_user_id` | 多数资料按"只有扫码者"描述；有实现提供了"允许的用户白名单"，暗示可能存在其他发送者 | 资料不一 | 待填 |
| P3 | 用已经用过的旧 `get_updates_buf` 再次请求，是否会重新下发同一批消息 | 没有资料说明；只有"拿到新值就保存"的建议 | 未知 | 待填 |
| P4 | 同一微信号移除后重新扫码，`ilink_user_id` 和 `ilink_bot_id` 是否保持不变 | 没有资料说明 | 未知 | 待填 |
| P5 | `sendmessage` 成功时是否返回消息标识；单条文本的长度上限；实际限速 | 有案例显示成功时只返回 `ret: 0`；有实现保守采用 1800 字符和每分钟 20 条 | 资料不一 | 待填 |
| P6 | 会话令牌的有效期；是否每条入站消息都下发新令牌 | 多数资料为 24 小时 | 资料一致，未实测 | 待填 |
| P7 | 外发图片、文件、视频是否都能真正出现在微信里 | 2026 年 4 月有资料称 bot 不能发文件；之后的多个实现声称图片、文件、视频都可发送；语音一致反馈为接受但不投递 | 资料不一 | 待填 |
| P8 | 入站媒体的下载地址来自哪个字段、主机范围、有效期；密钥的编码方式 | 有的用服务端签发的完整地址，有的用加密参数拼接；密钥存在"原始字节的 base64"和"十六进制字符串的 base64"两种编码 | 资料不一 | 待填 |
| P9 | `-14` 在 `getupdates` 和 `sendmessage` 上分别在什么条件下出现；冷却后是否能自愈 | `getupdates` 上表示账户会话过期；有案例显示使用旧会话令牌发送也会得到 `-14` | 资料不一 | 待填 |
| P10 | 不调用 `notifystart`、`notifystop` 是否影响收发 | 官方实现中调用失败只记录警告 | 资料一致，未实测 | 待填 |
| P11 | Bot Computer 容器能否访问 `ilinkai.weixin.qq.com` 和微信 CDN | 与本项目的出口策略有关，见 Spec 006.2 | 需在环境中验证 | 待填 |

### 探测方法提示

- P1、P4：用一次性脚本走完两次完整的扫码流程，记录各步骤的请求方法、状态值序列和返回的标识是否变化。
- P2：用第二个微信号尝试找到并给该 bot 发消息，观察是否到达以及 `from_user_id` 的值。
- P3：保存一次有消息返回的请求所用的旧游标，稍后用同一旧游标再请求一次。
- P5、P7：逐类型发送，在手机上确认是否出现；用逐步加长的文本找出上限。
- P6：间隔若干小时后用旧令牌回复，记录首次失败的时间点和错误码。
- P9：结合 P6 的结果，区分两个接口上的 `-14`。
- P11：在远端 debug computer 容器内执行只读的连通性检查，不改动网络策略。

## 5. 决策门

探测结论对设计的影响，在任务 1.2 结束时逐条处理。

| 探测项 | 如果结论是 | 则 |
| --- | --- | --- |
| P1 | 需要用户向客户端输入验证码 | 现有 `PluginDeviceLink` 契约没有输入通道。先以 `wechat_link_verification_required` 给出指引，并新增任务评估扩展设备链接契约（涉及 SDK、Server 和各客户端） |
| P1 | 只需在手机上确认 | 按 `design.md` §2.3.1 实现，无变化 |
| P2 | 其他用户也能发消息 | 设计不变：这些消息被标记为 `isAccountOwner = false`，由 Spec 009 拒绝。在技能和插件说明中注明"只响应账户所有者" |
| P2 | `from_user_id` 与 `ilink_user_id` 不是同一种标识 | 重新确定所有者判定依据并更新 `design.md` §3.2.5；在找到可靠依据之前不得发布 |
| P3 | 会重放 | 设计不变；`crash.test.ts` 以重放模式为主 |
| P3 | 不重放 | 设计不变（落盘队列已覆盖）；在文档中注明"入队前崩溃"窗口内的消息无法恢复，并尽量缩短该窗口 |
| P4 | 标识会变化 | 重新扫码会产生新的 Mapping 和 Channel。在插件说明中注明，并评估是否需要在 Spec 009 中增加"迁移旧会话"的能力 |
| P5 | 上限或限速与默认值不同 | 调整 `design.md` §3.2.6 的分片上限、manifest 的 `maxTextChars` 和限速常量 |
| P6 | 有效期不是 24 小时 | 调整安全窗口常量（保持比实测值少 1 小时） |
| P7 | 文件或视频可以投递 | 在 manifest 的 `messaging.outbound.media.kinds` 中加入对应类型并补测试 |
| P7 | 图片也不能投递 | 首版外发只支持文本，更新需求 5 和 README 的首版边界 |
| P8 | 下载主机不在 `weixin.qq.com` 子域内 | 更新域名校验规则，保持白名单方式 |
| P9 | `sendmessage` 上不会出现 `-14` | 去掉 `design.md` §2.3.5 中对应的分支 |
| P9 | 冷却后不能自愈 | 去掉探活步骤，`-14` 后直接清除凭据并要求重新扫码 |
| P10 | 必须调用 | 把 `notifystart` 失败从"只记录警告"改为"进入 `recovering` 并重试" |
| P11 | 不可达 | 该任务阻塞。与 Spec 006.2 的出口策略协调，在获得放行之前不继续阶段 4 |

## 6. 已知的平台限制（需要告知用户）

- 需要微信号已获得「微信 ClawBot」入口，该功能分批开放。
- 连接后必须先在微信里给 bot 发一条消息，Bot 才能回复。
- 用户超过约 24 小时未发消息后，Bot 无法回复，直到用户再次发消息。
- 不支持群聊。
- 存在"接口返回成功但消息未出现"的账号级情况，无法由客户端识别。
- 本功能通过微信面向 OpenClaw 开放的通道接入，可用性取决于腾讯的策略。
