# 需求：实时语音对话

状态：草案

日期：2026 年 11 月 6 日。

修订：2026 年 11 月 7 日。明确 TTS 只朗读 `SendToUser` 回复、抢话先停输出再替代 run、强制回声消除和重连票据。

## 阶段 0.1 已批准的产品基线

- 支持平台沿用当前代码库基线：macOS 桌面端、iOS 18 及以上、Android API 26 及以上。
- 第一版仍限定为一个已有 Bot 私聊中的一对一语音会话；实时语音继续与录音完成后批量转写的语音笔记保持独立。
- 单个语音会话最长 30 分钟，单个语音回合最长 60 秒。
- 发布时对所有用户提供能力，但仍受服务端开关、能力检查、Bot/channel 支持范围和账号限制共同控制；实现和验证完成前默认关闭。
- 现有语音笔记入口、协议和测试属于回归要求，不因实时语音增加而改变。

## 简介

OpenTeam 当前支持语音笔记。客户端完成本地录音后上传整个文件，服务端返回批量转写结果，再把文本放入普通消息编辑器。当前代码库还没有持久的双向音频会话、流式语音识别、语音合成、实时播放、语音活动检测或抢话中断能力。

本功能的目标是让用户与一个 Bot 进行持续的语音对话，并在 Bot 的回答生成过程中开始听到回复。功能必须保留 OpenTeam 现有的持久化会话模型、Agent 工具、运行取消、消息投递语义和账号授权，并支持 macOS 桌面端、iOS 和 Android。

## 术语

- **语音会话**：客户端与一个 Bot 对话之间经过认证、由服务端管理且有时限的连接。
- **语音回合**：一次已经确定的用户发言，以及对应的 Agent 回复尝试。
- **语音帧**：包含序列号和时间戳的一个二进制 Opus 数据包。
- **部分转写**：流式 STT 产生的文本，只在当前实时语音会话中显示，直到该回合结束。
- **最终转写**：被接受为用户消息内容，并通过现有 channel message 和 run 路径持久化的转写文本。
- **用户可见回复**：Agent 通过 `SendToUser` 工具发送并持久化为 `ChannelMessage` 的内容。Agent 的普通助手文本不展示给用户，也不朗读。
- **抢话**：Bot 播放语音时检测到用户开始说话，服务端立即停止音频输出；只有新发言的最终转写被接受后，才由现有消息替代路径取消旧 Agent 回合。
- **输出代次（generation）**：输出音频帧携带的编号。每条回复开始朗读、每次抢话或停止都会递增，客户端用它丢弃过时音频。
- **服务端媒体处理链路**：服务端拥有的解码器、重采样、VAD、STT、Agent 桥接、TTS、编码器和背压处理。
- **语音 Provider**：由服务端调用、提供流式 STT 和流式 TTS 的适配器。客户端永远不会获得 Provider 密钥。

## 范围

### 范围内

- 以一个已有 Bot 私聊为目标的一对一语音会话。
- 经过认证的会话创建和一次性 WebSocket 升级票据。
- 通过 WebSocket 双向传输二进制音频。
- 版本化的 Opus 帧协议，以及服务端解码和编码。
- 服务端将音频重采样为统一的内部 PCM 格式。
- 服务端 VAD、回合开始/结束检测、静音超时和最大回合时长。
- 流式 STT 的部分转写和最终转写事件。
- 第一阶段必须同时提供火山引擎豆包语音和 Deepgram 的流式 STT 适配器。
- 通过现有持久化 channel/run 路径创建最终用户回合。
- 将 Agent 的 `SendToUser` 回复按消息送入实时语音会话。
- 送入 TTS 前的语音文本规范化。
- 流式 TTS 和客户端播放。
- 各平台系统回声消除。
- 第一阶段必须同时提供火山引擎豆包语音和 Deepgram 的流式 TTS 适配器。
- 抢话、停止、取消和回合替代行为。
- 会话重连和会话过期规则。
- macOS 桌面端、iOS 和 Android 的采集、编码、解码、播放和生命周期适配。
- 服务端 Provider、模型、声音、语言、限制和功能开关配置。
- 账号级配额、并发限制、字节数限制、时长限制和 Provider 密钥隔离。
- 单元测试、协议测试、服务端集成测试、浏览器测试、原生端测试和设备验证。
- 最终转写及 Agent 回复与普通聊天记录之间的持久化对账。

### 范围外

- 替换现有语音笔记功能。
- 客户端直接调用 Provider API，或在客户端保存 Provider API 密钥。
- 第一版接入语音到语音模型会话。
- 多用户群组语音房间。
- PSTN 或电话呼叫。
- 用户离开应用后仍持续运行的后台语音会话。
- 跨平台 WebRTC 媒体协商。
- 默认持久化原始音频。
- 客户端断线后的服务端音频自动回放。
- 通过 Siri、Android App Actions、通知或外部 Connector 自动发起语音会话。
- 将现有文本 Agent Runtime 改造成原生音频 Runtime。
- 朗读 Agent 的普通助手文本（`agent.delta`）。
- 第一版在 `SendToUser` 工具参数生成过程中流式朗读；是否实现由阶段 0 测量决定。

## 需求

### 需求 1：会话授权和生命周期

**用户故事：** 作为已登录用户，我希望为有权限访问的 Bot 启动语音会话，同时不暴露 Bearer Token 或 Provider 凭据。

#### 验收标准

1. 当客户端请求创建会话时，服务端必须先使用现有用户会话完成认证，之后才能返回任何语音会话数据。
2. 创建会话时，会话必须绑定到且只能绑定到一个 Bot、一个 conversation、一个 channel、一个账号会话和一个客户端平台。
3. 服务端返回 WebSocket 票据时，票据必须是一次性的、有较短有效期的，并在存在 Origin 时绑定 Origin，且不能用于其他 Bot 或会话。
4. WebSocket 升级时，用户 Bearer Token 不得出现在 URL、WebSocket 负载、服务端日志或客户端调试状态中。
5. 会话过期、授权被撤销、超过服务端限制时，服务端必须关闭媒体连接，并释放解码器、Provider、计时器、队列和数据库资源。
6. 客户端显式结束会话时，服务端必须把会话设为终态，不再接受迟到的音频帧。
7. 新会话会超过账号或 Bot 并发限制时，服务端必须返回结构化且可安全重试的错误。

### 需求 2：音频传输和服务端媒体处理

**用户故事：** 作为用户，我希望双向音频传输具有可预测的延迟，并由服务端负责编解码和格式转换。

#### 验收标准

1. 客户端连接时，必须协商一个受支持的协议版本；服务端必须返回选定的编码格式、采样率、声道数、帧时长和最大帧大小。
2. 客户端发送音频时，必须使用带有递增序列号和采集时间戳的二进制 Opus 帧。
3. 服务端收到帧时，必须在解码前校验帧头、长度、序列窗口、会话身份和字节预算。
4. 服务端解码后，必须将音频规范化为统一的有符号 16 位单声道 PCM。
5. 帧格式错误、重复帧超出允许的抖动窗口、帧过大或序列号超前过多时，服务端必须拒绝该帧或关闭会话，不能无限缓冲。
6. 服务端生成输出音频时，必须按照协商的客户端编码格式编码并以二进制帧发送。
7. 发送方超过队列或 credit 窗口时，服务端必须施加背压；如果拥塞持续，必须关闭会话，而不能静默丢弃语音。
8. 除非未来单独批准明确的诊断模式，服务端不得持久化原始输入或输出音频。

### 需求 3：语音活动和回合检测

**用户故事：** 作为用户，我希望自然地说话，而不必为每句话按一次发送按钮。

#### 验收标准

1. 解码后的输入超过配置的语音阈值并持续达到最短时长时，服务端必须发送 `turn.started`。
2. 语音低于静音阈值并持续达到结束静音时长时，服务端必须结束该回合的 STT 输入。
3. 回合超过最大输入时长时，服务端必须结束当前分段；只有检测到新的语音开始后才能开始下一段。
4. Bot 播放音频时检测到用户说话，服务端必须发送 `barge_in`，停止 TTS 和排队的输出音频，并递增输出代次；此时不得取消 Agent run。
5. 抢话后的新发言产生被接受的最终转写时，旧 run 必须通过现有用户消息替代路径取消；新发言没有产生有效转写时，旧 run 必须继续完成，其后续回复只展示不自动朗读。
6. VAD 阈值和计时器必须在服务端可配置，并限制在安全范围内。
7. 客户端必须显示 listening、processing、speaking、interrupted 和 error 状态，且不能把部分转写当作持久化消息。

### 需求 4：流式语音识别

**用户故事：** 作为用户，我希望尽快看到自己正在说的话，并让最终转写准确地发送给 Bot。

#### 验收标准

1. 语音回合开始时，服务端必须打开或复用 Provider 的流式 STT 通道，并且不能向客户端发送 Provider 凭据。
2. Provider 产生部分文本时，服务端必须发送与当前语音回合关联且有大小限制的部分转写事件。
3. Provider 产生最终文本时，服务端必须为该回合发送且只发送一个最终转写事件。
4. 未识别到语音时，服务端必须结束回合，不得创建用户消息，并在会话状态中说明结果。
5. Provider 失败或超时时，服务端必须以可重试错误结束当前回合；在安全的情况下应保持语音会话可继续使用。
6. Provider 输出必须先规范化为 OpenTeam 的统一转写结果，再交给客户端或 Agent 代码。
7. STT 核心接口不得暴露 Provider 专用的 WebSocket 消息、鉴权字段或事件名称；新增 Provider 只能实现适配器和注册信息，不得修改会话状态机。
8. 火山引擎和 Deepgram 适配器必须把部分转写、最终转写、连接失败、超时和取消统一映射为 OpenTeam 事件和错误码。

### 需求 5：Agent 集成和持久化

**用户故事：** 作为用户，我希望最终语音回合像普通 OpenTeam 消息一样支持工具、记忆、取消和历史记录。

#### 验收标准

1. 最终转写被接受时，服务端必须通过现有幂等消息路径创建用户 channel message。
2. 最终用户消息必须保留安全可展示的语音元数据，包括会话 ID、回合 ID、时长和转写 Provider 元数据。
3. 每个被接受的语音回合最多只能创建一个逻辑 run。
4. 服务端必须把 run 与语音回合关联；该 run 每条 `SendToUser` 文本回复持久化后，必须按消息顺序送达活动语音会话。
5. 现有 Agent 工具、权限、上下文会话、记忆和持久化助手消息行为必须继续可用。
6. 语音回合被新发言替代时，服务端必须使用现有用户消息替代路径，并把语音回合标记为 superseded；用户显式停止时，必须使用现有 `stop` 取消路径，并标记为 interrupted。不得新增 computer 取消原因。
7. Agent 的每条 `SendToUser` 回复都必须出现在普通 channel 历史中；活动语音会话必须按 `messageId` 与持久化消息对账，进程内投递遗漏时必须按 run 补齐，且不得重复朗读。
8. 同一语音回合的用户消息幂等键必须由服务端生成；重试、重连或进程内重放不得创建重复用户消息。
9. 语音 run 必须保留普通用户 run 的回复提醒和投递义务；服务端只能通过隐藏提示告知 Agent 当前是语音对话，且不得改变非语音 run 的请求内容。

### 需求 6：流式语音合成和播放

**用户故事：** 作为用户，我希望 Bot 回复尚未全部生成时就开始播放，并且在我说话时迅速停止。

#### 验收标准

1. 一条 `SendToUser` 文本回复送达语音会话后，服务端必须先做语音文本规范化（去除 Markdown、替换代码块和 URL），再按句子边界请求流式 TTS 音频；聊天历史保留原始内容。
2. 服务端必须按顺序发送输出音频帧，并为每帧标识输出代次和代次内序列号。
3. 服务端必须按播放速度发送输出音频；TTS 产生音频快于实时播放时，必须暂停读取 Provider 流，而不是关闭会话。
4. 客户端必须维护有界抖动缓冲，并在达到配置的启动缓冲后开始播放。
5. 抢话或停止事件被接受时，客户端必须迅速停止播放，并丢弃已停止代次的所有输出帧，包括在途帧；服务端必须停止生成或转发过时音频。
6. TTS 在部分音频已经播放后失败时，客户端必须保留部分回复状态，并显示可恢复的会话错误。
7. 即使播放被中断，Agent 的回复仍必须作为普通聊天内容保留。
8. 附件、图片和 secret request 类回复不得朗读其内容，只朗读固定的本地化提示；发往外部 Connector 的 `SendToUser` 不得朗读。
9. TTS 核心接口必须支持增量文本输入、增量 PCM 输出、取消、关闭和调用方背压；Provider 专用的会话握手和结束消息只能存在于适配器内部。
10. 火山引擎和 Deepgram 适配器必须支持各自流式 TTS 会话的连接、会话开始、增量文本、结束和音频事件转换。

### 需求 7：平台支持

**用户故事：** 作为用户，我希望 macOS、iOS 和 Android 具有相同的语音对话语义，同时各平台使用正确的音频 API。

#### 验收标准

1. macOS 必须能够采集麦克风音频、编码 Opus 帧、打开语音 WebSocket、解码输出帧并通过桌面客户端播放音频。
2. iOS 必须使用 AVAudioSession 和 AVAudioEngine 或等效原生链路处理采集、路由变化、中断、输出和麦克风权限。
3. Android 必须使用 AudioRecord/AudioTrack 或等效低延迟链路，处理音频焦点和路由变化，并在支持的前台生命周期转换中保留会话状态。
4. Kotlin Multiplatform 共享核心必须负责协议模型、会话状态、重连策略和平台无关的命令处理。
5. 原生代码必须负责麦克风权限、音频设备、编解码绑定、播放时钟、音频焦点/会话类别和生命周期回调。
6. 现有语音笔记入口必须继续可用，且不能静默启动实时语音会话。
7. 每个平台都必须在采集链路中启用系统回声消除，并让播放与采集共用同一音频引擎或会话，使系统能用播放信号消除回声。
8. 回声消除不可用时，客户端必须向服务端声明；服务端必须在该会话的播放期间关闭基于 VAD 的抢话，只接受显式停止。
9. Android 必须在 `minSdk` 26 及以上的所有设备上完成 Opus 编码，不能依赖仅从 API 29 起提供的 `MediaCodec` Opus 编码器。

### 需求 8：重连和生命周期行为

**用户故事：** 作为用户，我希望短暂的网络或设备中断能够以可预测的方式结束，而不会破坏会话记录。

#### 验收标准

1. WebSocket 在最终转写被接受前断开时，服务端必须丢弃未完成回合，且不能保留部分消息。
2. WebSocket 在最终转写被接受后断开时，服务端必须继续执行并完成持久化 run 和 channel message，即使客户端已经离线。
3. 客户端在会话租约内重连时，必须先通过已认证的 HTTP 请求为该会话申请新的一次性票据；服务端必须作废旧票据，新连接成功后关闭旧连接，并返回当前会话状态和持久化回合结果。
4. 已播放或未确认的音频帧在重连后不得自动重放。
5. iOS 和 Android 的后台化、电话、蓝牙变化、音频焦点丢失、媒体服务重置和麦克风丢失必须产生明确的会话状态转换。
6. 自动重连必须使用有界指数退避，并在授权失败、用户显式停止或会话进入终态后停止。

### 需求 9：配置、限制和运维

**用户故事：** 作为服务端管理员，我希望能够配置该功能、了解成本，并防止异常客户端耗尽所有音频资源。

#### 验收标准

1. 实时语音配置必须与批量语音笔记配置分开；当能力兼容时，Provider 适配器可以复用已经验证的凭据。
2. 配置必须包括启用状态、Provider、适配器版本、Base URL 或 Provider 默认端点、STT 模型、TTS 模型、声音、语言、编码格式、最大会话时长、最大回合时长和并发限制。
3. Provider 密钥必须留在服务端，在视图和日志中脱敏，并通过服务端连接检查验证。
4. 服务端必须提供会话数、活动音频时长、解码错误、STT 延迟、TTS 首段音频延迟、Agent 延迟、抢话次数和关闭原因等安全诊断数据。
5. 限制必须覆盖每个账号的活动会话数、每个 Bot 的活动会话数、会话时长、输入字节数、输出字节数、队列大小和 Provider 并发数。
6. 指标和日志必须包含关联 ID，但不得包含原始音频、Provider 密钥、Bearer Token 或未脱敏转写内容。
7. Provider 注册表必须根据能力声明检查 STT/TTS 是否可用；配置界面必须同时展示火山引擎和 Deepgram 的配置卡片，并允许管理员选择默认 Provider；新增 Provider 时不得改变客户端协议。
8. 会话创建时必须固定所选 Provider 和经过校验的配置快照；运行中的会话不得因为管理员切换默认 Provider 而改变。

### 需求 10：兼容性和发布安全

**用户故事：** 作为维护者，我希望在发布新功能时，现有客户端和服务端继续正常工作。

#### 验收标准

1. 关闭实时语音的服务端必须继续支持文本聊天和语音笔记，行为与之前一致。
2. 客户端检测到语音能力不可用时，必须隐藏或禁用实时语音控件，并显示可操作的说明。
3. 未知的可选语音事件不得破坏移动端或桌面端会话状态。
4. 服务端必须用结构化兼容性错误拒绝不支持的协议版本和编码格式。
5. 数据库迁移必须是增量的，并且在应用层可回滚；删除语音会话记录不得删除 channel message 或 run。
6. 发布必须支持服务端开关和客户端可见的能力标记，再逐步开放给普通用户。

## 非功能需求

### 延迟目标

第一阶段 Provider 验证需要测量以下目标；在测量完成前，这些目标不作为最终发布门槛：

- 麦克风帧到服务端 VAD 观察：p95 小于 150 ms；
- 用户停止说话到首个部分转写：p95 小于 800 ms；
- 用户停止说话到首条 `SendToUser` 回复持久化：对于不调用工具的回复，p95 小于 2,500 ms；
- `SendToUser` 回复送达语音会话到首段可播放 TTS 音频：p95 小于 1,500 ms；
- 用户停止说话到首段可播放回复音频：对于不调用工具的回复，测量并记录 p95，用于阶段 0 决定是否流式解析工具参数；
- 接受抢话到客户端停止播放：p95 小于 250 ms；
- 健康连接的稳定音频队列：低于 1,000 ms；
- 外放（不戴耳机）时 Bot 连续朗读 30 秒：误触发抢话次数为 0。

### 可靠性

- 活动会话必须使用有界内存和有界队列。
- Provider 失败不能泄漏解码进程，也不能让 run lease 长时间处于活动状态。
- 重复控制帧或重连请求必须可以安全地再次处理。
- 持久化的最终转写必须能通过普通 channel 历史和消息投递查询恢复。

### 隐私

- 默认情况下，原始音频只存在于内存中。
- Provider 凭据只保存在服务端。
- 部分转写只属于当前会话，不加入全局事件历史。
- 诊断日志只记录 ID、大小、时长、延迟和错误分类。

## 成功定义

- 一个 macOS 客户端通过真实服务端和已配置的流式 Provider，连续完成至少十个说话/听取回合。
- iOS 和 Android 的采集/播放适配器使用相同的服务端协议完成验证。
- 用户可以中断 Bot 回复并开始新的回合，不会产生重复消息，也不会继续播放过时音频。
- 咳嗽或附和声不会取消正在进行的 Agent 回复。
- 每个平台在外放条件下都能正常对话，Bot 的声音不会触发抢话。
- 朗读的内容与聊天历史中的 Bot 回复一致。
- 最终用户内容和助手内容都持久化在现有 conversation 中。
- 现有语音笔记的浏览器、iOS、Android 和服务端测试继续通过。
- 协议、服务端、Worker、桌面端、iOS、Android、生命周期、安全和部署检查均提供与风险相称的证据。
