## 9. 统一验证阶段增量：Explore 明确失败后的新规划重试（task-42）

独立复核发现：服务端已持久化的 `502 planning_generation_failed` 使用原 request ID 会一直返回失败；原 Desktop 对所有错误都保留相同 ID，使同想法、同 Bot 的再次点击无法重新推理。

本增量把真实 Propose 请求的 ID 生命周期提取到生产调用的 `proposeExploreIdea`，只有服务端明确返回 **HTTP 502 且 code 为 `planning_generation_failed`** 才清除该请求意图。当前点击仍返回明确错误，不自动重试；用户再次点击才生成新 ID。想法、Bot 和表单不变，仍进入原规划草稿确认流程，没有自动审批。断网、未知 gateway 错误、错误状态不匹配、错误/成功响应无法解析时保留原 body/ID，以便已成功但响应丢失的请求重放。

实际使用 `createJsonTransport` 和生产 `createExploreApi` 的注入 fetch 回归，不启动服务器：

```bash
bun test apps/desktop/test/outcome-explore-retry.test.ts
bun scripts/check/i18n-catalog.ts
git diff --check
```

保留原错误重试语义时，先实际复现 **2 PASS / 1 FAIL / 21 assertions**：第二次明确失败后的重试再次得到同一 502。应用窄修后为 **3 PASS / 0 FAIL / 27 assertions**：同想法/Bot 明确失败后第二次使用新 ID；成功后响应丢失时 body/ID 完全相同且只推理一次；未知/不匹配/非法响应保留原意图。新增翻译仍使用静态 catalog，检查通过（2252 条 catalog，1953 条使用文案）。两个受影响源码根和测试根及原有 ambient 声明的 TypeScript 聚焦程序最终为 **0 diagnostics**；首次测试 fixture 状态字面量的类型诊断已用真实 `ExploreProposal` 类型修正后重跑。
