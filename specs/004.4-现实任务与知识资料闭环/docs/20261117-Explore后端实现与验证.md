## 正式接口与状态

导出 `@outcomego/contracts/explore`，响应均为真实业务 DTO，不加通用 result 包裹：

- `POST /api/v0/explore`：保存 title、可选 note/Bot/来源 Outcome/来源引用/budget，允许 draft 或 exploring。没有 Bot/目标/验收/边界也可保存。
- `GET /api/v0/explore`：按 status、updatedAt/id cursor 和 limit 分页。
- `GET /api/v0/explore/:id`：负责人授权的只读详情增量，用于刷新/重新打开，和列表同一 View/认证。
- `POST /api/v0/explore/:id/propose`：选择真实 Bot，返回 `{idea,plan:PlanningDraftView}`。
- `POST /api/v0/explore/:id/discard`：保留 note、资料引用、budget、已有草案/历史和 discardedAt。

正式状态为 `draft → exploring → proposed_for_delivery → converted/discarded`。已转换的 idea 只能读，不能再提议或丢弃；丢弃状态禁止转换。相同请求重放原响应，重用 key 改内容返回 `idempotency_conflict`；主体仍由已有认证上下文生成，客户端不能提交 converted/approved/actor 或伪造结果 Outcome。

## 草案与交付分离

`ExploreIdea.planningDraftId` 指向真正的 `OutcomePlanningDraft`；`proposedOutcomeId` 只指向真正转换得到的 Outcome。`Outcome.sourceExploreId` 为兼容旧数据的可选来源关联，绝不把草案 UUID 填进 Outcome FK。

复用 `OutcomePlanningService.prepare(input,signal)` 在事务外执行原规划模型规则；`persistInTransaction(tx,input,prepared)` 不调用模型、不自行开事务，由 Explore 最终事务同时保存草案和来源关联。初始短事务只加载/校验状态及标记 exploring，不持锁等待推理。模型完成后重新加 Explore 锁：已被丢弃/转换则不创建草案；并发已有有效同 Bot 草案则复用；不同 Bot 则冲突，不能遗留第二个未关联草案。

非 JSON 仍只重试一次，传输失败保持原有不额外重试行为。生成失败时保存可读取的 failed PlanningDraft 及 idea 链接，返回带 planId 的可重试错误；同 key 不再次调用模型，新 key 可重新提议。有效草案的再次提议复用原 planId，不丢失已选择候选项。

用户随后使用既有 Outcome 创建 API 提交真实 planId 和三维选择。服务端从草案反查 Explore，在同一事务创建独立 Outcome/revision、消费草案，并把 Explore 改为 converted、写真实 proposedOutcomeId。转换没有批准、Run、WorkItem 或来源 Contract 写入；失败回滚全部来源/草案/Outcome/revision 事实。正常批准和执行仍须用户分别操作。
