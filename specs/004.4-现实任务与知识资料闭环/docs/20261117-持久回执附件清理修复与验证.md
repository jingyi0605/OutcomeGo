# 2026-11-17 持久回执附件清理修复与验证

## 问题与修复

独立审查 Task32 在冻结代码 `b58286ab3` 发现真实数据丢失路径：`AppService.pruneUnreferencedAssets` 只收集消息 metadata 内的 `assetId`，而人工回执的照片、日志等材料保存在 `OutcomeHumanReceipt.assetRefs` / Evidence 中。启动后的正常清理和每六小时清理会把超过 24 小时、没有消息引用的材料当成孤儿删除。即使回执已经提交、接受或作为历史保留，后续验收读取也会得到 `asset_not_found`。

Task40 修复提交为 `aea3ae0daf319661071f59231e31cee01a8c3de6`，仅修改真实 AppService 的候选引用 SQL 并增加真实数据库 / AssetStore 回归。仍在 PostgreSQL 中提取候选 ID，不把完整历史 JSON 拉到进程内；消息引用和 AssetStore 原有 24 小时孤儿宽限期保持。

| 持久事实 | 实际支持的引用 | 清理策略 |
| --- | --- | --- |
| ChannelMessage.metadata | 既有递归 `assetId` | 保持既有行为 |
| OutcomeHumanReceipt.assetRefs | `asset:<64 位小写十六进制>` | 所有状态和历史序号保留 |
| OutcomeEvidence.sourceRef | asset / knowledge / file 类型下的规范 asset 或附件链接 | 保留独立 Evidence |
| OutcomeHumanActionCard.references | KnowledgeReference.sourceRef 中的规范附件链接 | 保留卡片知识快照 |
| OutcomeHumanReceipt.payload.references | 实际解析后保存的 KnowledgeReference.sourceRef | 保留已提交回执的知识快照 |

规范附件链接是 `file:<message UUID>:<index>:asset:<hash>`。任意包含 hash 的文本、错误前缀、错误 ID、非字符串值不会成为保留依据。回归中特意提供 `invalid:asset:<hash>` 并验证对应旧孤儿仍被删除。

同时审查了其他真实写入端：`settleOutcomeWorkItem` 生成的 `OutcomeOutput.contentRef` 是 `outcomes/...` 工作区文件路径，ContractRevision 没有附件引用槽位。本修复没有为这些位置虚构 AssetStore blob 引用。

## 并发发布复核与补充修复

独立审查随后复现另一条真实路径：清理取得“尚无引用”的旧 asset 快照后，真实 `HumanReceiptService.submit` 校验并提交回执 / Evidence；清理继续使用旧集合，仍会删掉刚被持久引用的 blob。第一次 SQL 并集修复不足以关闭这个并发门。

新增确定性回归在真实快照返回后暂停清理，真实提交回执成功后才恢复删除。`aea3ae0da` 上结果为 **1 PASS / 1 FAIL / 14 assertions**，错误仍为 `asset_not_found`。

补充修复使用已有 `human-receipt-asset:asset:<hash>` advisory 事务锁：

- `AssetStore.prune` 增加可选删除 guard，既有调用方和默认 24 小时宽限期兼容。实际删除闭包在 guard 内执行，等待后再次核对文件 mtime。
- AppService 对每个真正准备删除的旧候选取得同一 asset 锁，在同一事务内使用共享 SQL 重新检查当前消息 / 持久引用，直到 blob 和 metadata unlink 完成才释放锁。
- 回执将直接 asset 与已解析知识快照的 asset ID 合并、去重、排序后加锁，并在锁内校验真实 metadata。卡片快照发布及 Review 中的真实 asset/file Evidence 发布也使用相同锁；生产 HumanWork 工厂注入已有真实 AssetStore。工作区路径和普通文本引用不增加 asset 规则。
- 上述 Outcome 发布方先沿既有规则取得 Outcome 锁、再按 hash 排序取得 asset 锁；清理只取得 asset 锁并执行普通引用 SELECT，不反向取得 Outcome / WorkItem 锁。

第二个真实交错测试暂停在清理已持有 guard、即将 unlink 的位置，再启动真实回执提交；通过 `pg_locks` 确认回执等待确切的 asset 锁。恢复删除后，提交得到明确 `receipt_asset_not_found` 并回滚，没有产生引用已删除材料的部分回执。
