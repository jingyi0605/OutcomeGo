## 任务与失败行为

### 2.1 工具与两种创建来源

- Computer 仅在 Outcome 子线程注册 `RequestHumanAction`；成功返回 `waiting_for_human` 后结束当前回合，普通 turn/automation/event 的既有工具列表保持不变。
- 来源 A 从持久化 Run 验证 `origin=outcome`、Bot、WorkItem、执行状态；在同一 Outcome 事务内按 `human-action-request:<runId>:<input hash>` 回放或创建卡片，再通过共享状态转换进入 `waiting_human`。
- 来源 B 验证已经写入的 Decision 选择快照、`resolvedBy`、原请求 Agent 与 revision；按 Decision 幂等创建。原 Agent 保持 `waiting_decision`，直到人工验收后由共享 enqueue 继续。
- 不从 Contract 自动推断人工工作，不创建替代 Run 状态机。
- 生产知识消费者将所选 reference ID 解析为真实 Bot 文件、消息或关联文本附件；读取实际正文并保存 version/digest/有界摘要。超时、无权限、失效、不可读均沿用结构化错误。
- 未注册依赖返回明确的 503；历史读取不改变动作卡、Receipt 或状态。

### 3.1 回执

- `POST /api/v0/work-items/:id/receipts` 接受 `clientRequestId`、`expectedContractRevision`、`text`、`comment`、`assetRefs`、`sourceRefs`、`observations`，严格拒绝 actor 和最终状态字段；actor 从持久化 session 派生。
- 同一 key/内容/actor 在可变 revision、状态校验前返回已存响应；变更内容返回 409。请求持有 Outcome 事务锁，跨 WorkItem asset 引用使用排序后的事务锁验证冲突。
- 资产必须实际存在；知识引用必须实际读取；普通 external URL 只保存为未验证来源，不能满足 sourceReference Evidence。
- 只为存在的对应材料生成带真实 `workItemId`、`criterionId`、revision 和 `human_confirmed` 的 Evidence。缺材料写入缺口，不能自动 PASS。
- 保留全部回执历史；在同一事务中写入回执、Evidence、事件、幂等响应，并通过共享转换进入 `review_pending`。

### 3.2 唯一验收与续跑

- 唯一验收入口仍为 `POST /api/v0/outcomes/:id/reviews`。原通用证据、waiver、必需/可选条款及独立 Decision/HumanAction 门槛保留。
- 人工分支调用 `HumanReceiptService.reviewInTransaction`，只使用最新回执的材料来源与回执之后的新 Review。旧 FAIL/PASS 不能自动作用于重新提交的回执。
- FAIL 保存审阅说明并驳回；缺材料或未验证结果保持待验收。PASS 必须引用该回执、该 WorkItem、该条款的实际 Evidence，不能以普通确认或不相关材料替代。
- 接受时再次检查所用 asset 和知识 version/digest；随后在原 Review 事务中更新人工项、回执、卡片时间，再调用 `enqueueOutcomeTurn(reason=human_action_accepted)`，继续原请求 Agent 的同一子线程。
- enqueue 失败会回滚整个验收；取消的请求 Agent 不会复活。续跑有稳定幂等键，不向主对话发送可见消息。

### pending successor 的冻结策略

共享 `isOutcomeDecisionRevisionActive(tx,outcomeId,revisionId,requesterAgentId)` 为唯一执行快照判定：

1. 当前 revision 正常处理；存在 N+1 draft/pending 时，旧 N 必须仍为最新有效批准快照，并具有原 Agent 的真实 `startedAt` 和匹配 Outcome Run 的真实启动事实。
2. 创建卡片使用来源 Run/Decision 对应 Agent 的不可变 revision，不能把 N 的请求绑定到 N+1。
3. start、receipt 以及 `/reviews` 的窄人工选择均使用该请求 Agent 上下文。客户端使用动作卡的 revision，不能直接使用 Outcome 的 pending 指针。
4. N+1 真正批准后，所有新旧 N 控制请求返回 revision conflict 409；已存的相同请求仍优先回放，历史事实仍可读取。
5. N 的人工 Review 可以在 pending 期间接受相应动作卡并续跑原 Agent，但绝不能将当前 N+1 的 Outcome 全局标为 accepted。

知识读取对已经批准过且仍属于同一 Outcome/Bot 的历史 revision 保留只读能力；默认 provider 的严格当前 revision 行为不变。控制操作另受上述共享判定约束。
