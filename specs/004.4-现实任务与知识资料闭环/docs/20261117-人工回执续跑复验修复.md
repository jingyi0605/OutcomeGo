# 人工回执同线程续跑复验修复

日期：2026-11-17。原生任务：`task-39`。关联：[第二波代码交付](20261117-第二波人工动作回执交付.md)、[任务清单](../tasks.md)。

## 实际问题与原因

统一验收冻结版本 `b58286ab3` 在 Agent 来源和 Decision 来源的实际数据库测试中均失败：人工 WorkItem 与 Receipt 已 accepted，但 `runs` 只有 1 条，原断言要求 2 条。这是本线测试 fixture 的真实缺陷，不属于第 0 波失败基线。

`humanActionScenario` 复用的 Bot 没有显式状态，schema 默认是 `provisioning`。真实 `enqueueOutcomeTurn` 要求 Outcome 的目标 Bot 为 `active`；目标尚未可运行时，保留 `outcome-turn:<requesterId>` 的 processing 幂等记录，并返回 `queued_for_capacity`。因此，这个 fixture 不满足“接受后立即创建新 Run”的前提。

没有更改生产服务、共享 enqueue、状态机或验收断言来绕过问题。

## 修复与新增证据

- 仅在会执行真实 mailbox enqueue 的 `humanActionScenario` 中，将持久化 Bot 明确设为 `active`，并返回更新后的 Bot；第一波普通动作卡 fixture 的默认行为不变。
- 两来源接受测试保留原 `runs.length === 2`、同 WorkItem、同 rootRunId 和普通主对话零可见消息断言。
- 增加活动 Bot 前提、续跑幂等记录 completed、对应 Run ID 和唯一 InboxEvent 的断言，证明重复 Review 不会重复入队。
- 新增专门的不可运行 Bot 测试：真实 Bot 变回 provisioning 后接受人工回执，验证 Receipt 已 accepted 且续跑 processing 意图存在、暂时没有第二个 Run；激活后执行两次共享 drain，再回放 Review，最终仍恰好 2 个 Run，原 rootRunId 不变，持久化意图 completed。
