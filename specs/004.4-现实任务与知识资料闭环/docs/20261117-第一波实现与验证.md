## 实现边界

资料读取采用负责人确认的既有共享挂载，未新增 computer 端点：

1. `KnowledgeScopeService` 每次解析 Outcome、当前 revision 与执行 Bot；缺范围、跨范围和旧 revision 返回结构化错误。
2. `createProjectFileKnowledgeProvider(prisma, scope, agentData, assets)` 注入已有 `AgentDataStore.root/botDirectory` 和 `AssetStore.metadata/contentPath`。
3. AgentFileState 只用作受管文件元数据目录，按路径检索。正文通过当前 Bot 目录下真实普通文件读取，限制 1 MB、检查 UTF-8/二进制、读取前后文件变化及实际 SHA-256，防止数据库 digest 落后时误用旧引用。
4. SearchDocument 的 file/message 是消息和附件投影；在候选限制前按当前 Bot 的有效 channel membership 筛选，不依赖可能为空的 senderBotId。读取时重新验证关联；附件只能来自当前允许消息的 attachments，不能按任意 asset hash 读取。
5. 无挂载、缺失、无法提取文本的文件/附件返回 `unreadable_source`。资料改变返回 `knowledge_source_stale`。Provider 不写 Contract、WorkItem、Evidence，不做全文缓存或文件复制。
6. Fixture provider 只通过显式测试依赖创建，没有生产默认注册。

`HumanWorkService.createCard(tx, input, actor)` 是第一波内部构造函数，在调用方事务中创建共享 human WorkItem、动作卡快照、关联条款及目录内事件，并通过 `transitionWorkItem` 进入 ready。人工任务不创建 Run，也不会把调用方 Agent 自动结算。

API 注册在既有认证中间件之后，公开地址为：

```text
GET  /api/v0/outcomes/:id/work-items?status=ready&executorType=human
GET  /api/v0/work-items/:id
POST /api/v0/work-items/:id/start
POST /api/v0/work-items/:id/pause
```

`main.ts` 按既有规则将 `/api/v0` 规范化为 `/api` 后分发。list 包含统一 Agent/human view、evidenceCount 和 nextAction；detail 返回持久化动作卡。start 同时承担 paused/rejected 的继续入口，复用已冻结的 human 状态机；保留首次 startedAt/startedBy。pause 只接受当前 step、摘要、已读引用和原因，不接收任意表单对象。服务端从 session 或本地 owner 上下文生成 actor。revision 条件、同 key 同内容重放、同 key 不同内容冲突及并发互斥在同一事务实现。

## 本次观察的基线缺陷

本线第一次在 fresh disposable DB 上调用真实 search 时，两个消息/附件引用未返回。直接观察：

```bash
docker exec outcomego-l4-pg psql -U outcomego -d outcomego \
  -c 'SELECT column_name,is_generated FROM information_schema.columns WHERE table_name=$$outcomego_search_document$$'
```

输出包含 `searchVector | NEVER`。该库由当前 `deploy-schema.ts` 建立；Prisma 已创建 searchVector 列，raw schema 的 `CREATE TABLE IF NOT EXISTS` 不会把现有列转换为 generated 列。新插入消息的向量因此是 NULL。此结论仅针对本次实际 fresh 部署，未检查或宣称所有既有环境都有该问题。

负责人批准本 provider 内的最小兼容：保留非 NULL 向量的原 `@@ to_tsquery` 条件；仅当向量为空时用参数化 `to_tsvector(title/subtitle/content)` 计算。Bot/channel 限定与 limit 不变。测试先证明真实 NULL 向量仍可查到消息/关联附件，再填入非空向量证明原分支继续返回相同引用。没有修改 SearchService、raw schema 或其他线的数据库文件。

第 0 波记录的全量数据库失败仍为发布/整合门槛阻塞，详见父规格 [失败基线](../../004-OutcomeGo整体项目/docs/test-failure-baseline.md)。本次只执行已列的定向测试，不能把 387 个 PASS 宣称为全量 CI 已恢复绿色。

## 独立复核修复记录

2026-11-17，复核任务 14 指出两个 P2，均在本线工作树修复，提交 `6bd25528a`。schema、contracts、路由注册及第二波边界均无变化。

1. 来源筛选原先在 SQL 候选 limit 后进行。实际复现：同一 Bot 的较早匹配 message 与较新匹配 file，message-only 且 limit=1 得到空结果。现在共享 provider 先合并 bound/query allowedSources 的交集，ProjectFile store 在 SQL limit 前按有效 file/message 类型过滤，message-only 不再查询 AgentFileState。空交集直接返回空结果；Bot/channel 与附件关联检查仍在原路径验证。
