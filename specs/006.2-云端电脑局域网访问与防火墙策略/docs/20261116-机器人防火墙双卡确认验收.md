# 机器人防火墙双卡确认验收

日期：2026-11-16

对应需求：`../requirements.md` 需求 6。对应设计：`../design.md` §2.3.6、§3.2.3、§6.7。对应任务：`../tasks.md` 2.5。

## 实现边界

- `UpdateComputerNetworkPolicy` 在顶层用户机器人的运行时目录中可发现；子机器人和自动任务不展示该工具，服务端同时拒绝这些调用。
- 首次调用读取当前策略并将新增目的地合并进去，保存合并后的候选策略，发送核验卡片；核验通过后再次调用发送独立授权卡片；最终批准后才能调用应用保存的合并策略。
- 两张卡片均发送到该机器人的所有者私聊。普通 widget 的文本、手写 approvalId 或其他机器人的请求不构成授权。
- 请求通过 `sourceRunId`、`sourceCallId` 唯一约束实现幂等。卡片和请求的绑定在同一数据库事务内完成，避免先显示卡片再绑定请求的窗口。
- 请求有效期为创建后的 15 分钟。拒绝、关闭、过期、已消费以及策略 revision 冲突均阻止应用。应用时返回保存策略和实际 Computer 状态，保存成功不等于内核已应用。
- 合并后的规则总数不得超过 128 条；旧版本遗留的会删除或改写既有规则的审批记录会在应用前被拒绝，不会覆盖当前策略。
- 当前没有独立的机器人管理员角色；本次权限范围是顶层用户机器人提出请求、所有者通过卡片逐次授权。未新增可由机器人自行赋予的管理员字段。

## 自动验证

- 服务端专用操作测试：核验、授权、应用的阶段顺序；初次调用重放；子机器人和 routine 拒绝；拒绝、过期、已消费和后续 payload 改写拒绝。
- 策略服务测试：输入校验、revision 冲突、一次性消费。
- Computer 运行时测试：工具可发现、子机器人和自动任务目录不暴露该工具、显示卡片后结束当前轮并等待用户。
- 真实临时 PostgreSQL 数据库：部署完整 schema；两项 widget 集成测试通过，覆盖核验、最终批准、关闭和过期持久化，以及 `sendVisible` 事务内绑定。
- 同一临时数据库额外验证：未核验请求拒绝；跨机器人应用拒绝；两个并发应用调用只有一个成功，revision 只增加一次；消费后重放拒绝。
- 测试数据库在验证后删除；未把测试卡片写入用户聊天。
- server、computer、messaging、db 和 desktop 类型检查通过；契约测试和 Python 网络规则测试通过。

## 验收限制

本次未在真实用户聊天中代替用户点击核验或最终授权卡片，也未替用户应用新的 LAN 策略。真实用户聊天的首次操作仍需所有者依次完成两张卡片。
