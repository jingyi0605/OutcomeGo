# 云端电脑出网故障复盘与回归防护

日期：2026-11-16

关联：`requirements.md` 需求 5；`design.md` §2.3.5、§6.5、§6.6；`tasks.md` 阶段 6。

## 现象

调试环境的 Computer 容器出现两类故障，先后表现为：

1. 控制面不稳定：`debug.sh check` 在“策略已应用”和“策略超时”之间来回变化；Computer 内 Node 到 Mac 上服务端的套接字停在 `SYN-SENT`，旧连接停在 `FIN-WAIT-1`，Mac 侧有对应的 `SYN_RCVD` 和 `LAST_ACK`；服务端日志每 10–30 秒出现 `transport_closed`、`route_fenced`、`route_changed`。
2. 局域网正常、互联网不通：`curl` 全部返回 000，`apt` 报 `No route to host`，容器内表 18791 只有 `unreachable default`。

## 根因

三个问题叠加，互不相同。

### 1. 宿主机无法解析容器，回包排队约 20 秒

- 容器的全部出站流量由 `ip rule pref 110` 送入表 18791，该表默认只有 `unreachable default`。
- 容器没有到 Docker 网关 `172.19.0.1` 的、不经过该表的路由，反向路径校验失败，宿主机发给容器的 ARP 请求被丢弃。
- 宿主机的邻居条目停在 `INCOMPLETE`，Mac 返回的 SYN-ACK 排在邻居队列里，约 20 秒后才被放出。所有由容器发起的连接因此停顿，表现为上面的套接字状态。
- 抓包证据：SYN-ACK 在宿主机 `eth0` 上 1 毫秒内就出现，但很久之后才出现在容器网桥上；网桥上的 ARP 请求在约 23 秒内没有得到应答。
- 单次 `curl` 有时成功，是因为容器发起的新连接会刷新邻居条目。

### 2. 容器 `rp_filter` 在创建后被改回 2，公共回包被丢弃

- 启动脚本把所有接口的 `rp_filter` 写成 0，但新建容器约 15 秒后，`eth0` 和 `default` 又变回 2。`docker restart` 不会出现这种情况，所以只用 `restart` 反复测试时无法复现。重置的来源没有查明。
- `rp_filter=2` 时，公共地址回包的反向校验用未标记的查找，落入只有 `unreachable default` 的表 18791，被丢弃。局域网因为有 `pref 98` 指向 `main` 的规则而不受影响。
- 抓包证据：容器带标记的 SYN 持续重传，`1.1.1.1` 的 SYN-ACK 已到达网桥，容器仍不完成握手。

### 3. 出口复验子进程拒绝 `ipv4`/`ipv6`

- 探测循环先经托管出口探测，通过后装上 TUN 默认路由，再启动不带传输标记的子进程用普通套接字复验。
- 子进程入口的白名单只允许 `egress` 和 `quality`，而复验发送的是 `ipv4`/`ipv6`。子进程立即退出，复验判为失败，默认路由随即被撤销，没有任何日志。
- 手动装上路由后，普通流量立即正常（`1.1.1.1` 返回 301，`deb.debian.org` 返回 200），约 12 秒后被 worker 撤销。

## 修复

| 问题 | 修复 | 位置 |
| --- | --- | --- |
| 宿主机无法解析容器 | 为容器直连网段安装 `ip rule pref 94 … lookup main` | `docker/outcomego-computer-network.py` 的 `connected_prefixes()` |
| 公共回包被丢弃 | `rpf` 链给 eth0 入站包打传输标记；所有接口写 `src_valid_mark=1`，反向校验走 `main` 表，不再依赖 `rp_filter` | `nft_ruleset()`、`disable_reverse_path_filter()` |
| 复验子进程拒绝探测 | 探测类型收成 `computerProbeKinds`，发送方和入口共用 | `apps/computer/src/computer-network-probe.ts`、`browser-network-worker.ts` |
| 失败不可见 | 复验失败输出固定原因码；`GET /v1/browser-network` 返回 `connectivity` | `browser-network.ts`、`browser-network-worker.ts` |
| 检查不覆盖真实流量 | `debug.sh check` 增加出口、公网、局域网、宿主机邻居检查；新增 `debug.sh smoke` | `scripts/dev/debug.sh` |

另外回滚了一个未证实有效的实验：`docker/outcomego-network-mark.c` 对服务端控制端点取消标记，以及 `browser-network.ts` 中对应的环境变量。它不是根因，保留只会增加 `connect()` 拦截的风险。

## 防回归措施

| 类别 | 措施 | 对应需求 |
| --- | --- | --- |
| 不依赖会被改回的内核状态 | `src_valid_mark` 加 `rpf` 链；`pref 94` 规则 | 需求 5.1、5.2 |
| 失败可见 | 原因码日志；`connectivity` 状态 | 需求 5.3、5.4 |
| 契约共用 | `computerProbeKinds` 单一来源和测试 | 需求 5.5 |
| 真实流量验证 | `debug.sh check` | 需求 5.6 |
| 在新建容器上验证 | `debug.sh smoke`（强制重建后等待 45 秒再检查） | 需求 5.7 |

`connectivity` 状态是缓存值，不能单独作为出网证据。验证时删除 TUN 默认路由，`connectivity` 仍显示 `working`，而 `check` 的公网检查报告失败。因此“真实流量检查”不能被状态字段替代。

## 未覆盖和遗留

- 复验失败原因码的日志路径只有类型检查和代码审查，没有在真实容器里触发过。触发它需要让复验子进程真实失败。
- `rp_filter` 被改回 2 的来源没有查明。当前功能不依赖它，但如果其他内核参数也被重置，需要重新排查。
- 直连网段只在容器启动时读取一次。运行中用 `docker network connect` 新增网络时，新网段不会自动得到 `pref 94` 规则。
- 复验白名单的修复没有针对 `browser-network-worker.ts` 的顶层 `await` 做端到端测试，只测了共用的解析函数。
- 修复目前只在调试环境验证。生产需要把这些改动提交并随正常发布构建，不需要修改生产容器环境。
