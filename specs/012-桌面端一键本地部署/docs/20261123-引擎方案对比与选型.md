# 引擎方案对比与选型（2026-11-23）

本文支撑 `design.md` §3.3.4 与 §3.3.6。凡标注“估算”或“未核实”的内容，都不是实测结论。

## 1. 前提

- macOS 与 Windows 上的 Linux 容器都需要 Linux 内核，所以底层一定是虚拟机；不存在“不需要虚拟机”的方案。Windows 上最轻的形态是 WSL2。
- “还要装 Hyper-V”不是必须的：微软文档说明 `wsl --install` 会启用 WSL 运行所需的功能；Docker 文档的 WSL2 后端要求中没有 Hyper-V 功能。真正的门槛是 WSL 功能启用（通常需要一次管理员授权和重启）以及 BIOS 虚拟化。
- 本项目的 `computer` 容器要求 rootful、完整内核、cgroup v2 与 Docker 风格 Compose 语义，见《现状核查记录》§4。

## 2. 候选对比

| 方案 | macOS | Windows | 底层 | 对本项目的判断 |
| --- | --- | --- | --- | --- |
| Docker Desktop | 是 | 是 | Windows 上 WSL2 或 Hyper-V | 现状。可用，但体积大、有 GUI、有商业授权限制，用户需自行安装 |
| Podman / Podman Desktop | 是 | 是 | Windows 上是 WSL2（官网明确） | 需 rootful machine；Compose 依赖外部 provider；`systempaths=unconfined` 等选项可能不兼容（未验证） |
| Rancher Desktop | 是 | 是 | Windows 上需要 WSL | 自带 Moby 与 Compose，文档列出 Windows 11 Home；仍是完整桌面应用 |
| 微软 `wslc`（WSL 容器） | 否 | 是 | WSL2 | 暂不可用：单一来源称 2026-09-29 GA，尚不支持 Compose，特权、cgroup、tun 无资料 |
| Apple `container` | 是 | 否 | 每个容器一个轻量虚拟机 | 不适合：需 macOS 26 与 Apple Silicon；与 `pid: service:` 共享命名空间的模型冲突 |
| OrbStack / Colima / Lima | 是 | 否（Lima 的 Windows 支持未核实） | 轻量虚拟机 | macOS 上适合作为 external 引擎，或托管的基础 |
| 自管 Hyper-V 虚拟机 | 否 | 是 | Hyper-V | 需要 Pro 以上版本和管理员权限，门槛不降反升，不采用 |

## 3. 选型结论

1. **引擎提供者分两类。** `external`：用户已有的 Docker 兼容引擎，Linux 永远使用它；`managed`：由 OutcomeGo 托管。
2. **Windows 托管引擎：** 私有 WSL2 发行版 `outcomego-engine`，内置固定版本的 dockerd 与 Compose；不使用 Docker Desktop，不修改用户的 `.wslconfig` 与其他发行版。
3. **macOS 托管引擎：** 基于 Apple Virtualization 的 Linux 虚拟机，候选实现为 Lima（vz 后端）；备选为 vfkit 加自管 dockerd。最终选择取决于 Spike C。
4. **不采用：** Hyper-V 后端、`wslc`（暂缓，待其支持 Compose 后重评）、Apple `container`。
5. **分期：** 先在 external 引擎上交付“一键部署”功能面（M1），再分别交付两个托管引擎（M2、M3）。

## 4. 内存估算（估算，待 Spike F 实测）

**实测基线：** 空闲 computer 容器约 245 MiB（`docker stats`），见《现状核查记录》§6。

**每个桌面的估算：** 来自一般经验，没有在本项目里测过。

| 组成 | 估算 |
| --- | --- |
| 监督进程基线（实测） | 约 0.25 GiB |
| 桌面外壳（Xvfb、dbus、xfwm4、xfdesktop、xfce4-panel、x11vnc、查看器） | 0.25–0.45 GiB |
| Chromium，1–5 个普通标签 | 0.6–1.5 GiB |
| LibreOffice 打开一个普通文档 | 0.25–0.5 GiB |
| 合计，单机器人 | 约 1.4–2.7 GiB |

**配置约束（均已核实）：**

- `computer` 容器的整体内存上限取 `min(配置值, 引擎虚拟机内存的 75%)`（`docker/outcomego-memory-init.c`）。配置值默认 12 GiB（`deploy/compose.yaml:100`）。
- 交换空间关闭（`memswap_limit` 等于 `mem_limit`，`memory.swap.max` 为 0），超限直接 OOM 杀进程；触到整体上限可能杀掉共享运行时并重启容器（`docs/configuration/server.md`）。
- 每桌面上限默认 10 GiB（`OUTCOMEGO_DESKTOP_MEMORY_LIMIT`），整体上限更小时没有意义。

**推导（初始值，需实测校准）：**

- 整体上限 3 GiB 需要引擎虚拟机至少 4 GiB；4 GiB 需要至少约 5.4 GiB。
- postgres、server、worker 与内核也在同一虚拟机内，占用未测。
- 因此托管引擎虚拟机内存：最低 4 GiB（仅轻度、单机器人），推荐 6 GiB 以上，多机器人建议 8 GiB 以上。

**公式（写入 `design.md` §3.3.6）：**

- `computerLimit = min(12 GiB, floor(客户机内存 × 0.75))`
- `desktopLimit = max(1 GiB, computerLimit − 1 GiB)`
