## 3. 已核实：更新代理与内置 CLI 的冲突

- `updateAgentCommand` 用 `process.argv[0]` 和 `process.argv[1]` 拼启动命令（`apps/cli/src/update-agent.ts:161-173`）。在桌面端内，它们是 Electron 可执行文件和带版本号的 `app.asar.unpacked` 路径，桌面自更新后会失效，也没有 `ELECTRON_RUN_AS_NODE`。
- 代理服务只支持 launchd 与 systemd，其余平台返回 `null`（`apps/cli/src/update-agent-service.ts:36-66`）。Windows 上代理是分离进程，重启后需要用户执行 `outcomego start`（`update-agent.ts:178-202`）。
- 现有代码已经意识到“常驻的 Windows 进程不能占用将被替换的可执行文件”，并对 Bun 单文件二进制做了复制（`update-agent.ts:204-215`）。如果代理直接以桌面端的 Electron 可执行文件常驻，会占用应用自身的 exe，可能阻塞桌面自更新。这一点是据代码注释推断，尚未在 Windows 上复现，见 Spike E（任务 1.7）。

## 4. 已核实：compose 对引擎的要求

`deploy/compose.yaml` 的 `computer` 服务使用 `cgroup: private`（第 97 行）、`cap_add: ["ALL"]`（第 123 行）、`seccomp:unconfined`（第 125 行）、`systempaths=unconfined`（第 128 行）、`/dev/net/tun`（第 130 行）。`computer-memory-init` 通过 `pid: service:computer` 加入其命名空间，持有 `SYS_ADMIN`、`SYS_CHROOT`、`SYS_PTRACE`（第 160 行）。`docker/computer-entrypoint.sh` 以可写方式重新挂载 `/sys` 和 `/sys/fs/cgroup`。

因此引擎必须是 rootful、完整 Linux 内核、cgroup v2、具备 Docker 风格的 Compose 语义。`deploy/compose.yaml` 中所有卷均为命名卷，没有宿主机路径绑定，这是“在引擎内执行 compose”方案可行的前提。

## 7. 未验证（不得当作事实）

1. computer 容器能否在 WSL2 内核、Lima 客户机内核上启动（cgroup v2 可写、nftables、tun、`systempaths=unconfined`）。
2. `wsl.exe -d <发行版> --cd <路径> --exec docker compose …` 的 stdin 透传、`/mnt/c` 读取 `.env` 的行为与速度。
3. Lima 的 vz 后端所需 entitlement、辅助二进制的签名与公证路径，以及客户机是否默认挂载用户主目录。
4. Compose 2.20（CLI 当前最低版本）是否支持 `pull --progress=json`；不支持时只能做到“按镜像”粒度的进度。
5. WSL2 虚拟机默认内存是否为宿主机的一半（凭记忆，未核实）。
6. GitHub 托管的 Windows 与 macOS runner 是否支持 WSL2 与 Apple Virtualization 嵌套虚拟化。
7. Windows Home 版对 WSL2 的支持情况；抓取到的 Docker 文档摘要与 Rancher Desktop 文档对此说法不一致。
8. Lima、Moby 等组件的许可证与本项目 `GPL-3.0-only` 的兼容性（需法务确认）。
9. 镜像总体积与首次部署耗时。
10. 微软 `wslc`（WSL 内置容器命令）仅有一篇博客作为来源，且尚不支持 Compose，暂不纳入方案。
11. 桌面端关闭窗口或退出后，WSL 托管引擎能否继续运行（实例空闲回收策略）。第三方资料称实例空闲超时默认约 15 秒，微软官方文档未核实。
12. Intel Mac 在 macOS 13.5 上能否启动所选的客户机内核。某第三方资料称 Linux 6.12 及以上需要 macOS 15.5，Lima 官方文档没有此说法。
13. Windows 关机或注销时，关窗隐藏逻辑是否会延迟关机，需要在真机上实测。

## 9. 已核实：官方文档中的系统与事件要求（2026-11-23）
