# 第三方组件许可证评估与建议（2026-11-23）

本文回答 `design.md` §8.2 Q11：Lima、Moby 等组件与本项目 `GPL-3.0-only` 的许可证是否兼容，以及发布时需要做什么。

**这不是法律意见。** 结论基于下面标明“已核实”的公开资料和仓库内文件；标明“凭记忆”的内容没有在本次核对中验证，必须由法务确认。

## 1. 结论

1. **没有发现许可证层面的硬性冲突。** 候选组件主要是 Apache-2.0 和 MIT，它们可以随 `GPL-3.0-only` 产品分发和调用。
2. **真正的工作量不在“能不能用”，而在“分发时要做什么”。** 托管引擎的 rootfs 和虚拟机镜像里含有 GPL 类组件（例如 Linux 内核、各类用户态工具）。只要我们把这些镜像放在自己的 Release 里提供下载，就是在分发它们的目标码，需要同时提供对应源码的获取方式。
3. **这件事项目已经在做，只是还没有登记。** `docker/computer.Dockerfile` 已经把 `x11vnc`、`xfce4-*`、`ffmpeg`、`chromium`、`libreoffice-*` 等装进 GHCR 上发布的 `computer` 镜像（第 93、110、117–119、146、150–152 行）。仓库里没有仓库级的第三方声明文件，只有 `packages/plugins/wechat/NOTICE.md` 和 `packages/plugins/whatsapp/NOTICE.md`。托管引擎不会引入新的合规类别，但应该借这次机会把整体补齐。
4. **建议把它做成可检查的流程**：新建 `THIRD-PARTY-NOTICES`、为每个发布资产提供源码获取方式、在 CI 中扫描许可证，并在发布前由法务过一遍（见 §6）。

### 2.2 Apache-2.0 与 GPL 的兼容方向

来源：[Apache 基金会：GPL 兼容性说明](https://www.apache.org/licenses/GPL-compatibility.html)。

- 页面写明 FSF 认为 Apache-2.0 与 GPL 第 3 版兼容，并且“Apache 2 software can therefore be included in GPLv3 projects”。
- 反方向不成立：“GPLv3 software cannot be included in Apache projects”，即兼容只在一个方向上成立。
- 页面还写明 FSF 从未认为 Apache-2.0 与 GPL 第 2 版兼容。

对本项目的含义：本项目是 `GPL-3.0-only`，不是 GPLv2，所以 Apache-2.0 组件可以包含进来。即使将来把 Lima 作为库并入 CLI，也不违反许可证（仍需保留版权与 NOTICE，见 §3）。

### 2.3 “聚合”与“分发目标码”的条款

来源：仓库根目录 `LICENSE`（GPLv3 全文）。

- 第 5 条（聚合）：把受保护的作品与“其他单独且独立的作品”放在同一存储或分发介质上，只要它们没有组合成一个更大的程序，就称为“aggregate”；“Inclusion of a covered work in an aggregate does not cause this License to apply to the other parts of the aggregate.”
- 第 6 条（分发非源码形式）：分发目标码时，必须同时提供对应源码，方式有 a 至 e 五种。其中 6(d) 允许“从指定地点提供目标码，并在同一地点以同样方式免费提供对应源码”，并要求在目标码旁清楚指明源码位置，且只要需要就必须保持可用。

## 3. 分析

### 3.1 我们的代码调用这些组件，是否变成一个合并作品

我们的 CLI 通过命令行启动 `docker`、`limactl`、`wsl.exe`，并通过 stdin/stdout 交换数据。它们是各自独立运行的程序。这与项目现在调用 `docker` 的方式一致，不是新增的做法。

GNU 的常见问题解答对“管道、套接字、命令行参数通常不构成合并作品”有明确说法，但本次两次读取该页面都被限流（HTTP 429），**没有核实原文**。结论来自上面已核实的 GPLv3 第 5 条和通行理解，需法务确认。

### 3.2 Apache-2.0 组件分发时的义务

凭记忆（Apache-2.0 第 4 条，标准内容，未在本次重新核对）：

- 随分发附上许可证文本。
- 保留原有的版权、专利、商标和署名声明。
- 若有 `NOTICE` 文件，在分发中保留其内容。
- 修改过的文件要有显著的修改说明。
- 不得使用贡献者的商标作为自己的产品名。

做法：不修改上游组件；原样分发或原样下载；把许可证文本和 NOTICE 汇总到 `THIRD-PARTY-NOTICES`。

### 3.3 GPL 类组件：只有“我们分发”才产生义务

| 部分 | 谁分发 | 我们的义务 |
| --- | --- | --- |
| Windows：WSL 与 Linux 内核 | 微软 | 无，由 Windows 提供 |
| Windows：我们构建的 rootfs（含用户态 GPL 软件） | 我们（放在 Release） | 需提供对应源码获取方式 |
| macOS：虚拟机内核、initrd、磁盘镜像 | 取决于方案 | 自托管则需提供源码；从上游官方地址下载则由上游承担 |
| 引擎二进制（Moby、Compose） | 我们或上游 | Apache-2.0，附许可证与 NOTICE |
| 现有 GHCR 镜像（`computer` 等） | 我们 | 已存在，应同一并补齐 |

关键取舍：

- **方案 A：安装时从上游官方源下载并校验摘要，我们不转发。** 我们不是分发者，GPL 源码义务落在上游。缺点：上游地址可能变化，可用性和供应链风险更高；首次启动要联网安装 dockerd，速度慢且不易复现。
- **方案 B：我们在 CI 中构建并自托管，附源码获取方式。** 版本固定、可复现、离线性更好。缺点：我们成为分发者，必须维护源码获取方式。

建议：许可证上两者都可行，选择由 Spike A 和 Spike C 的工程结论决定。**无论选哪个，都应先建立方案 B 所需的源码获取机制**，因为现有 GHCR 镜像本来就需要它，建立后三类资产可共用。

## 4. 具体建议

### 4.1 必做（发布前）

1. **新建仓库级 `THIRD-PARTY-NOTICES`。** 每个随发布分发或安装时下载的第三方组件登记名称、版本、许可证、来源地址，并附 Apache-2.0 的 NOTICE 内容。随 Release 资产发布，并在桌面端“关于”页提供链接。
2. **为分发的 GPL 类组件提供源码获取方式。** 采用 GPLv3 第 6(d) 的做法：在 Release 页面旁提供源码归档或指向上游源码的固定链接，写明获取方式，保证至少三年可用。Debian 系 rootfs 可用 Debian 的归档与快照服务固定版本（凭记忆，需核对），并把构建配方放进仓库。
3. **不内置、不依赖专有的引擎软件。** 本方案不使用 Docker Desktop 本体，只使用 Moby、Compose 等开源组件。Docker Desktop 的订阅条款与本项目分发无关（凭记忆，未核对）；坚持这一点可以避开该类问题。
4. **名称使用。** 界面与文档里提到 Docker、Moby、Lima 等名称时，仅用于描述兼容性（例如“兼容 Docker 的引擎”），不把它们用作本产品或引擎的名称。引擎名称使用 `outcomego-engine`。商标具体政策凭记忆，需法务核对。
5. **资产摘要与签名。** 复用现有 sigstore 流程（`apps/cli/src/release.ts`、`apps/cli/scripts/sign-release.ts`），让用户能验证所下载的就是我们登记的那一份。

### 4.2 建议（降低长期成本）

1. 在 CI 中加入许可证扫描和 SBOM 生成（例如用 Syft 生成 SPDX 格式，凭记忆，工具选择可由团队决定），新增依赖时自动提示许可证变化。
2. 发布流程里加一个检查：任何新增的第三方二进制，必须同时更新 `THIRD-PARTY-NOTICES`。
3. 固定引擎组件版本，升级通过 PR 并附许可证变更说明。

### 4.3 不建议

- 不要把 GPL 类组件的代码直接编译进我们的二进制。本方案没有这个需要，保持“独立程序、命令行调用”即可。
- 不要在没有登记的情况下随意替换 rootfs 基础发行版，不同发行版的许可证与源码获取方式不同。

## 6. 请法务确认的问题

1. 我们在 Release 页面提供 rootfs 或虚拟机镜像下载，是否构成对其中 GPL 组件的“分发”？采用 GPLv3 第 6(d) 的方式提供源码是否足够？
2. 通过命令行与独立程序（Docker、Lima、`wsl.exe`）交互，是否会被认定为合并作品？
3. “Docker”“Moby”“Lima”等名称在界面与文档中的使用范围是否合适？
4. 现有 GHCR 镜像（含 `x11vnc`、XFCE、`ffmpeg` 等）当前的源码提供与声明方式是否充分，是否需要在本次一并补齐？
5. Electron 与 Chromium 随桌面端分发的声明（`LICENSE.electron.txt`、`LICENSES.chromium.html`）是否已经满足要求，是否需要并入 `THIRD-PARTY-NOTICES`？（electron-builder 默认带这些文件，凭记忆，未在本仓库核对。）
