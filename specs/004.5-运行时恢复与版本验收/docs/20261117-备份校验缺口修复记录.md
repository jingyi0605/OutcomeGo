## 问题与修复

原校验器只按 `outcomego_*` 前缀接受表名，并用一份跨表列名清单猜测外键目标；目标表完全未提供时又跳过校验。这既漏掉新增 Outcome 关系，也会把没有外键的投影字段错误解释成关系。

本轮把物理结构和关系来源统一到本工作树的 `packages/db/prisma/schema.prisma`：

- 表和列按 `@@map` / `@map` 对应物理名称核对，不再把名称前缀当作已存在的物理表。
- 外键只取源模型的显式 `@relation(fields: [...], references: [...])`，按目标模型实际列建立索引；非空引用的目标表未提供时作为空目标处理并拒绝。
- 复合外键比较整个有序 tuple，不把多个单列命中误当作一条关系；使用 PostgreSQL 默认 MATCH SIMPLE 的任一分量为 null 时豁免规则。
- Decision、HumanReceipt、HumanActionCard 与未来明确声明的 Explore 模型直接从 schema 获得规则，不维护第二份模型/关系清单。
- helper 不加载 Prisma Client、不连接数据库，也不增加依赖。模型按当前 schema 的分行声明布局读取；属性扫描跳过字符串、保留注释里的换行，并支持跨行关系、映射列和复合引用。无法解析的模型布局、未解析的关系目标和缺失的关系字段显式报错，不静默丢弃。

### 历史 F2 的澄清

历史 F2 使用 `outcomego_channel.botId`；实际 `Channel` 没有这列，因此它不是一个真实 FK 缺目标表的复现。原正例也误带了这列。本轮不改历史样本、日志或 FAIL 结论，把它保留为“被接受的非当前物理列”证据，并新增正确的回归：

1. 原 `Channel.botId` 样本因不存在的物理列而拒绝。
2. 使用实际 `ChannelMember(channelId, botId)` 外键：备份提供 Channel 和 ChannelMember，但整个 Bot 表未提供，必须拒绝。
3. 原正例/破损关系例改用真实 ChannelMember 关系，不保留旧的列名猜测行为。

历史 F1 的虚构物理表和 F3 的 Outcome 孤儿引用也有专门回归；保留的历史观测位于 `20261117-l5b-evidence/`，没有重跑采集器或重写历史文件。

## 当前格式兼容边界

本轮核查了 `scripts/backup.sh`、当前 Prisma schema 和 `prisma/sql/raw-schema.sql`。`scripts/backup.sh` 生成 PostgreSQL custom-format dump 与 volume archives，不是本校验器的 portable JSON 输入；本仓库现有 portable JSON 构造入口为 `createOutcomegoBackup`。

当前 raw schema 唯一单独 `CREATE TABLE` 的对象为 `outcomego_search_document`。该表在 Prisma 中有 `@@ignore` 的完整物理形状，包含 `searchVector Unsupported("tsvector")?`；helper 保留该表和生成列，并不把其 `botId` / `channelId` 当作 FK。schema 初始化 marker 是 schema comment，不是备份数据表；PostgreSQL 系统 catalog 不属于 `outcomego-backup/v1` 的产品物理表。

没有新增“必须包含所有表/字段”的要求，仍接受有效的部分表和稀疏行、空表、null 可选关系、无 FK 的标量 ID。列检查只拒绝当前物理模型没有的列；不检查所有字段类型、必填值或生成列是否可写。校验通过仍不是数据库实际导入成功的证据。

原 manifest 格式、产品/schema 版本错误、canonical SHA-256、rowCounts 合同和导出构造 API 保持不变；不转换旧 schema、字段或表名。文件校验继续只读，同一有效或失败源文件可重复校验。
