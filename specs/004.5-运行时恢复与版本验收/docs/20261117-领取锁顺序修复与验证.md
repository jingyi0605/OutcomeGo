## 问题与修复

源码问题已用真实 PostgreSQL 重现。旧 Worker 按候选优先级扫描所有 Outcome，并持有阻塞式事务咨询锁；全局停止按 Outcome UUID 升序取得多把锁。候选顺序为 B、A 而停止顺序为 A、B 时，双方形成死锁。旧扫描还会让已锁定的后台 Outcome 阻塞前台消息。

实现提交：`8be7c16b913164318c7fdd72328fbade0ec338e4`，仅修改：

```text
apps/worker/src/worker.ts
apps/worker/test/outcome-claim-locks.integration.test.ts
```

领取现在按原优先级逐项选择，先检查已有租约及前台/Routine 是否可领取；Outcome 候选按 Outcome → WorkItem 顺序尝试取得非阻塞锁，争用时继续下一个候选。首个有效候选一旦选定即结束扫描，所选项的锁一直持有到领取事务完成。取消队首的同次清理、revision 复查、过期 Run 防重发、唯一租约和普通消息行为均保留。

本提交不修改线 3 的共享 revision 谓词，也不复制 Decision 或派生补充任务的规则。
