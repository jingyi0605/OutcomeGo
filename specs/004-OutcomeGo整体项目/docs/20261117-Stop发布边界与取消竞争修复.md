## 实际原因与修复

### 可见消息与终态取消竞争

原 `assertBackgroundRequestDeliveryAllowed` 未在实际消息发布事务调用。已经认领的 completion 在请求停止后仍能发布主对话消息和同伴消息。`sendVisible` 在附件准备结束后、实际事务开始时执行既有 Stop 检查；`sendToAgent` 在实际事务中执行相同检查。检查锁序保持 Agent lifecycle → bot-run-claim，与退休顺序一致。

`SubagentService` 在成功停止子任务后，根 Run 可能恰好终态化，随后传输取消抛错。现在重读根 Run：已经终态则承认成功，仍活跃时继续报错，不掩盖实际停止失败。既有 ordinary/Routine 广义 Stop 和 Outcome 隔离逻辑未被替换。

### 显式 Stop 优先于重驱

`WakeWorker.fail` 原先优先处理上下文优先级中断，即使 Run 已有实际 Stop 标记，也可能将它改成 interrupted 并重驱。现在 `TurnStoppedError` 或已持久化的显式停止事实优先，保留取消及删除原因，不创建重驱和提醒；查询未完成的优先级前驱时同样排除实际停止请求。

普通 typed/peer 中断的有界重驱保持原行为。恢复线的内存、启动恢复和清理代码不在此改动范围；已与对应所有者确认 fail 区段互不覆盖。

### 连接通道的真实发布认领

负责人已经明确批准并冻结以下语义，**不再等待策略批准**：

1. 所有附件、原生文件 token 及 packaged stdio 运行环境准备在发布认领之前完成。
2. 使用真实持久化 Run 验证 Bot 和 origin；在生命周期 → botclaim → 来源 Run `FOR NO KEY UPDATE` 的同一个短事务内重新检查来源仍运行及 Stop 事实，并完成既有 `PluginInvocation` 的条件 `Executing` 认领。
3. 短事务提交后才发起文本 RPC 或原生文件 I/O。事务不包围外部请求，不以事务超时宣称保护整个长 RPC。
4. Stop 先于未认领请求提交时，拒绝发布，零 RPC；先认领的调用已经在途，允许 Stop 提交后继续保存实际回执。
5. 已完成回执重放不发送第二次；在途、失败或结果不确定的调用不自动重试。一次拒绝不能把另一个正在执行的回执覆写为失败。

### 独立复核发现的来源 Run 缺口

`a8b2f025b` 的背景根请求检查不能替代来源自身状态检查：普通 user/Routine/Outcome origin 会从背景 helper 提前返回。真实 user 工具入口虽然先检查 running，但异步准备期间实际 Stop 可将来源改为 cancelled；此时尚未认领的发布仍可能执行。这是独立审查发现的实际 P1，不是策略分歧；`483112921` 及最初 93 PASS 不能单独作为 Task49 完成依据。

补充 `e89efc9e3` 在短认领事务内对所有来源取得上述锁，再读取 Run 的 `status`、`requestStoppedAt`、`error`；已停止返回 `request_stopped`，其他不活跃来源返回 `tool_context_invalid`。来源行锁还与 `RunService.cancel` 对 running Run 的直接更新串行化，因为该更新不取得 botclaim。事务提交后才进行外部 I/O，完成回执仍先于可变状态检查重放。

新增五个真实回归先在旧 helper 上复现 **0 PASS / 5 FAIL**，随后原样验证修复：实际 `InternalToolService` user 入口通过 running 检查后暂停文本准备，使用实际 `SubagentService.stopRun` 提交取消后才释放；原生 token 准备使用同样实际 Stop；另外覆盖 cancelled user/Routine/Outcome 拒绝及独立新 active 来源正向发布。测试通过 Effect 的错误通道取得原始 ApiError，继续断言结构化 `request_stopped`，没有把期望改成任意异常。
