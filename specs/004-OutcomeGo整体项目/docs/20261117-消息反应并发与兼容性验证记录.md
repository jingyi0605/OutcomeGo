实际生产问题：

- 用户 receipt 在事务外读取，同请求并发均可读到不存在，随后各自 create，触发唯一约束；不同请求也会同时读取旧 metadata 再覆盖，丢失其他 actor 的反应。
- Bot receipt 仅按 Bot/callId 标识，provider 在另一个 Run/聊天重用 callId 会返回旧结果；事务内同 key create 同样没有串行化。
- Bot 通知 key 没有 Run 身份，跨 Run add/remove/add 会被先前相同 key 抑制；已归档聊天仍可能被反应修改，离群作者仍可能被用户反馈重新唤醒。

这些失败在独立无认证污染的进程和新数据库中重现，不属于 task-48 的级联错误。

## 生产修正

用户和 Bot 路径对同一目标 `ChannelMessage` 使用同一种 `FOR NO KEY UPDATE` 行锁，并在取得锁后重新读取最新 metadata。用户 receipt 查询移入该事务及锁之后，保证重放只返回原 receipt 和当前消息，不重新 toggle 或唤醒。

Bot receipt 使用 `reaction:<botId>:<runId>:<channelId>` scope，callId 仍为 key。精确调用 advisory lock 先于 receipt 检查，使未知地址的返回也能幂等重放。新增通知 key 同时包含 Run/callId。

旧 `reaction:<botId>` receipt 保留兼容读取：早于当前 Run 的旧 receipt 不影响新调用；可能属于当前在途 Run 的 receipt 必须由原持久化通知精确证明 Run/channel/Bot/message 归属，才复制 scoped receipt 并原样重放。无法证明时返回明确错误，不重复 toggle；原参数冲突检查仍保留。

对用户反馈保持作者必须仍在 channel.members 的条件。Bot 修改目标复核当前成员身份和 channel 未归档。没有新增 schema、合同、客户端标志、工具门禁或全局 runtime。
