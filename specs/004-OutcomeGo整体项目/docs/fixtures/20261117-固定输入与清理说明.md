# 2026-11-17 固定输入与清理说明

这六份 JSON 是完全虚构的可重复输入和预期状态，不是回放结果或实际数据库导出。`$bot`、`$outcome`、`$revision`、`$workItem` 等变量必须在执行时绑定到新建 fixture 的真实 ID；不得用固定 UUID 覆盖已有用户对象。

| 文件 | 父场景 | 输入与主要关联 |
|---|---|---|
| research-outcome.json | A/F/G | 研究任务、批准/执行/成果/返工；WorkItem→Revision→Outcome、Run→WorkItem |
| decision-pending.json | B/E | 缺失输入、两选项竞争、同线程续跑；Decision→WorkItem/Revision |
| human-action.json | C | Agent 请求人工、上传、回执事务失败重试、统一 Review；Card requester→Agent、Receipt→Human |
| duplicate-event.json | D | 六个恢复/失败场景；相同完成事件和消费回执、unknown 外部回执 |
| fresh-install-import.json | H | 当前格式导入与 unknown table/missing target/orphan 负例；实际 restore 仍待执行 |
| release-assets.json | H | 发布资产、签名/名称、关闭入口/旧镜像；不执行发布或远端重建 |

每个文件包含 schemaVersion、fixtureId、fictional、input、initialState、requests、expectedStates、idRelations、notificationCategories、assertions 和 cleanup。`bun scripts/check-outcome-contracts.ts` 校验状态枚举、事件目录、关系语法、输入边界和六个文件的完整性；它明确输出 runtimeReplay=PENDING。

实际数据库脚手架位于 `apps/server/test/fixtures/outcome-recovery/`，使用真实 messaging/Decision/Human/Review 服务。无知识来源的场景才使用空 resolver。未知外部回执的 adapter 仅是 test fixture；真实 provider 的发送/查询/unknown 分类须另外验收。

CLI 只接受显式本地 PostgreSQL 测试库，保留配置端口（CI 5432/本线 55437/集中验收 55439），不读取 `.env`，不从通用 DATABASE_URL 选择数据库。`--plan` 不连接数据库；真实执行会新建自己拥有的 Bot、Outcome、workspace、channel 与对照 foreground Run/lease。证据先写出，再清理该 Bot 的事件/幂等回执和关联数据、自己的 channel 与临时目录；不要全局 deleteMany、truncate、删表或修改失败状态来“修复”场景。

执行中断时先保存日志/JSON，再按报告中的 fixtureBotId/outcomeId/WorkItem IDs 查明残留范围；只能清理本次创建的对象。脚本拥有的 executor PID 必须已退出。数据库 schema 升级测试与其他 lane 不共用同一正在运行的库。只有确认归属并保存证据后才删除自己的 `outcomego-w3-pg` 容器；历史原始失败日志、固定输入文件和其他 worktree/DB 保留。
