## 私有存储更新与并发移除

真实缺陷：`PluginManagement.update` 原先可删除或关闭已有连接的
`persistentState`，导致私有目录无法再从当前清单定位；停止运行时期间，
另一服务设置的 `stateRemovalPending` 也没有在应用包更新前重新验证。

修复：

- 在停止运行时之前检查已有持久化连接的定义，拒绝会失去私有存储管理能力的更新；
  提示先卸载包以执行现有持久化存储清理。
- 预先拒绝已有的待移除状态，不触发额外 stop。
- stop 完成后，在事务中按稳定顺序锁定该安装的连接行；
  检查连接集合、运行时 generation 和移除标记，再写入包及连接。
- 保留兼容更新后的私有目录以及后续正常账户移除能力。

原有三个失败断言均保留。新增回归证明已进入失败移除状态的账户不会再次被更新停止，
连接事实和安装版本不变。

### 集成复核发现的锁顺序问题

首个增量提交 `98dfb9b35bc34bb3c07d3d33d55ce9ee59036a2b`
被 integrator 暂停接纳：它先锁账户，再写安装记录，与现有卸载流程的
“安装记录 → 账户”相反。这是本次补丁引入的真实问题，不属于原有基线。

新增真实数据库 barrier：
先让卸载事务持有安装锁，再启动更新并确认它等待安装锁；

**0 PASS / 1 FAIL**，账户锁被更新持有，返回 PostgreSQL `55P03`。

## T3 取消与重启回执

两个原始失败分别来自：

1. `InternalToolService` 的 `PluginCall` 分支调用 `plugins.invoke` 时没有传递
   `serviceEffect` 提供的 `AbortSignal`。HTTP 请求已经取消，底层插件调用仍等待提供方。
   第 406 行的 `settled` barrier 失败是首因；第 411 行 `P2034` 清理失败是后续竞态。
2. `startup-recovery.ts` 原先中断 Run，却不处理关联的运行中插件回执。
   SIGKILL 后第 342 行仍为 `running`，无法返回已定义的未知结果语义。

修复只给该调用传递 signal，并在现有重启事务内将被恢复 Run 的运行中插件回执
标记为 `failed`、`PLUGIN_RESTART_UNKNOWN_OUTCOME` 和完成时间。
已完成回执和结果不会被覆盖，也不会自动重放远端动作。
原测试保留了 SIGKILL、完成回执不变、重复恢复不变、未知结果禁止重放及提供方只执行一次断言。

HTTP 用例另外跟踪并等待真实 invocation 结束；即使 Bot 清理失败也执行 fixture close，
避免未关闭的安装和客户端污染后续测试。没有编辑 Human 的 transport/connectors
短事务认领实现；`InternalToolService` 改动仅在 `PluginCall` 分支，
与其 connected SendToUser 分支分离。Recovery 负责人确认本次恢复块与其任务不冲突。
