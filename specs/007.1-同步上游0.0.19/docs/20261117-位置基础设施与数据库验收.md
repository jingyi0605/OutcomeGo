## 2. 契约与 API

新导出为 `@outcomego/contracts/user-location`，同时由 contracts 根入口导出。

| 契约 | 字段与含义 |
| --- | --- |
| `DeviceLocation` | `latitude`：-90..90；`longitude`：-180..180；可选 `accuracyMeters`：0..10,000,000；`capturedAt`：带时区的可解析 ISO 时间；`device`：`phone` / `computer` |
| `LocationSubmission` | `fix: DeviceLocation` 与 `sharingRevision: UUID`；不接受客户端声明的账户作为归属依据 |
| `UserLocation` | `DeviceLocation` 字段加非负整数 `ageMinutes` |
| `UserLocationView` | 有 fix 的 `UserLocation`，或 `{ available: false, reason }`；不返回地址，不表示实时跟踪 |
| `UserLocationState` | `sharing: { enabled, revision }` 加 `location: UserLocationView` |
| `UpdateLocationSharingInput` | `enabled` 与 `expectedRevision: UUID`；变更需要匹配当前 revision |
| `SendMessageInput.location` | 可选 `LocationSubmission`；原有 `clientId`、reply、附件、voice、sourceMachineId、richText 等字段不变 |

上游 `location` 直接使用 fix，本地增加 revision 包装以阻止关闭/重新开启后旧请求恢复定位。未来 UI 必须使用本地契约，不能直接传上游 payload。

| HTTP 路径 | 方法 | 输入 / 输出 | 权限与副作用 |
| --- | --- | --- | --- |
| `/api/v0/location` | GET | 返回 `UserLocationState` | 由会话解析账户；首次读取仅建立关闭状态的 tombstone，不开启共享 |
| `/api/v0/location/sharing` | PUT | `UpdateLocationSharingInput` → state | revision 比较后变更开关；每次旋转 revision 并清除旧 fix |
| `/api/v0/location` | PUT | `LocationSubmission` → view | 必须已明确开启共享且 revision 匹配 |
| `/api/v0/location` | DELETE | 无输入 → 关闭 state | 无条件关闭该账户的共享，清空 fix 并旋转 revision；不删除 tombstone |
| 现有 direct / group message API | POST | 原有输入加可选 location | fix 与新消息在同一事务接受；过期 revision 拒绝整次新消息接受 |

以上响应均为 `cache-control: no-store`。后端 flag 未开启时返回 `404 location_disabled`，不访问新表；现有无定位消息不受影响。无效/撤销会话返回 `401 unauthorized`，共享 revision 不匹配返回 `409 location_sharing_changed`。

## 3. 账户、实例与取消语义

### 3.1 服务端

- 认证必需模式：以可信 `authenticatedSessionId` 查询仍有效的 `outcomego_session`，从真实 `userId` 生成 `ownerKey=user:<userId>`。不信任 body 中的 owner、provider account、connectionId 或任意“全局账户”字段。
- 认证关闭模式：使用 `ownerKey=local`；不与认证账户命名空间混用。各实例的既有独立数据库是实例边界，不新建虚构的租户或插件实例身份。
- 读取账户归属时持有 session 的共享行锁，以便事务与 session 删除保持顺序；再使用该 owner 的事务级 advisory lock 串行化共享开关、清除和写入。多 server 进程使用相同数据库锁，不靠进程内布尔变量隔离。
- DELETE 及 PUT 共享变更都保留新 revision 的 tombstone。这样即使 late write 在清除之后抵达，或共享已经重新开启，旧 revision 仍然失效。
- 成功 sign-out 先按现有流程撤销认证会话，再使用此前服务端验证的 user id 关闭该账户共享。其他设备持有的旧 revision 也失效。flag 默认关闭时该回调不访问位置表；位置清除失败也会在 finally 中继续原有设备撤销，不阻断现有 sign-out 清理。
- direct/group 的会话 identity 与输入字段分别传递；权限在实际记录 fix 的消息事务中再次核验，覆盖附件准备等延迟窗口。消息失败也回滚 fix。
- location 不写入消息 metadata、转录或 external message 回执；外部消息没有可信设备 fix，因此不新增位置入口。现有 `external_dm` 的只读行为和枚举保留。
- 幂等 hash 排除 location，与上游增量的原则一致。一个已接受 nonce 的重试直接返回原回执，不因为新 fix/revision 而冲突，也不重新记录位置或重放消息。
- `capturedAt` 超过服务器当前时间时按当前时间保存；tool 说明 fix 的年龄和精度，不承诺地址或实时位置。

### 3.2 client-core

- 仅 `locationEnabled: true` 才启用基础流程。默认 false 的旧客户端继续发送原有单个请求，不查询位置 API，不等待定位，不改变 cookie/认证行为。
- opt-in 必须提供同步 `getAccountKey()`，建议格式包含规范化服务器、账户与单调递增的适配器 generation。切换离开后再切回也必须改变 generation；未提供返回 `location_owner_required`，不发请求。
- 每个 opt-in 操作在第一次 await 前记录 generation/account key，随后固定原服务器 URL 和 bearer token；每次异步边界后重新核验账户和 token。定位流程使用 `credentials: omit`，不能从可变 cookie jar 换成新账户。
- `cancelPendingLocationRequests()` 同步递增 generation 并 abort 已登记请求。未来平台适配器必须在切账户、退出登录或销毁旧 client 时调用，且在变更后建立新的 account generation；本阶段没有连接任何 UI。
- `clearUserLocation()` 和 `updateLocationSharing()` 在网络操作前先取消 pending 操作并停止本地 fix 附加。清除失败也不恢复本地共享；只有成功显式 enable 才恢复。
- 设备定位等待默认 3,000ms，可用 `locationTimeoutMs` 配置。异常/超时降级为不含位置的正常消息；取消或账户变化拒绝原 pending send，不把旧内容发送到新账户。
- `clientId` 在定位等待前生成，调用方提供的 durable nonce 始终保留。HTTP 已开始后的取消不代表服务器未接受；应按现有 delivery 状态及相同 nonce 核对，不能自动换 nonce 重发。

### 3.3 GetUserLocation

Computer 从同一个 `GET_USER_LOCATION_TOOL` 定义注册名称、描述和空对象 schema，通过现有 control plane 转发。Server 先验证活动 run context，拒绝 subagent 和 owner 参数，随后检查 flag。

现有 bot 属于单部署 owner，run 没有独立租户 owner 字段。因此认证模式的工具仅在数据库恰有一个 User 时读取该 owner 的 fix；没有 owner 或多于一个时返回 `available:false`，不会任选一行。client API 的多账户行仍相互隔离。auth-disabled 工具只读 `local`。该限制也适用于 routine；真正的多用户 bot 归属需要另行设计，本阶段不把部署共享 bot 改造成多租户模型。

## 8. 风险、回滚点与阶段停止

- 真实生产备份的复制恢复、线上延迟/多进程长时运行和真实设备定位权限仍未验收；本阶段为基础组件，不声称这些已通过。
- 开启 flag 前先部署 schema；回滚保留 additive 表和当前 migrator，避免旧部署脚本处理未知新表。环境变更、生产操作和远程 computer rebuild 都需 Jackson 另行授权。
- opt-in 的平台适配器必须提供 account generation 并接入 cancel，不能只改环境变量或复用上游 UI 代码。Desktop/iOS 保持完全 unwired。
- 工具遵循现有单 owner bot 归属；多 User 时返回不可用，不根据最近写入者猜账户。若以后需要真正多用户 bot，应先补 run/bot 的归属模型。
- 关闭共享无法撤回已经完成的工具输出，HTTP abort 也不能撤销已提交消息；保持 nonce 并按已有回执核对结果。未知结果不自动重发。
- 原阶段 1 的只读校验器刻意钉住 Phase 1 源文件与“仅文档”范围；在 Phase 2 上不能用它证明运行源码不变，也不修改其历史 fixture 迎合新增能力。

本阶段的新实现作为独立提交交付，PR 保持 draft，目标 origin/OutcomeGo。未合入时可直接关闭 PR；已合入时由另一个审查 PR 回滚本阶段应用改动，保留位置表并关闭 flag。不要回滚已验收的阶段 1 审计，也不要 reset 主工作区。

阶段 2 交付后停止，等待 Jackson 结论。阶段 3 尚未开始；预计可靠性适配及 PostgreSQL 故障/lease/Stop 回归需 3–5 个工程日，不含审查与环境等待。
