## 持久化、并发与兼容

- 日志版本为本地独立的 `version: 1`，不是服务端契约版本。
- 磁盘 scope 为 `draft-review:[API_BASE, auth.mode, user.id]:message.id`；与普通消息发送日志分开，不会覆盖既有 journal。无需数据库迁移。
- scope 中不包含凭据。持久身份按服务器及用户隔离；运行中的操作额外按本地 credential generation fencing。换账号后，旧异步响应不能写入新账号卡片。
- 日志沿用主进程双槽、原子替换和 fsync；保存完整消息/引用/附件描述，不复制附件文件字节。浏览器开发模式使用 localStorage 后备。
- 同一运行时通过共享卡片 journal 保持未完成请求所有权；卸载再挂载不会另发请求。读取请求带本地 attempt 校验，发送前发出的迟到 refresh 不能解锁新的发送。
- 写盘失败阻止请求发出，已存在的草稿保留。读取/网络失败时，不确定操作继续锁定，等待之后的只读核实。
- 存储字段与服务端现有卡片状态、发送 API 完全兼容。`packages/contracts` 没有变更，也没有新增必填或可选网络字段。
- Phase 2 的位置功能仍保持原有关闭/未连线状态。本阶段没有增加 UI 入口或 feature flag。

## 风险与回滚

1. **原生交接验收**：沙箱目录、文件权限、PDF 字节保留、AppleScript 编译和不确定回执已有自动验证；尚未对真实联系人执行 Messages 发送。原生 macOS/系统权限组合仍需 Jackson 在真实应用场景验收。
2. **磁盘占用**：可能已经交给 Messages 的附件不做基于年龄的删除，以免破坏系统排队消费。长时间使用会积累 outbox；未核实前不要删除或让清理任务接管。草稿回执也不自动过期删除。
3. **服务端权威性**：本地 read 水位只影响通知投影，不代替服务器确认。原有 read receipt 控制器继续负责发送与核实。通知点击旧消息不会提升到频道最新已读。
4. **账号隔离**：日志按服务器/用户分区，运行中结果按 generation 隔离；不把 token 写盘到草稿日志。回滚时不能合并或改写不同 scope 的记录。
5. **代码回滚**：本阶段按草稿、PDF staging、通知、测量/回归文档分别提交，可对相应提交执行新的 revert 提交。无需数据库降级或契约回滚。不要重置主工作区、强推或直接提交 OutcomeGo。
6. **数据回滚**：回滚代码时保留 `durable-send-journal` 下的新 namespace 和 Pictures outbox。旧版可以忽略新 journal；服务器已确认的回执保持有效。不确定动作先核实目标，不因为回滚重新发送。
