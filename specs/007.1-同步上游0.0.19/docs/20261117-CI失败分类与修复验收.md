## 3. 分类证据与未确定部分

### a：WeChat 目录扫描与 rename 的确定竞态

旧实现先在 state 根目录创建 `cursor.json.<random>.tmp`，写入、fsync 后 rename 到 `cursor.json`。另一个协程先 `readdir(state)` 再逐个 `stat`，可能拿到暂存名字；rename 删除这个名字后，stat 返回 ENOENT。最终文件 mode 正确也不能阻止这次扫描失败。CI 日志明确报暂存名，不能解释为单纯“机器慢”。

新增 deterministic regression 在 JSON serialization 回调执行检查。该回调精确处于 staging open 之后、rename 之前，不依赖 sleep、polling、重试或 mock。修复前真实运行失败，根目录可见 `cursor.json.995c8ac5d80d.tmp`；修复后通过。

DNS 在 UDP 使用 port 0 选出号码后，又用同一号码申请 TCP；UDP 的空闲端口不保证 TCP namespace 也空闲。首轮修复 head `1699f3192` 的 push `44011988127` 全绿，PR `44012032409` 再次在 `127.0.0.1:43112` TCP listen 报 EADDRINUSE（2.89ms），WeChat 两个目标用例均通过。这是资源分配错误，不能归为计时 flake；后续补入 DNS 修复，而非重跑原 head 碰运气。源文件与基线 blob 相同，但没有历史基线 CI 失败证据，因此不归 c。

## 4. 修复与兼容性

- `StateStore.writeJson` 改在现有私有 `state/tmp` 下创建随机、0600 的暂存文件，再原子 rename 到原来的 state 根目录 canonical 路径。读者扫描 published state 名字时不再遇到正在消失的 staging 名字。
- tmp 是 prepare 创建的同一 state 树内 0700 目录；不新建迁移、格式版本或账户目录结构。保留 `STATE_VERSION=1`、原文件名、open O_EXCL、文件 fsync、目标目录 fsync、失败清理和并发整文件替换行为。
- prepare 原有 tmp 清理继续回收中断写入；原有根目录旧 `.tmp` 清理保留，兼容升级前遗留文件。账号 remove/clear 生命周期不变。
- 新回归同时检查 published 旧字节在交接前仍可读取、staging 文件 0600、目录 0700、新字节在交接后可读及暂存清空。
- 原成功/失败写入用例只增加 tmp 清空断言，保留旧根目录检查；`secrets.test.ts` 没有改动。没有捕获并忽略 ENOENT，没有缩小原断言范围或增加对测试的重试包装。

这只解决正常原子 replacement 与根目录扫描的冲突，不承诺在另一个调用显式删除账号/整个目录时提供全目录 snapshot。tmp 需和 state 根目录处于同一文件系统，沿用正常的 prepare 创建布局，不支持单独把 tmp 外挂为另一个文件系统。

### DNS：让 port 0 在各 transport 独立分配

- `startComputerDns` 为 UDP 和 TCP 分别维护 bound port。请求 port 0 时，两者各自把 0 传给内核选择可用号码，不再把 UDP 号码直接用于 TCP。
- 返回值保留 `port`（UDP），额外增加内部 `tcpPort`；测试的 TCP 客户端读取实际 TCP endpoint。原 UDP、分片/合并 TCP、失败路由、调用次数和 SERVFAIL 断言全部保留。
- 唯一生产调用在 `browser-network-worker.ts`，使用默认固定 5353；非零配置仍让 UDP/TCP 使用同一显式端口，默认 host 列表、协议行为和失败传播不变。不修改 wire contracts 或运行环境。
- 新回归通过 scoped spy 模拟 TCP namespace 拒绝显式使用 UDP 号码、仍允许 kernel port 0 分配的情形；修复前原启动路径确定性报 EADDRINUSE，修复后成功启动真实 sockets。spy 在 finally 恢复。没有资源获取重试、test retry 或 timeout 扩大。
