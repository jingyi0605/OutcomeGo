## 解包超时的原因与源码修复

main CI `44019060660` 与 PR CI `44028516454` 的原始日志均已取回，实际失败为 `managed runtime archive confinement > enforces the archive entry limit even when every entry has zero payload bytes`，后者 5000.35ms 超过原 5000ms。随后测试清理目录导致未完成解包报告 `ENOENT: Cannot cd into .../payload`，不能把该次运行视为成功。

原 extractor 对每个合法 `./` Directory header 都交给 tar 做 root 元数据操作。此时 payload root 已由安装器以 0700 创建，20,001 个 root header 的 fixture 因而触发大量冗余文件系统操作。

修复只在 `packages/plugin-sdk/src/runtime-assets.ts`：照旧累计所有 header 数量、展开字节并进行路径、类型、链接、取消和上限验证；已创建的 payload root directory header 不再进入 tar 的实际写入。非法记录仍标记整份 archive 无效，20,000 上限和私有权限保持不变。普通文件、目录和链接行为保留。

原 20,001 entries 拒绝用例原封不动；新增恰好 20,000 entries（19,999 root header + 1 文件）的成功用例，核验文件内容与 payload root 0700，防止错误忽略 root header 计数或改变权限。

## 后续真实缺陷：开始读取前取消的语音上传

`923250372` 的本地完整 workspace test 触发原 server 断言：`cancelling a stalled upload releases its stream before calling the provider`，期望 `cancelled=true`，实际 false。实现先异步读取 credentials，再进入 boundedBytes；若此时 signal 已取消，原 `throwIfAborted` 在取得 reader / 注册取消回调之前抛错，Request body 因而未释放。该代码早于本次上游增量，仍是当前预检中真实重现的资源生命周期缺陷。

新增不依赖 sleep 的 `an upload cancelled before reading still releases its stream` 回归，先 abort 再调用 service。在修复前实际失败：0 pass / 1 fail、Expected true / Received false；原始输出保存在本轮目录的 `transcription-early-before.log`。

修复在 `apps/server/src/transcription/service.ts`：已有 body 且 signal 已取消时，先 await body.cancel（清理错误不覆盖取消结果），再抛出原 abort。正常流式读取、响应上限、provider 请求以及原 cancellation 错误码不变；没有改变既有断言或 timeout。此修复独立 commit，可单独 revert；仅影响已取消但尚未开始读取的 body 释放。

两个取消用例在停止本轮本地 Docker builds 后连续独立执行 20 次，40/40 PASS；整个 transcription 文件和 server typecheck PASS。第一次并行 Docker 构建期间的重跑在第 5 次被机器调度停顿打断，旧用例记录 18,875.14ms（原 5,000ms timeout）而非断言错误，该轮失败日志完整保留，不计入 20 次成功序列。采样 load average 8.24 / 9.80 / 7.60、物理内存 16 GiB，存在较多压缩/交换活动；没有增加 timeout 或终止其他会话的进程。
