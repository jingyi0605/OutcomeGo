## 2. 逐项行为比较与取舍

| 项目 | 上游 v0.0.19 | 本地已有语义 | 本阶段取舍 |
| --- | --- | --- | --- |

| 旧 worker success / delta | 主要保护 fail 与 settlement | session、compaction、message delta 和 completion 分别投影；Bot home Pi session 不允许替换 | 所有生产 projection 调用携带 attempt，检查与写入共用事务；保留每种投影逻辑和 home session 不变量 |

| Stop 与缓冲成功 | 保留 cancelled，同时释放 lease、结算 inbox | 本地还用 requestStoppedAt、routine 原 context、durable handoff receipt 阻止后续发布 | 保留取消原因；补接已有发布 guard；claim/retry 同时检查 handoff 原 routine 的 Stop |
| stalled lease | 启动及每 30 秒通知无有效 lease 的 processing wake | claim 可回收两分钟前的 processing，但没有新 queue hint 时可能永远不再 claim | 增加启动/周期 sweep，并覆盖已到期 pending 的丢失通知；不抢有效 lease |
| terminal processing 遗留 | 延迟结算主要由当前 worker 的 fail 路径恢复 | claim 会删除 terminal lease，但 processing inbox 仍可能遗留 | sweep 还恢复已投影 completed/cancelled 且没有有效 lease 的 inbox，不重跑模型 |
| Server restart | 此增量集中在 worker 恢复 | 本地 Server 持有 TASK_RECOVERY_LOCK，先取消旧 computer，再中断运行；foreground 最多三次 runtime.reconcile | 只对未行动的指定自动 wake 应用同一重试策略；保留普通用户、Task、foreground 的原恢复逻辑 |
| external inbound recovery | 上游不覆盖 fork 的完整外部消息模型 | connection/binding/cursor 幂等；最多 20 次或 30 分钟，退避 2 秒至 60 秒 | 完全保留，不套用自动 wake 的四次上限，不混用 connector 账户与 bot/run 身份 |
| external outbound recovery | 不替代 fork 的发送台账 | DB-clock lease fencing；pending 过期为 failed，sending 过期为 uncertain，恢复绝不重发 | 完全保留；自动重试看到 receipt 就退出。没有把 uncertain 转成可自动重放 |
| 多实例与上下文 | 依赖 DB lease | foreground 和 automation 独立 lease scope，最多四个 automation；home/channel/automation context 与 connectionId 路由分离 | 使用共享数据库锁和计数，不用进程内 attempt 状态；保留 scope、容量、channel/delivery 路由和不可变 session path |

已有两个 Stop-ordering 数据库用例实际复现：`assertBackgroundRequestDeliveryAllowed` 虽然已经存在并导出，`sendVisible` 与 `sendToAgent` 没有调用，已 claimed 的 handoff 在 routine root Stop 后仍可发布。本阶段将 guard 接在这两个事务入口，先取得 claim gate，再取得 room gate，保留未 Stop 的普通发送。没有重写整个消息路由。

进一步执行既有 typed-message 回归，六个 agent/connector/background_revival 用例实际复现：较早的 typed interruption 会使随后的显式 Stop 仍进入 redrive，或被 unfinished-work reminder 当作可恢复工作。本阶段让 durable Stop / TurnStoppedError 优先于 priority interruption，保留 cancelled_by_user 或既有删除原因，并用已有 requestIsStopped 排除已 Stop 的 reminder；普通优先级中断仍沿用原有有界 redrive。

## 3. 参数、判定与可观察性

| 参数 | 值与含义 |
| --- | --- |
| 自动 wake 类型 | routine.scheduled、routine.manual、routine.event、automation.wake_parent、request.check |
| `AUTOMATION_ATTEMPT_LIMIT` | 4，包含初次执行；最多三次自动重试 |
| `AUTOMATION_RETRY_DELAYS_MS` | 30,000 / 120,000 / 300,000 毫秒 |
| 重试计数 | 已有 `InboxEvent.attempts`，每次真实 claim 递增；进程重启不清零 |
| 有效 lease | 同一 run、相同 ownerId，expiresAt 晚于数据库 UTC 时钟；心跳不能复活过期 lease |
| 原有 lease / heartbeat | 120 秒 / 30 秒，未改变 |
| `STALLED_WAKE_SCAN_MS` | 30,000 毫秒；每轮最多 100 个 terminal inbox、100 个 bot queue hint，防止本进程重叠扫描 |
| queue hint | 保留 pg-boss retryLimit=5、retryDelay=2、retryBackoff=true；这不是模型 attempt 预算 |
| 新 feature flag | 无；这是后端恢复行为。没有开启 Phase 2 的位置 flag 或任何 UI |

候选自动重试还必须满足：bot active、inbox processing、run running/failed、持久化 attempt 相同、不是显式 Stop 或 priority_peer_interrupt、request/handoff 原归属仍允许继续、routine 未暂停/删除/禁用，且没有任何已记录行动。prompt fingerprint 不视为行动；其他 tool 开始后即不重试，不要求它成功。

事务内保存 `status=pending`、清除 claimedAt、设置 availableAt、恢复同一 run 为 queued，并写 `run.retry_queued`，记录 botId、inboxId、attempt、attemptLimit、delayMs 和错误说明。worker 另输出结构化 `Automation retry queued`；sweep 和异常结算也有日志。queue hint 发送失败不丢弃已提交的 due time，后续 sweep 可以补通知。正常 queue 在指定延迟到期后触发，补通知可能再等一个 30 秒扫描周期及队列负载。

fencing 的内部身份为 `{ botId, runId, inboxId, ownerId, attempt }`。在 lifecycle gate → bot claim gate → run row 的顺序下，检查 inbox 的归属和 attempts，再检查 lease。校验与 projection/retry/settlement 写入处在同一个事务，不能先读后脱离锁写入。dispatch 仍先持有 TASK_RECOVERY_LOCK 的共享锁，只到 computer 接受响应头；projection 不持有该全局恢复锁，避免 Server 等待 runtime 取消时阻塞其完成投影。claim 的既有全局恢复隔离保持不变。

bootstrap 单独遵守既有用户首条消息的 Bot row → Run row 顺序：在 claim gate 之后、run row 之前先取 Bot row；claim 等到该行后重新核对 inbox/run/onboarding，不能把用户已经跳过的 greeting 恢复为 running。两个真实数据库并发用例分别覆盖 claim 与 retry，没有更改 bootstrap 的四次预算或 readiness probe 策略。

若当前 attempt 已投影 completed/cancelled，允许在其 lease 已被清理后收尾，但 durable attempt 必须相同，且不能存在其他 owner 的 lease。只比较“有没有不同 owner 的 lease”不足以拒绝已经失去 lease 的旧 attempt，新增回归明确覆盖 successor 的 running/backoff/failed/completed 四种状态。

`WakeAttempt` 和 projection/dispatch 的可选参数只在内部使用；contracts、ComputerTurnRequest、客户端事件字段和数据库 schema 均未变化。`requestWakeAllowed` 的 runId 参数为可选字段，供本地 durable handoff 归属查询使用。

## 6. 风险与回滚

- 本阶段默认启用后端恢复行为，重试仅覆盖未观察到行动的窗口。若外部行动没有写下任何 run item、message 或 durable receipt，无法声称全局 exactly-once；未知发送结果仍由既有 external uncertain 流程处理，不自动重发。
- projection 为所有生产流事件增加短事务和数据库 ownership 校验，会增加数据库往返；已保持 delta 本身为单次 upsert，但未做线上吞吐/长时多实例压力验收。每次只锁当前事件，不持有整个模型流。
- worker restart 用例覆盖新实例接手和持久化状态；真实主机重启、remote computer、网络分区和生产部署未执行。无设备/签名环境依赖。
- 滚动发布时旧 worker 不认识新增 fencing，不能宣称混跑时旧进程也受保护；正式部署应协调替换全部 worker。没有在本阶段操作任何运行环境。
- 无数据库或 contracts 迁移。回滚应用提交可恢复原执行策略，位置表与 Phase 1/2 仍保留；回滚前应核对 pending retry 的 availableAt/queue 状态，旧 worker 没有本阶段新增的丢失通知扫描。
- CI 红灯调查中的 archive 五秒预算仍是已记录风险，不在本阶段改无关测试。新 head 的 CI 状态需按其实际 run 单独核对。
- 应用回滚点为 `21e61eea8`；CI 步骤和本文档单独提交，可独立撤回。禁止 reset 主工作区、回滚其他会话提交、force-push 或自行合并 Draft。
