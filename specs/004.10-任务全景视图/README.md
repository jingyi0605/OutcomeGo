# Spec 004.10 - 任务全景视图

规格编号：`004.10`

状态：Draft（只做规划，不开始实现）

日期：2026 年 11 月 24 日。

父规格：[Spec 004：OutcomeGo 整体项目](../004-OutcomeGo整体项目/README.md)

## 一句话

让所有者在一处看清三件事：**所有 bot 在做什么**、**需要我处理什么**（包括各种由人来做的现实任务，例如邮件、拜访、巡检、手动待办，这里只是举例）、**每件事什么时候**。

## 为什么合成一份规格

三部分共用同一条主线和同一批基础设施（展示状态推导、"需要我"队列、时间条目），拆开会互相引用且无法单独交付价值：

> **谁执行，决定记录从哪来。**
> bot 执行的工作，从已有的持久记录读时推导，不靠 bot 登记；人执行的事，必须有显式的待办记录，因为没有运行可以推导；等外部的事，是待办加上"等待"和跟进时间。

| 部分 | 解决什么 | 需求 | 阶段 |
| --- | --- | --- | --- |
| **A 活动视图与目标降级** | "所有 bot 在做什么"从请求进展、例程、目标任务推导，不再靠 bot 登记目标；目标只留给要契约和验收的交付 | A1 至 A10 | 0、4、5 |
| **B 现实待办项** | 通用的待办机制：由人来做的事有处安放，不含任何具体场景；没有有效所有者消息引用的创建只能先成为"建议"，所有者可对信任的例程设置自动接受规则 | B1 至 B12 | 6 |
| **D 架构约束** | 一切由 pi agent 推理，系统只限定输入输出格式；不硬编码任何具体场景；业务数值由所有者配置 | D1 至 D4 | 2、4、6 |
| **E 目标管理设置页** | 桌面端设置里独立的一页，位于"模型"与"语音消息"之间，集中显示所有相关且必要的设置 | E1 至 E3 | 2、4、6、8 |
| **C 时间线与日历** | 目标任务排期并到点才开始，目标详情时间线，全局日历，ICS 订阅，外部日历叠加 | C1 至 C13 | 1、2、3、7、8 |

## 决定的状态

**已由用户确认（2026-11-24）：**

1. 先做目标详情内的时间线，再做全局日历。
2. 日期字段：人工任务、目标截止日；同时让规划角色给 bot 任务排期并可选估时。"排期"指有些任务当前不能完成，要在未来某个时间继续，所以排期是"不早于"的约束，到点才开始。
3. ICS 订阅和外部日历叠加纳入后续规划。
4. 活动视图与目标降级、现实任务融合、任务时间线机制整合在同一份规格中。
5. 先写规格，不实现代码。
6. **活动视图与现有两个目标泳道并存**（"Bots are working"和"Paused or failed"）：先同时实现和显示，由所有者评估后再决定是否取代；本规格不实现取代。
7. **待办项用独立的轻量实体**，不扩展 tracked 目标。
8. **例程回合允许使用 `SuggestTodo`，只能创建建议**；是否设上限由策略设置决定，代码里不写死数值。
9. **手机端首批包含待办的接受、延后、忽略、完成。** 这是对 004.4 移动端写操作限制的例外，仅限待办这四项。
10. **004.9 的规划角色已在用户环境启用**（由用户确认，未在代码或环境里独立验证）。
11. **架构约束（用户要求）：一切由 pi agent 推理，系统只限定输入输出的格式；代码里不允许硬编码任何具体任务场景，只有通用的、可循环的流程。** 邮件、拜访、巡检、手动待办等只是示例，不是需求；业务数值（限额、过期天数等）不写进代码，由所有者在策略设置里配置。
12. **允许为例程或 bot 设置"其建议自动接受"**：通用规则，只能由所有者创建，必须绑定具体的例程或 bot，不针对任何场景。
13. **策略初始值先按规格里的值试用**，保留集中定义的默认值，试用后再调整。
14. **所有者授权校验采用"引用"而不是"转述"**：agent 创建待办时提交所有者消息的 ID，由服务端读取并校验，不靠 agent 在多步流程里转述原话。
15. **高紧急度事项是否触发打断式通知，作为可配置选项**（策略 `todo.highUrgencyNotify`），默认关闭。
16. **桌面端设置里新增独立的"目标管理"页，位于"模型"与"语音消息"之间，显示所有相关且必要的设置**（用户要求）。总开关和规划、审查设置从"通用"页搬来；业务策略项、自动接受规则、ICS 订阅和外部日历叠加随各自功能上线逐步出现在这一页。
17. **总开关关闭时，目标管理页其余分组可见但禁用**，并说明开启后生效。
18. **"通用"页保留一行只跳转、不可编辑的入口**，点击后打开目标管理页。
19. **目标管理页提供"仪表盘显示"选项**（并存、只显示活动、只显示目标泳道），默认并存，用于评估活动视图是否取代泳道；"需要我"区始终显示。

**已按讨论内容纳入规格，但具体取舍仍待确认**（共 10 项，见 [design.md §10.2](design.md)）：

- 目标降级的具体范围（bot 不再日常登记目标，已有 tracked 目标如何处理）。
- 目标降级的具体范围：已有 tracked 目标是否批量关闭（第 9 项）。
- 待办的范围：bot 可见的待办范围、待办是否并入目标管理开关、`blocked` 的 `policy` 来源是否进入"需要我"、待办是否有独立的到期推送（第 6、7、10、11 项）。
- 改期是否回写计划、日历默认显示项、ICS 默认内容、目标暂停期间排期任务是否放行、"必须建例程"的要求能否放宽（第 14、15、16、17、19 项）。

## 阶段顺序（建议，待确认）

用户确认的顺序是"时间线先于日历"。其余部分的位置是建议：

| 阶段 | 内容 |
| --- | --- |
| 0 | 核实与基线：请求进展的续跑是否可靠、bot 遵从度、提示词与缓存基线（涉及真实对话，需用户同意） |
| 1 | 目标详情时间线 v1（只用已有数据） |
| 2 | 策略设置通道、目标管理设置页（骨架、总开关、规划与审查、排期与延后）、排期数据、到点才开始、运行中延后、人工任务日期、目标截止日 |
| 3 | 时间线 v2（计划条、估算条、改期界面） |
| 4 | 活动视图与"需要我"统一队列 |
| 5 | 目标降级与提示词精简（必须在活动视图可用之后） |
| 6 | 现实待办项 |
| 7 | 全局日历 |
| 8 | ICS 订阅与外部日历叠加 |
| 9 | 移动端：待办的四个操作为首批（已确认）；活动列表与议程为可选 |

阶段 5 放在阶段 4 之后，是因为 bot 停止登记目标之前，所有者必须已经有地方看到 bot 的工作，否则会失去可见性。

## 核心取舍

- **展示状态读时推导，不存储。** 活动视图、待办的"逾期""需跟进"、任务的"已排期""已延后"都由现有字段推导；不新增任务状态，不改目标状态派生。
- **不另建提醒机制。** "无人跟进"只呈现请求进展自己已有的终态（对账 3 次后转 `blocked`、来源 `runtime`），不再造一套检测。
- **没有有效所有者消息引用的创建只能是建议。** agent 创建待办必须提交所有者消息的 ID，由服务端校验（存在、由所有者发出、同一对话、在有效期内），不靠 agent 转述；`SuggestTodo` 永远是建议，除非命中所有者创建的自动接受规则；判断不依赖来源类型。
- **一切由 agent 推理，系统只定格式。** 是否记录、标题、概括、紧急度、何时跟进都由 agent 给出；服务端只校验格式、权限、来源门和幂等。
- **不硬编码场景，业务数值不进代码。** 代码里只有通用流水线和格式与规模上限；数值由所有者配置的策略设置承载。场景只写在文档示例里，新增场景不需要改代码。
- **时间诚实。** 实际时间是事实，计划和估算只是意图；不预测完成日期，没有截止日的永不显示逾期。
- **提示词不增反减。** 目标降级精简的篇幅用来抵消待办新增的篇幅，目标是净减少。
- **设置页分组随功能上线逐步出现。** 活动、待办、自动接受规则、日历分组分别在阶段 4、6、8 加入，未上线的功能不显示空分组。
- **新增存储仅限**：待办项、自动接受规则、任务与目标的日期列、订阅令牌，以及现有设置表里的一个策略 JSON 列。其余都是投影。

## 与相邻 Spec 的关系

- **004.2**：沿用目标状态派生，不改状态机；`recomputeOutcomeStatus` 不变（design.md §6.2）。
- **004.3**：沿用收件箱与决策，统一进"需要我"队列。
- **004.4**：人工任务（`executorType=human`）增加日期；动作卡与回执规则不变；移动端回执上传仍不在范围内。待办项是另一种更轻的"人做的事"，不要求契约和验收；待办的移动端接受、延后、忽略、完成，是对 004.4 移动端写操作限制的已确认例外，仅限这四项。
- **004.7**：**部分取代。** `TrackOutcome`、`CloseOutcome` 工具与 tracked 目标保持兼容；变化只在 bot 的默认行为（不再日常登记）和提示词（A7、A8）。
- **004.9**：扩展 `PlanTask` 字段，沿用批准后 `SavePlan` 对未开始任务的差异规则；规划角色提示词增加排期指导。用户确认规划角色已在其环境启用，任务会按计划拆分；004.9 规格本身仍标为 Draft。
- **005.4 的事件触发例程**：任何插件事件都可以经由所有者配置的例程驱动 agent 产生待办建议，代码不针对具体插件。`google-calendar` 插件是外部日历叠加的数据来源。
- **010 群任务看板**：独立，不并入，也不进入本 Spec 的视图。
- **Explore 想法**：保持不变。Explore 是"交付前的想法"，待办是"某人要做的事"，两者不合并。
- **计算机运行时**：新增线程工具（`DeferWorkItem`）和待办工具位于 `packages/contracts`，由 `apps/computer` 读取，生效需要同步并重建远端 computer 容器；重建会中断正在运行的 bot 任务，必须先征得用户同意（见 `AGENTS.md`「Remote Debug Computer」）。

## 讨论中被替代的方案

讨论过程中曾计划拆成三份规格（时间线与日历、活动视图与目标降级、现实待办项）。现合并为本规格，原三份不再单独建立。
