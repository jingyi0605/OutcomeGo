# 需求文档 - 任务全景视图

状态：Draft

关联文档：[README.md](README.md) · [design.md](design.md) · [tasks.md](tasks.md)

## 简介

所有者想用目标管理回答三个问题：所有 bot 现在在做什么、有什么需要我处理、每件事什么时候。现状有三处缺口：

1. **bot 的工作靠登记。** 目标管理依赖 bot 把事情登记成目标，是记账式的，并和系统已有的请求进展、例程、子 agent 记录重复；仪表盘只展示目标，bot 忘了登记就看不到。
2. **现实任务无处安放。** 人工任务只能挂在一个有契约和验收的完整目标下；由人来做的事（例如邮件、拜访、巡检、随手记的事，这里只是举例）没有地方放。
3. **没有时间维度。** 任务没有排期，不能"未来某个时间再继续"，没有时间线，也没有日历。

本规格分三部分补齐：

- **A 活动视图与目标降级**：从已有记录看 bot 正在做什么、接下来会做什么。正式目标留给需要追踪、契约或验收的工作，单次安排可在目标管理中以轻量目标展示。
- **B 现实待办项**：人要做的事有轻量的待办记录，外部内容先成为"建议"。机制是通用的，不针对任何具体场景。
- **D 架构约束**：一切由 agent 推理、系统只定格式，场景不硬编码，策略数值可配置。
- **C 时间线与日历**：目标任务可排期并到点才开始，目标详情有时间线，另有全局日历、ICS 订阅和外部日历叠加。

服务对象是所有者（用户本人）。

## 术语表

- **System**：OutcomeGo 服务端、worker、桌面端与移动端。
- **请求进展**：bot 对"用户请求"的持久记录（`Run.requestProgress`），含状态（working、waiting、blocked、complete）、摘要、剩余事项、下一步、检查时间和受阻来源。`Task` 派发时自动开始追踪。
- **活动项（ActivityItem）**：活动视图里的一行，是对请求进展、例程、目标任务的只读投影，不单独存储。
- **单次安排**：所有者交给 bot 在约定时间仅执行一次的事项，在目标管理中作为轻量目标展示。排期和执行状态取自例程。
- **需要我**：所有者必须亲自处理的事项汇总队列。
- **待办项（TodoItem）**：由人执行的轻量事项，不要求契约、规划和验收。
- **建议**：状态为 `suggested` 的待办，来自 `SuggestTodo`，或来自没有通过所有者消息引用校验的 `CreateTodo`；需所有者确认，或命中所有者创建的自动接受规则，才成为正式待办。
- **来源引用**：agent 提供的不透明三元组 `{ kind, id, label }`，系统不解释其含义。
- **所有者消息引用**：agent 创建待办时提交的所有者消息 ID，不是转述的文字；服务端按 ID 读取并校验该消息。
- **来源门**：服务端按所有者消息引用判断一条待办能否直接成为 `open`，不依赖来源类型，也不靠 agent 转述。
- **自动接受规则**：所有者创建的规则，使匹配的例程或 bot 提出的建议直接成为 `open`。
- **目标管理设置页**：桌面端设置里独立的一页，集中放置目标管理相关的全部设置。
- **策略设置**：所有者可配置的业务数值（`taskPolicy`），与代码里的格式与规模上限分开。
- **紧急度**：agent 声明的 `low`、`normal`、`high`，只影响同一分区内的排序。
- **分诊**：对建议做接受、延后或忽略。
- **执行者**：`owner`（所有者）、`bot`、`external`（等外部）。
- **升级成目标**：把待办或 bot 的工作转成带契约和验收的目标。
- **无人跟进**：请求进展对账用尽后转为 `blocked` 且来源为 `runtime` 的状态。
- **排期（`scheduledAt`）**：任务"不早于"的开始时间。bot 任务未到点不启动；人工任务和待办只是预约，不阻塞任何流程。
- **截止（`dueAt`）**：期望完成的时间，只用于展示和逾期提示，不阻止执行。
- **估时（`estimateMinutes`）**：规划角色对 bot 任务耗时的估算，只用于画估算条，不产生延期告警。
- **实际时间**：任务真正开始和结束的时间，来自任务记录与运行记录。
- **运行分段**：任务的每一次运行的开始和结束。延后继续的任务有多段，段间空档不是运行。
- **延后（defer）**：运行中的 bot 任务声明"现在做不完，某时间继续"，转回 queued 并带续做说明。
- **错过计划**：到点后因停机等原因，超过宽限时间才有机会放行。
- **宽限时间**：由策略 `schedule.graceMinutes` 决定（初始值 60 分钟，待确认，见 design.md §10.2）。
- **时间条目（TimeItem）**：时间线、日历和 ICS 共用的只读投影。
- **展示状态**：由现有状态和日期在读取时推导，不存储（design.md §2.2）。
- **action / deliverable**：计划任务的性质（004.9）。`action` 表示对外部系统或现实环境执行操作，重做可能重复产生影响。

## 范围说明

### In Scope

- 活动视图、请求进展字段的公开与隐私、统一的"需要我"队列、通知分级、无人跟进的呈现。
- 目标降级：bot 默认不再登记目标，提示词与工具描述同步调整，已有 tracked 目标的处理。
- 所有者通过对话安排单次提醒或执行。桌面端目标管理和日历默认显示该安排，bot 按上下文准备并随提醒提供建议。
- 待办项实体、手动添加、建议与分诊、通用来源引用、自动接受规则、等待与跟进、紧急度、交给 bot、升级成目标、晨报。
- 通用处理流水线与策略设置：场景由 agent 推理和所有者配置表达，代码不含具体场景（D 部分）。
- 桌面端设置里独立的"目标管理"页，位于"模型"与"语音消息"之间，集中显示所有相关且必要的设置（E 部分）。
- 目标详情时间线、实际时间、规划角色排期、到点才开始、运行中延后、人工任务日期、目标截止日、所有者改期。
- 全局日历、ICS 订阅、外部日历只读叠加。
- 移动端：待办的接受、延后、忽略和完成（已确认纳入首批）；活动、"需要我"与近期议程只读（可选）。

### Out of Scope

- 自动排期、关键路径、预计完成日期、延期预测。
- 向用户的外部日历写入事件。
- 拖动调整任务依赖。
- 规划角色读取用户日历空闲时间来排期。
- 自动判断待办是否已完成（第一版由所有者手动完成）。
- 待办内置的重复规则或日历展开（周期性由例程驱动）。
- 针对具体场景的专用逻辑，例如邮件、拜访、巡检（场景只作为文档示例）。
- 由 agent 创建或修改自动接受规则（规则只能由所有者管理）。
- 移动端的目标管理设置页（移动端不管理策略、规则和订阅）。
- 为目标管理设置新增命令面板入口（现有命令面板只收录部分设置页，模型、语音消息等页也不在其中）。
- 自建 SCM（PR、CI）观察器；外部事实优先是原则，不在本规格实现。
- 群任务看板（010）并入；Explore 想法的改动。
- 取代或移除现有的目标泳道：先与活动区并存，评估后由所有者另行决定。
- 多用户共享日历和团队待办。
- 移动端甘特图、移动端回执上传、移动端创建待办。

## 需求：第一部分 活动视图与目标降级

### 需求 A1：活动视图

**用户故事：** 作为所有者，我希望一眼看到每个 bot 当前在做什么、什么状态、做到哪，以便不用逐个对话去问。

#### 验收标准

1. WHEN 打开活动视图 THEN System SHALL 列出所有 bot 当前未结束的工作，每项显示：bot、标题、状态、原因（受阻或等待时）、正在做什么的一句话、最后活动时间、下次检查时间（如有）。
2. WHEN 一项工作来自用户请求 THEN 标题 SHALL 取自原始消息内容的短预览，状态 SHALL 来自请求进展。
3. WHEN 一个请求下有 executor 子任务 THEN System SHALL 把它们汇总在父请求下，不单独成行。
4. WHEN 工作已完成 THEN System SHALL 在"最近完成"里保留策略 `activity.recentCompletedHours`（初始 24 小时）规定的时长，之后只在历史中。
5. WHEN 没有 bot 在工作 THEN System SHALL 显示空状态，而不是报错。
6. WHEN 服务端是旧版本（没有新字段） THEN System SHALL 降级为只显示状态和下次检查时间。
7. WHEN 仪表盘显示活动视图 THEN System SHALL 默认让活动区与现有的"Bots are working"和"Paused or failed"目标泳道并存同时显示，并允许所有者在目标管理设置页选择显示方式（并存、只显示活动、只显示目标泳道，默认并存）用于评估；"需要我"区在任何方式下都显示；System 自身不得移除任一泳道，是否取代由所有者评估后另行决定。
8. WHEN 同一目标同时出现在活动区和目标泳道 THEN System SHALL 允许这种重叠，并让活动区的行可跳转到该目标；已在"需要我"中显示的事项不在活动区重复。

### 需求 A2：请求进展的公开与隐私

**用户故事：** 作为所有者，我希望看到 bot 对自己工作的描述，同时不泄露不该显示的细节，以便放心使用。

#### 验收标准

1. WHEN 活动视图读取请求进展 THEN System SHALL 返回状态、摘要、剩余事项、下一步、受阻来源、检查时间、截止时间、更新时间和修订号。
2. WHEN 返回列表 THEN System SHALL 不包含证据（`evidence`）和工具错误原文（`toolError`），这两项只在单项详情里返回。
3. WHEN 返回任何请求进展 THEN System SHALL 仅对所有者身份开放；bot 不能通过任何工具读取其他 bot 的请求进展。
4. WHEN 摘要或剩余事项显示在界面 THEN System SHALL 标注"由 bot 填写"，并按纯文本渲染，不解析为可执行内容或链接。

### 需求 A3：例程与目标任务并入活动

**用户故事：** 作为所有者，我希望例程和目标里 bot 的任务也出现在同一个视图里，以便不用在多个页面之间切换。

#### 验收标准

1. WHEN 例程最近一次执行失败、被跳过或正在运行 THEN System SHALL 把它作为活动项显示，含最近一次状态和下次运行时间。
2. WHEN 例程的执行成功 THEN System SHALL 不单独成行，只在例程详情里可见。
3. WHEN 目标里的 bot 任务正在运行 THEN System SHALL 显示其阶段和任务清单完成数（来自 `ReportOutcomeProgress`）。
4. WHEN 目标里的 bot 任务有未到点的排期 THEN System SHALL 显示"已排期，何时开始"，不得显示为"正在工作"。
5. WHEN 目标是 tracked 目标 THEN System SHALL 不把它作为"正在工作"的活动项，它仍在目标列表中。
6. WHEN 同一件事同时出现在多个来源 THEN System SHALL 在活动视图内只显示一次。

### 需求 A4：统一的"需要我"队列

**用户故事：** 作为所有者，我希望所有需要我亲自处理的事都在同一个队列里，以便不遗漏、不重复。

#### 验收标准

1. WHEN 汇总队列 THEN System SHALL 合并：收件箱步骤（决策、批准、验收、人工动作）；请求进展 `blocked` 且来源为用户或策略的事项；"无人跟进"和"检查未触发"异常；待办的逾期、今天到期、待分诊和需跟进（B 部分）。
2. WHEN 排序 THEN System SHALL 先按紧急度（逾期、受阻、已等待最久）再按等待时间排序，并常显总数。
3. WHEN 展示一项 THEN System SHALL 显示一行原因和就地操作（打开对话，或沿用现有卡片的操作）。
4. WHEN 同一事项同时满足多个来源 THEN System SHALL 只在队列中出现一次。
5. WHEN 事项被处理 THEN System SHALL 立即从队列中移除（读时推导，不存储队列状态）。
6. WHEN 旧服务端缺少新来源 THEN System SHALL 只显示收件箱步骤。

### 需求 A5：通知分级

**用户故事：** 作为所有者，我希望只有真正需要我的事才打断我，以便不被噪音淹没。

#### 验收标准

1. WHEN 新事项进入"需要我" THEN System SHALL 通过现有通知渠道提醒；"无人跟进"首次出现时同样提醒。
2. WHEN 工作完成 THEN System SHALL 只在视图中留痕，不推送。
3. WHEN 状态是进行中、等待中或例程成功 THEN System SHALL 保持静默。
4. WHEN 同一事项同一状态已通知过 THEN System SHALL 不重复通知，按请求 ID 和修订号去重。

### 需求 A6：无人跟进的呈现

**用户故事：** 作为所有者，我希望 bot 停下来没人跟的任务能被我发现，以便不依赖"让 bot 都建例程"来兜底。

#### 验收标准

1. WHEN 请求进展处于 `working` 且已经发生过对账（对账次数大于 0，小于 3） THEN System SHALL 显示"核对中"，不报警。
2. WHEN 对账用尽，请求进展转为 `blocked` 且受阻来源为 `runtime` THEN System SHALL 显示"无人跟进"并进入"需要我"。
3. WHEN `waiting` 请求的下次检查时间已过期超过策略 `activity.checkOverdueMinutes`（初始 10 分钟）仍未被分发 THEN System SHALL 显示"检查未触发"并进入"需要我"。
4. WHEN 呈现这些状态 THEN System SHALL 不新建任何提醒、重试或轮询机制，只呈现请求进展已有的状态和字段。

### 需求 A7：目标降级，bot 不再日常登记目标

**用户故事：** 作为所有者，我希望目标只用于真正需要契约和验收的交付，而不是 bot 的日常记账，以便目标列表保持有意义。

#### 验收标准

1. WHEN 事项只是 bot 自己要持续跟进的工作 THEN bot SHALL 用 `Task` 和 `ReportRequestProgress` 跟进，不调用 `TrackOutcome`。
2. WHEN 用户明确要求"建一个目标"或"追踪这个" THEN bot SHALL 按现有规则创建目标，行为不变。
3. WHEN 事项需要所有者批准计划、最终验收或人工动作 THEN bot SHALL 使用目标（`TrackOutcome` 的 decision 或 approval，或 `CreateOutcome`）。
4. WHEN 生成基础提示词 THEN System SHALL 使目标管理一节净减少篇幅，并保证提示词内容不随会话轮次变化。
5. WHEN 更新工具描述 THEN `TrackOutcome` 的描述 SHALL 与新规则一致，不再要求"登记所有当前回合做不完的事"。
6. WHEN 调用 `TrackOutcome` 和 `CloseOutcome` THEN 输入输出 SHALL 保持兼容，旧调用不受影响。

### 需求 A8：已有 tracked 目标

**用户故事：** 作为所有者，我希望已经存在的 bot 登记目标不被突然改动，以便平滑过渡。

#### 验收标准

1. WHEN 系统升级 THEN System SHALL 不自动迁移、关闭或删除已有 tracked 目标。
2. WHEN 目标列表显示 tracked 目标 THEN System SHALL 带"bot 登记"标记，并提供筛选。
3. WHEN bot 对自己登记的 tracked 目标调用 `CloseOutcome` THEN System SHALL 照常处理。

### 需求 A9：默认隐藏与密度

**用户故事：** 作为所有者，我希望视图默认只显示我关心的内容，且 bot 多了也看得清，以便长期使用。

#### 验收标准

1. WHEN 首次打开 THEN System SHALL 默认隐藏：成功的例程执行、超出"最近完成"时长的工作、executor 子任务、tracked 目标；并提供"显示全部"切换。
2. WHEN 组织内容 THEN System SHALL 把"需要我"置顶并展平，其余按 bot 分组并汇总各状态数量。
3. WHEN 活动项不超过策略 `activity.cardMaxItems`（初始 8 个） THEN System SHALL 用卡片显示，超过则用表格。
4. WHEN 表达状态 THEN System SHALL 同时使用文字、图标和颜色；动画只用于"进行中"和"需要我"，并遵守减少动态效果的偏好。

### 需求 A10：移动端活动（可选）

**用户故事：** 作为所有者，我希望在手机上也能看到 bot 在做什么，以便外出时掌握。

#### 验收标准

1. WHEN 手机打开活动 THEN System SHALL 只读显示"需要我"和活动列表，复用同一接口。
2. WHEN 点击条目 THEN System SHALL 打开现有对话或详情页。

### 需求 A11：单次安排与事前准备

**用户故事。** 作为所有者，我希望在目标管理和日历看到 bot 接下来承诺做的事，并在到点时拿到结合当前情况的提醒或结果。

#### 验收标准

1. WHEN 所有者在对话中交办未来某时刻仅执行一次的事项 THEN bot SHALL 从上下文判断意图、执行时间与任务内容，并保存明确的单次安排。时间已明确时直接保存，关键时间含糊时澄清，未约定时间的事项不生成推测的日历条目。
2. WHEN 单次安排保存成功 THEN 桌面端目标管理的「即将执行」与全局日历 SHALL 默认各显示一条，以同一例程 ID 跳到同一详情，显示负责 bot、约定时间和真实状态。列表内去重，周期例程的默认可见性保持不变。单次安排保有轻量流程，无需创建契约或安排所有者验收。
3. WHEN 单次事项可从现有授权资料中获益 THEN bot SHALL 按上下文安排事前准备，即使所有者只说「提醒我」。到点交付提醒或执行结果，并在有帮助时提供事实依据、建议和待确认项。若时间不足或资料不可用，则照常提醒，并说明影响结果的资料缺口。对外操作沿用原有授权和审批。
4. WHEN 改期、暂停或取消 THEN 两处展示 SHALL 跟随同一来源更新，旧排期尚未开始的回合失效。WHEN 触发扫描重试、并发或 worker 恢复 THEN 同一次安排 SHALL 至多启动一个正式定时回合，结束后可查运行与交付结果。提醒已送达只表示 bot 完成提醒。
5. WHEN 新场景、不同数据来源或标题措辞进入同一机制 THEN System SHALL 依赖 bot 提交的结构化时间与通用指令。资料选择、准备时机、内容和建议均由 bot 推理。代码、数据模型、界面、基础提示词和工具描述统一使用通用语义，场景示例留在 `docs/`，准备提前量没有固定默认值。
6. WHEN 所有者打开尚未执行的未来单次安排 THEN 桌面详情 SHALL 提供「生成运行建议」，即使没有配置自动准备。生成过程只读，详情显示状态、事实依据、缺失信息和待确认项。已识别为单次安排的旧固定日期 Cron 复用此入口，并保留其调度定义和执行时间。

### 需求 A12：目标与任务主动巡检

**用户故事。** 作为所有者，我希望系统在目标或任务接近截止时间时主动分析当前状态，及时发现阻塞和缺失信息。

1. WHEN 目标或任务接近 `dueAt` THEN System SHALL 按巡检策略发起一次分析，分析内容包括当前状态、阻塞、缺失信息、下一步和时间风险。
2. WHEN 所有者手动执行目标或任务分析 THEN System SHALL 立即入队，并记录为当前修订的手动分析。
3. WHEN 当前修订已经执行过手动分析 THEN System SHALL 跳过该修订的自动巡检。
4. WHEN 所有者修改目标或任务的内容、契约修订或排期 THEN System SHALL 允许新修订重新进入自动巡检。
5. WHEN worker 重复扫描同一截止窗口 THEN System SHALL 对同一目标或任务的当前修订与排期最多入队一次自动分析。
6. WHEN 目标或任务已完成、取消或关闭 THEN System SHALL 停止新的自动巡检。
7. WHEN 巡检完成 THEN System SHALL 将分析结果保存在目标线程，并区分自动分析与手动分析来源。

## 需求：第二部分 现实待办项

本部分描述**通用的待办机制**。邮件、拜访、巡检等具体场景不是需求，只是用来说明机制如何被使用的示例，见需求 D 部分和 `docs/20261124-场景示例.md`。

### 需求 B1：添加待办

**用户故事：** 作为所有者，我希望随手记一件要做的事，以便不用为它建一个目标。

#### 验收标准

1. WHEN 所有者在桌面端输入一行文字 THEN System SHALL 创建状态为 `open`、执行者为所有者的待办，可选日期和标签。
2. WHEN 所有者在对话里表达了需要记录一件由自己跟进的事 THEN agent SHALL 自行判断并调用 `CreateTodo`，附上该所有者消息的引用（消息 ID，不是转述的文字）；创建可以发生在同一回合，也可以发生在多步流程的后续步骤；System 不依赖任何固定措辞，也不把它转成目标。
3. WHEN 创建待办 THEN System SHALL 不要求契约、验收或规划，也不创建目标。
4. WHEN 同一请求被重试 THEN System SHALL 通过 `clientRequestId` 保持幂等。

### 需求 B2：待办的状态与时间

**用户故事：** 作为所有者，我希望待办有清楚的状态和时间，以便知道什么时候该做什么。

#### 验收标准

1. WHEN 待办存在 THEN 状态 SHALL 属于 `suggested`、`open`、`waiting`、`done`、`dismissed` 之一。
2. WHEN 保存时间 THEN System SHALL 支持截止（`dueAt`）、预约（`scheduledAt`）、延后到（`snoozeUntil`）、跟进时间（`followUpAt`）。
3. WHEN 展示 THEN System SHALL 读时推导：待分诊、逾期、今天、本周、无日期、已延后、需跟进、等待中。
4. WHEN 所有者点完成 THEN System SHALL 记录完成时间，可附一句备注，不要求回执。
5. WHEN 待办完成或忽略 THEN System SHALL 从"需要我"移除，并在策略 `todo.restoreRetentionDays` 规定的时长内可在历史中查看和恢复。
6. WHEN 没有 `dueAt` THEN System SHALL 永不将该待办显示为逾期。

### 需求 B3：建议与分诊

**用户故事：** 作为所有者，我希望 agent 从外部内容或定时任务里识别出的事项先让我确认，以便不被误报和恶意内容左右。

#### 验收标准

1. WHEN agent 调用 `SuggestTodo`，或调用 `CreateTodo` 但所有者消息引用缺失或校验不通过 THEN System SHALL 创建 `suggested`，并在响应里说明原因；命中所有者创建的自动接受规则时见需求 B12。
2. WHEN agent 调用 `CreateTodo` 并附上所有者消息引用 THEN System SHALL 校验：该消息存在；由所有者发出（消息角色为 user，且所属运行的来源是所有者对话，而不是例程、事件、唤醒等系统合成的消息）；属于该 bot 所在的对话；在策略 `todo.ownerRef.maxAgeHours` 内；且该消息已授权的待办数未达策略 `todo.ownerRef.maxTodosPerMessage`（未设置则不限）。全部通过才创建 `open` 并保存授权消息 ID。
3. WHEN 所有者接受建议 THEN System SHALL 将其变为 `open`；延后则在指定时间前不进"需要我"；忽略则变为 `dismissed`，并记住去重键。
4. WHEN 同一去重键被重复建议 THEN System SHALL 不产生第二条而返回已有记录；已忽略的去重键不再被建议。
5. WHEN 策略 `todo.suggestionTtlDays` 已设置且建议超过该天数未处理 THEN System SHALL 自动将其过期为 `dismissed`，原因标为 `expired`；未设置则不过期。
6. WHEN 所有者批量操作 THEN System SHALL 支持一次接受或忽略多条。
7. WHEN 策略 `todo.maxPendingSuggestionsPerBot` 已设置且某 bot 的未处理建议已达上限 THEN System SHALL 拒绝新的建议并说明原因；未设置则不限。
8. WHEN 展示一条由引用授权的待办 THEN System SHALL 显示被引用的所有者消息的预览，内容由服务端按引用读取，不由 agent 转述。

### 需求 B4：来源引用与内容边界

**用户故事：** 作为所有者，我希望任何来源的事项都以同样的方式被记录和处理，以便新增一种场景不需要改代码。

#### 验收标准

1. WHEN agent 提出待办 THEN System SHALL 接受不透明的来源引用 `{ kind, id, label }`：`kind` 是 agent 给出的短字符串，System 不枚举、不解释其含义。
2. WHEN 保存 THEN System SHALL 只保存来源引用（`label` 不超过 120 字符）和 agent 概括（不超过 300 字符），不保存外部内容正文，不保存 URL。
3. WHEN 两个请求仅在来源类型和文字上不同 THEN System SHALL 走同一条校验路径，并适用同样的去重、过期和展示规则。
4. WHEN 展示建议 THEN System SHALL 显示来源标签和概括，标注"由 bot 填写"，按纯文本渲染，不提供按来源类型定制的界面或链接。

### 需求 B5：周期性与定时产生待办

**用户故事：** 作为所有者，我希望定时或周期性的事项能自动出现，以便不用自己记。

#### 验收标准

1. WHEN 需要周期性、定时或由事件触发地产生待办 THEN System SHALL 由所有者已有的例程驱动 agent 回合完成；待办本身不内置重复规则、日历展开或任何场景逻辑。
2. WHEN 例程回合产生待办 THEN System SHALL 只允许 `SuggestTodo`，并在记录里保存产生它的例程 ID（取自回合上下文，不由 agent 自述）。
3. WHEN 例程反复提出同一来源的事项 THEN System SHALL 按需求 B3.4 去重，未处理的同源待办不重复出现。

### 需求 B6：紧急度

**用户故事：** 作为所有者，我希望 agent 能表达事项的轻重缓急，以便最该看的先出现，同时不被外部内容操纵。

#### 验收标准

1. WHEN agent 提交建议或待办 THEN System SHALL 允许附带紧急度（`low`、`normal`、`high`），缺省为 `normal`。
2. WHEN 排序 THEN System SHALL 只在同一分区内先按紧急度、再按时间排序；紧急度不改变分区，也不使建议排到所有者自己的待办或收件箱步骤之前。
3. WHEN 紧急度为 `high` THEN System SHALL 仅在策略 `todo.highUrgencyNotify` 开启时触发一次打断式通知（按待办 ID 去重）；默认关闭。

### 需求 B7：等待与跟进

**用户故事：** 作为所有者，我希望等别人答复的事到时间自动回到我面前，以便不用自己记。

#### 验收标准

1. WHEN 所有者把待办标为"等待对方"并设置跟进时间 THEN 状态 SHALL 为 `waiting`；到跟进时间时 System SHALL 将其显示为"需跟进"并回到"需要我"。
2. WHEN 待办被延后 THEN System SHALL 在 `snoozeUntil` 之前不让它出现在"需要我"。
3. WHEN 所有者想让 bot 代为跟进 THEN System SHALL 通过需求 B8 完成。

### 需求 B8：交给 bot 与升级成目标

**用户故事：** 作为所有者，我希望可以把待办交给 bot 去做，或在它变复杂时升级成目标，以便灵活处理。

#### 验收标准

1. WHEN 所有者点"交给 bot"并选择 bot THEN System SHALL 以所有者身份向该 bot 的对话发送一条消息（含待办标题、备注、来源标签和所有者可编辑的指令），并把待办的执行者改为 bot，记录该消息。
2. WHEN bot 开始处理 THEN 活动视图 SHALL 通过消息 ID 关联到对应请求，待办显示其进展。
3. WHEN 对应请求完成 THEN 待办 SHALL 进入"待确认完成"，由所有者确认。
4. WHEN 所有者点"升级成目标" THEN System SHALL 打开新建目标流程并预填标题和备注；目标创建后待办标为完成并关联该目标。
5. WHEN 交给 bot THEN System SHALL 不扩大 bot 的任何权限，来源内容仍视为不可信。

### 需求 B9：晨报

**用户故事：** 作为所有者，我希望每天早上知道今天要处理什么，以便安排一天。

#### 验收标准

1. WHEN 策略 `todo.digest.enabled` 为开启 THEN System SHALL 在 `todo.digest.localTime`（所有者时区）生成晨报；默认关闭。
2. WHEN 生成内容 THEN System SHALL 只含今天到期、逾期、待分诊、需跟进的数量和最多 `todo.digest.maxTitles` 条标题，不含来源内容或 bot 概括。
3. WHEN 送达 THEN System SHALL 通过推送通知和"需要我"顶部卡片。
4. WHEN 当天没有任何事项 THEN System SHALL 不推送；同一天只发送一次。

### 需求 B10：安全与隐私

**用户故事：** 作为所有者，我希望待办功能不会成为泄露或被操纵的入口，以便放心开启。

#### 验收标准

1. WHEN 没有通过校验的所有者消息引用 THEN System SHALL 只允许产生建议（需求 B3.1、B3.2）；自动接受规则只能由所有者创建（需求 B12）。
2. WHEN 保存来源 THEN System SHALL 只保存来源引用、标签和 bot 概括，不保存外部内容正文。
3. WHEN bot 读取待办 THEN System SHALL 只返回该 bot 自己创建的，以及所有者在与该 bot 的对话中创建的。
4. WHEN 回合是例程或事件回合 THEN System SHALL 只允许调用 `SuggestTodo`，不允许创建、读取或修改其他待办。
5. WHEN 任何待办相关操作发生 THEN System SHALL 不向外部发送任何消息，对外发送仍走现有草稿审批。
6. WHEN 所有者操作 THEN System SHALL 支持一键清除某个 bot 的全部未处理建议。

### 需求 B11：移动端待办（已确认纳入首批）

**用户故事：** 作为所有者，我希望在路上也能处理待办，以便不必回到电脑前。

#### 验收标准

1. WHEN 手机打开"需要我" THEN System SHALL 显示待办和建议。
2. WHEN 在手机上操作 THEN System SHALL 支持接受、延后、忽略和完成。
3. WHEN 在手机上操作 THEN System SHALL 不提供回执上传、创建待办和管理自动接受规则。
4. WHEN 对待办开放这四个移动端写操作 THEN System SHALL 只放宽这四项（对 004.4 移动端写操作限制的例外，仅限待办），目标、决策、回执等其余移动端写操作的范围不变。

### 需求 B12：自动接受规则

**用户故事：** 作为所有者，我希望对我信任的例程或 bot 提出的建议自动接受，以便不用逐条分诊，同时不被外部内容操纵。

#### 验收标准

1. WHEN 所有者创建规则 THEN 规则 SHALL 至少包含一个来自回合上下文的字段（例程 ID 或 bot ID），可再用来源类型字符串进一步收窄；只有来源类型的规则 SHALL 被拒绝。
2. WHEN 创建、修改、删除或启停规则 THEN System SHALL 只允许所有者通过桌面端接口操作；任何 bot 工具都不得读写规则。
3. WHEN `SuggestTodo` 创建的建议命中启用的规则 THEN System SHALL 直接创建 `open`，记录 `acceptedBy = rule` 和规则 ID，界面标注"自动接受"和规则名。
4. WHEN 匹配规则 THEN System SHALL 只对回合上下文里的例程 ID 和 bot ID、以及来源类型字符串做相等比较，不解释任何内容。
5. WHEN 策略 `todo.autoAccept.maxPerRulePerDay` 已设置且某规则当天命中已达上限 THEN System SHALL 将该建议降级为普通 `suggested`；未设置则不限。
6. WHEN 所有者停用或删除规则 THEN System SHALL 只影响之后的建议，已自动接受的待办保持不变。
7. WHEN 所有者查看规则 THEN System SHALL 显示每条规则的命中次数和最近命中时间，并可对已自动接受的待办一键忽略。
8. WHEN `CreateTodo` 因引用校验失败而降级为建议 THEN 自动接受规则 SHALL 不适用。

## 需求：第三部分 时间线与日历

### 需求 C1：目标详情内的时间线

**用户故事：** 作为目标所有者，我希望在目标详情里看到任务的先后、依赖和进度，以便知道目标走到哪一步、下一步是什么。

#### 验收标准

1. WHEN 打开一个有任务的目标详情 THEN System SHALL 显示时间线，每个任务一行，含名称、负责方（bot 或人工）、状态、起止条和依赖连线。
2. WHEN 任务已开始 THEN System SHALL 用实心条表示每一段实际运行，从实际开始画到实际结束；运行中的任务画到"现在"。
3. WHEN 任务因延后有多段运行 THEN System SHALL 按运行分段绘制，段间空档不画成连续运行，并标注"延后至 X"。
4. WHEN 任务没有任何时间信息且有未完成的依赖 THEN System SHALL 把它放进"未排期"区，显示它在等待哪些任务，不编造日期。
5. WHEN 目标有截止日 THEN System SHALL 在时间线终点显示旗标，并显示"今天"线；已过截止日且未完成时突出显示。
6. WHEN 用户使用键盘或读屏软件 THEN System SHALL 提供与时间线等价的列表视图，状态同时用文字、图标和颜色表示，不只靠颜色。
7. WHEN 目标只有一个任务，或没有计划（旧数据） THEN System SHALL 仍显示该任务，不报错。
8. WHEN 服务端不返回时间字段（旧版本） THEN System SHALL 降级为只显示任务顺序和状态。

### 需求 C2：任务实际时间可见

**用户故事：** 作为目标所有者，我希望看到任务真实开始和结束的时间，以便区分"计划"和"实际发生的事"。

#### 验收标准

1. WHEN 客户端读取目标详情 THEN 每个任务视图 SHALL 包含首次开始时间、结束时间，以及最近 20 段运行的开始、结束和状态。
2. WHEN 任务从未运行 THEN 这些字段 SHALL 为空，System 不得用创建时间代替。
3. WHEN 任务被重新放行并产生新运行 THEN System SHALL 保留此前的运行分段，不覆盖首次开始时间。
4. WHEN 事件留存清理删除了旧事件 THEN 时间线 SHALL 不受影响，因为实际时间来自任务和运行记录而不是事件回放。

### 需求 C3：规划角色给任务排期

**用户故事：** 作为目标所有者，我希望规划角色在拆分任务时能指定哪些任务要等到某个时间再开始，以便把需要间隔、周期性或依赖外部日期的工作安排到合适的时候。

#### 验收标准

1. WHEN 规划角色调用 `SavePlan` 并为任务提供 `startAt`、`dueAt` 或 `estimateMinutes` THEN System SHALL 校验并保存到计划中，批准后创建任务时复制到任务。
2. WHEN `dueAt` 早于 `startAt`、估时超出范围或时间格式无效 THEN System SHALL 返回 400 `invalid_schedule`，且不保存任何内容。
3. WHEN 任务没有提供这些字段 THEN System SHALL 保持与现在完全相同的行为。
4. WHEN `startAt` 已经过去 THEN System SHALL 视为已到点，不报错，使重规划时可以原样回传。
5. WHEN 批准后 `SavePlan` 修改未开始任务的排期 THEN System SHALL 按 004.9 的差异比对规则处理（先删除待处理排队记录再重新入队）。
6. WHEN `SavePlan` 修改已开始或已结束任务的排期 THEN System SHALL 拒绝，保持原值。
7. WHEN 规划角色提示词生成 THEN 它 SHALL 包含排期指导：只在任务确实不能或不应更早开始时给 `startAt`，只在有把握时给估时，拿不准就不填。

### 需求 C4：排期任务到点才开始

**用户故事：** 作为目标所有者，我希望被排到未来的任务在到点之前不要启动，以便按我的时间安排推进。

#### 验收标准

1. WHEN bot 任务的 `scheduledAt` 晚于当前时间 THEN System SHALL 不创建执行回合，任务保持 queued，即使其依赖已完成。
2. WHEN 到点且其余条件（依赖、并发名额、契约有效）满足 THEN System SHALL 恰好放行一次；重复调度不得产生第二个回合。
3. WHEN 任务正在等待未来的 `scheduledAt` THEN System SHALL 不占用 bot 的并发名额。
4. WHEN 目标被取消、已验收，或契约被新的已批准修订取代 THEN 排期中的任务 SHALL 不再被放行。
5. WHEN 系统停机跨过 `scheduledAt` THEN System SHALL 在恢复后补放行，不丢失任务。
6. WHEN 放行时已晚于计划超过宽限时间，且任务性质为 `action` THEN System SHALL 不自动执行，而是创建一个决策，让所有者选择"现在执行"或"等我改期"。
7. WHEN 晚于宽限时间的任务性质为 `deliverable`，或没有性质（无计划回退） THEN System SHALL 照常放行。
8. WHEN 展示任务 THEN "已排期""错过计划""已延后"SHALL 由现有状态和日期读时推导，System 不得新增任务状态，也不得改变目标状态的派生规则。

### 需求 C5：运行中任务延后继续

**用户故事：** 作为目标所有者，我希望执行中的 bot 发现现在做不完时，能约定在未来某个时间继续，以便不一直占用名额，也不被误判为已完成。

#### 验收标准

1. WHEN 运行中的 bot 任务调用 `DeferWorkItem`，提供 `resumeAt` 和续做说明 THEN System SHALL 把任务转回 queued，设置排期为 `resumeAt`，保存续做说明，并结束本回合。
2. WHEN 因延后而结束的回合被结算 THEN System SHALL 不把任务标记为完成、失败或待审查。
3. WHEN 到 `resumeAt` THEN System SHALL 按需求 C4 放行，新回合带有续做说明。
4. WHEN `resumeAt` 不在未来、超过策略 `schedule.deferMaxDays`（初始 180 天），或该任务已达策略 `schedule.deferMaxCount`（初始 10 次） THEN System SHALL 拒绝并说明原因（初始值待确认，见 design.md §10.2）。
5. WHEN 调用方不是该任务当前正在运行的回合 THEN System SHALL 返回 409 `tool_context_invalid`。
6. WHEN 任务延后 THEN System SHALL 不扩大任何权限，不改变契约，也不改变任务的依赖。
7. WHEN 延后发生 THEN System SHALL 写入审计事件，时间线显示延后原因摘要。

### 需求 C6：人工任务日期

**用户故事：** 作为目标所有者，我希望目标里需要我亲自做的事有明确的日期，以便安排自己的时间。

#### 验收标准

1. WHEN `RequestHumanAction` 提供 `scheduledAt` 或 `dueAt` THEN System SHALL 保存到该人工任务。
2. WHEN 所有者在界面修改人工任务的日期 THEN System SHALL 保存并写入审计事件。
3. WHEN 人工任务有 `scheduledAt` THEN System SHALL 不因此阻塞任何流程，也不自动改变其状态。
4. WHEN 人工任务的 `dueAt` 已过且尚未提交回执 THEN 展示状态 SHALL 标为逾期（读时推导）。

### 需求 C7：目标截止日

**用户故事：** 作为目标所有者，我希望给目标设一个截止日，以便在时间线和日历里看到终点。

#### 验收标准

1. WHEN 所有者设置或修改目标的 `dueAt` THEN System SHALL 保存，且不改变契约内容哈希，不触发重新批准。
2. WHEN 目标已验收或已取消 THEN System SHALL 拒绝修改截止日。
3. WHEN 规划角色希望建议截止日 THEN System SHALL 只允许它写进计划说明，由所有者决定是否设置。
4. WHEN 目标是 tracked 目标 THEN System SHALL 同样允许设置截止日。
5. WHEN 截止日变化 THEN System SHALL 写入审计事件，记录修改者和旧值。

### 需求 C8：所有者调整排期

**用户故事：** 作为目标所有者，我希望能改动未开始任务的排期，以便计划变化时不必重新规划整个目标。

#### 验收标准

1. WHEN 所有者修改未开始的 bot 任务的 `scheduledAt`、`dueAt` 或 `estimateMinutes` THEN System SHALL 更新任务并写入审计事件，不改变契约和已批准的计划内容。
2. WHEN 任务已经开始、完成、失败或取消 THEN System SHALL 返回 409 `schedule_not_editable`。
3. WHEN 改期到当前时间之前 THEN System SHALL 视为立即可放行。
4. WHEN 同一个请求被重试 THEN System SHALL 通过 `clientRequestId` 保持幂等。
5. WHEN 因错过计划而等待所有者的任务被改期到未来 THEN System SHALL 重新进入正常排期流程，并关闭对应的未决决策。

### 需求 C9：时间保持诚实

**用户故事：** 作为目标所有者，我希望界面不要编造精确的时间，以便我能区分事实、计划和猜测。

#### 验收标准

1. WHEN 显示估算条 THEN System SHALL 使用与实际条不同的样式（虚线轮廓）并标注"估算"。
2. WHEN 任务没有 `dueAt` THEN System SHALL 永不将其显示为逾期或延期。
3. WHEN 展示目标 THEN System SHALL 不显示"预计完成日期"，不计算关键路径，不自动重排任务。
4. WHEN 数据缺失 THEN System SHALL 显示"未排期"，不推断日期。

### 需求 C10：全局日历

**用户故事：** 作为所有者，我希望在一个日历里看到哪天有什么，以便安排自己的一天。

#### 验收标准

1. WHEN 所有者打开日历 THEN System SHALL 提供日、周、月视图，默认显示今天，时区采用其时区设置。
2. WHEN 查询日期范围 THEN System SHALL 限制在 93 天内，返回条目不超过 1000 个，超出时提示缩小范围。
3. WHEN 汇总条目 THEN System SHALL 包含：目标截止日、人工任务、有排期的 bot 任务、待办项、跟进时间（请求进展和待办）、例程（过去的运行和未来的计划）。
4. WHEN 首次打开 THEN System SHALL 默认显示目标截止日、人工任务、有排期的 bot 任务、待办项、跟进时间及 A11 的单次安排，默认隐藏其余例程、已完成的 bot 任务和外部日历。
5. WHEN 点击条目 THEN System SHALL 跳转到对应的目标、任务、待办、对话或例程。
6. WHEN 拖动条目改期 THEN System SHALL 只允许所有者拥有的条目（人工任务日期、目标截止日、待办日期）和未开始的 bot 任务排期，其余不可拖。
7. WHEN 条目逾期 THEN System SHALL 突出显示，规则同需求 C9.2。
8. WHEN 展开例程的未来运行 THEN System SHALL 每个例程每次查询最多展开 100 次，并折叠成每日徽标。
9. WHEN 条目是全天条目 THEN System SHALL 按所有者时区的日期显示，不因夏令时或时区漂移。
10. WHEN 所有来源都没有数据 THEN System SHALL 显示空状态，而不是报错。

### 需求 C11：ICS 订阅

**用户故事：** 作为所有者，我希望在自己的日历应用里看到这些安排，以便不用打开 OutcomeGo 也能看到。

#### 验收标准

1. WHEN 所有者创建订阅 THEN System SHALL 生成带随机令牌的只读地址，令牌只保存哈希，订阅可命名并可选择包含的条目类型。
2. WHEN 日历应用请求订阅地址 THEN System SHALL 返回 iCalendar，范围为今天前 30 天到后 180 天；每个条目有稳定 UID 和最后修改时间；时间用 UTC，全天条目用日期；并声明建议的刷新间隔。
3. WHEN 生成内容 THEN System SHALL 默认只含标题和时间，不含描述，不含外部日历事件的任何细节，不含应用链接（除非所有者开启）。
4. WHEN 所有者撤销或轮换令牌 THEN System SHALL 使旧地址立即失效，返回 404。
5. WHEN 请求频率过高 THEN System SHALL 限流；无效令牌 SHALL 返回与不存在相同的响应。
6. WHEN 令牌出现在访问日志中 THEN System SHALL 将其脱敏。
7. WHEN 订阅内容里包含外部日历叠加的事件 THEN System SHALL 排除它们，避免把外部日历再次分发。

### 需求 C12：外部日历叠加

**用户故事：** 作为所有者，我希望在日历里同时看到自己的外部日程，以便避开冲突。

#### 验收标准

1. WHEN 所有者启用叠加并选择已连接的日历账号 THEN System SHALL 以只读方式显示外部事件，可选择只显示"忙"。
2. WHEN 叠加 THEN System SHALL 不写入、不修改外部日历，也不向任何 bot 暴露这些事件。
3. WHEN 外部日历不可用或授权失效 THEN System SHALL 降级为无叠加并提示原因，不影响其他条目。
4. WHEN 缓存外部事件 THEN System SHALL 只在内存中保留，不超过 5 分钟，不写入数据库。
5. WHEN 宿主无法在没有 bot 回合的情况下调用插件的读取工具 THEN 本需求 SHALL 保持 BLOCKED，不引入"让 bot 定时轮询日历"的替代方案。

### 需求 C13：移动端议程（可选）

**用户故事：** 作为所有者，我希望在手机上看到今天和近期要处理的安排，以便出门在外也能掌握。

#### 验收标准

1. WHEN 手机客户端打开议程 THEN System SHALL 只读列出今天起 14 天内的条目，复用需求 C10 的日程查询。
2. WHEN 在手机上显示目标 THEN System SHALL 不提供时间线甘特图。
3. WHEN 手机端条目被点击 THEN System SHALL 打开对应目标、任务或待办的现有详情页。

## 需求：第四部分 架构约束（不硬编码场景）

### 需求 D1：通用处理流水线

**用户故事：** 作为所有者，我希望待办、建议和各类任务处理都由 agent 推理完成、系统只管格式与权限，以便换一个任务场景不需要改代码。

#### 验收标准

1. WHEN 任何待办、建议、跟进或交接由触发源（所有者消息、例程、事件、唤醒）产生 THEN System SHALL 走同一条流水线：触发 → agent 回合推理 → 结构化输出（工具调用）→ 服务端校验 → 持久化 → 读时推导展示 → 所有者操作。
2. WHEN 服务端校验 THEN System SHALL 只检查格式（类型、长度、枚举、时间格式、条数）、权限（回合来源、bot 隔离）、来源（所有者消息引用）和幂等，不判断内容是否"重要""紧急"或"属于某个场景"。
3. WHEN 需要判断一件事是否要记录、紧急程度、标题与概括怎么写、何时跟进 THEN 这些 SHALL 由 agent 推理给出，并随输出一起提交。

### 需求 D2：不硬编码场景

**用户故事：** 作为所有者，我希望系统里没有写死的具体场景，以便我能按自己的工作方式使用它。

#### 验收标准

1. WHEN 代码、数据模型、提示词模板、工具描述涉及待办与建议 THEN System SHALL 不出现针对具体场景（例如邮件、拜访、巡检、客户、发件人）的分支、枚举值、字段或文案规则。
2. WHEN 需要标识来源或分组 THEN System SHALL 使用不透明字符串（来源类型、标签），服务端不枚举、不解释其含义。
3. WHEN 所有者希望处理某个具体场景 THEN System SHALL 仅通过所有者可配置的内容表达：对话指令、例程提示词、技能；这些内容不属于代码。
4. WHEN 增加一种新场景 THEN System SHALL 不需要修改代码或提示词模板。

### 需求 D3：策略数值可配置

**用户故事：** 作为所有者，我希望过期天数、宽限时间这类数值由我决定，以便按自己的节奏调整。

#### 验收标准

1. WHEN 需要业务策略数值（过期天数、保留期、宽限时间、延后次数与天数、可选的未处理建议上限、展示阈值、晨报时间） THEN System SHALL 从所有者可配置的策略设置读取，不在业务代码里写死。
2. WHEN 代码需要限制 THEN System SHALL 只保留输入输出的格式与规模上限（字段长度、数组条数、查询范围与条数、令牌长度）。
3. WHEN 策略值缺失 THEN System SHALL 使用一处集中定义的初始值，并可被所有者修改；修改后无需改代码或重新部署即生效。

### 需求 D4：场景示例只放文档

**用户故事：** 作为维护者，我希望场景只作为示例存在，以便不会把示例误当成需求去实现。

#### 验收标准

1. WHEN 需要说明某个场景如何运作 THEN System SHALL 把它写在文档里作为非规范性示例，示例不构成需求，也不随代码发布。
2. WHEN 验证待办机制 THEN System SHALL 用与场景无关的夹具测试代码路径，并用至少两种不同的示例场景走同一路径，结果一致。
3. WHEN 评审待办相关代码与提示词 THEN 评审清单 SHALL 包含"没有场景标识符、没有按来源类型的分支、没有业务策略数值的字面量"。

## 需求：第五部分 目标管理设置页

### 需求 E1：独立的目标管理设置页

**用户故事：** 作为所有者，我希望目标管理的设置集中在一页，以便不用在多处寻找。

#### 验收标准

1. WHEN 打开桌面端设置 THEN 左侧导航 SHALL 在"模型"和"语音消息"之间显示"目标管理"一页；其余页面的名称和相对顺序不变。
2. WHEN 打开该页 THEN System SHALL 按分组显示所有与目标管理相关且必要的设置（见需求 E2）。
3. WHEN 目标管理总开关关闭 THEN System SHALL 只让总开关可操作，其余分组可见但禁用，并说明开启后生效。
4. WHEN 本页上线 THEN System SHALL 移除"通用"页里原有的目标管理开关和弹窗，使每项设置只有一个可编辑入口，并在"通用"页保留一行只跳转、不可编辑的入口，点击后打开本页。
5. WHEN 深链接指向目标管理设置 THEN System SHALL 打开该页并定位到对应分组。
6. WHEN 在移动端 THEN System SHALL 不提供这一页。

### 需求 E2：页面包含的设置

**用户故事：** 作为所有者，我希望在这一页能调整目标管理相关的全部选项，以便按自己的方式使用。

#### 验收标准

1. WHEN 显示总开关 THEN System SHALL 提供"启用目标管理"（`outcomesEnabled`），并说明它同时控制待办（待办是否并入该开关待确认，见 design.md §10.2 第 7 项）。
2. WHEN 显示"规划与审查" THEN System SHALL 提供：规划 bot、规划独立模型、审查 bot、审查独立模型、环境说明（不超过 8000 字符）；原有的"bot 不可用"提示照常显示。
3. WHEN 显示"排期与延后" THEN System SHALL 提供策略 `schedule.graceMinutes`、`schedule.deferMaxCount`、`schedule.deferMaxDays`。
4. WHEN 显示"活动视图" THEN System SHALL 提供策略 `activity.recentCompletedHours`、`activity.checkOverdueMinutes`、`activity.cardMaxItems`，以及仪表盘显示方式 `activity.dashboardLayout`（并存、只显示活动、只显示目标泳道）。
5. WHEN 显示"待办" THEN System SHALL 提供策略 `todo.suggestionTtlDays`、`todo.restoreRetentionDays`、`todo.maxPendingSuggestionsPerBot`、`todo.ownerRef.maxAgeHours`、`todo.ownerRef.maxTodosPerMessage`、`todo.highUrgencyNotify`，以及晨报的 `todo.digest.enabled`、`todo.digest.localTime`、`todo.digest.maxTitles`。
6. WHEN 显示"自动接受规则" THEN System SHALL 提供规则列表（名称、例程或 bot、来源类型、启用状态、命中次数、最近命中时间）、创建、编辑、停用、删除，以及策略 `todo.autoAccept.maxPerRulePerDay`。
7. WHEN 显示"日历" THEN System SHALL 提供 ICS 订阅管理（创建、命名、选择条目类型、是否含应用链接、复制地址、撤销、轮换）和外部日历叠加（账号、日历、只显示"忙"）。
8. WHEN 某个分组对应的功能尚未上线（例如外部日历叠加在可行性验证通过之前） THEN System SHALL 不显示该分组，不留空壳。

### 需求 E3：编辑行为

**用户故事：** 作为所有者，我希望调整设置简单、可恢复，以便放心试用。

#### 验收标准

1. WHEN 修改任一设置 THEN System SHALL 即改即存（沿用现有设置页的行为），失败时显示原因并恢复原值。
2. WHEN 显示数值型策略项 THEN System SHALL 显示单位、取值范围和初始值；这些来自契约包里集中定义的元数据，界面代码里不写数值。
3. WHEN 所有者想回到初始值 THEN System SHALL 为每个策略项提供"恢复初始值"；允许"不限制"的项（未设置即不限）显示明确的"不限制"状态。
4. WHEN 输入超出范围 THEN System SHALL 在界面和服务端都拒绝，并显示允许的范围。
5. WHEN 新增界面文案 THEN System SHALL 同时提供中英文条目，并通过现有 i18n 目录检查脚本。
6. WHEN 使用键盘或读屏软件 THEN System SHALL 可完整操作本页，状态不只靠颜色表示。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 所有者有至多 200 个未结束的请求 THEN 活动视图查询 SHALL 在 500 ms（p95）内返回。
2. WHEN 一个目标有至多 20 个计划任务（`PLAN_LIMITS.maxTasks`）及其返工任务 THEN 时间线 SHALL 无需虚拟化即可流畅滚动和缩放。
3. WHEN 日程查询范围为 93 天且条目不超过 1000 个 THEN 服务端 SHALL 在 500 ms（p95）内返回。
4. WHEN 到期放行和建议过期扫描运行 THEN System SHALL 只查询已到点或已到期的记录，不扫描全部任务。

### 非功能需求 2：可靠性

1. WHEN worker 在 `scheduledAt` 前后重启或停机 THEN System SHALL 通过持久化记录恢复放行，不依赖进程内定时器。
2. WHEN 同一任务被并发放行 THEN System SHALL 通过现有任务锁和幂等记录保证只产生一个回合。
3. WHEN 夏令时切换 THEN 日历和 ICS SHALL 保持时间点正确，全天条目日期不漂移。
4. WHEN 外部日历、订阅或活动视图的某个来源失败 THEN System SHALL 只让该来源缺失，不影响目标执行和其他视图。

### 非功能需求 3：可维护性

1. WHEN 增加新的时间来源或活动来源 THEN System SHALL 通过统一的时间条目或活动项契约接入，不为每个来源新增视图逻辑。
2. WHEN 活动视图、"需要我"、时间线和日历判断展示状态 THEN System SHALL 使用同一份推导实现，不各写一套。
3. WHEN 排查问题 THEN 放行日志 SHALL 记录任务、计划时间、实际放行时间和延迟秒数；建议的创建、去重、过期 SHALL 有日志。

### 非功能需求 4：安全与隐私

1. WHEN 任务带有排期或延后 THEN System SHALL 不扩大 bot 的权限，不绕过契约批准。
2. WHEN 创建 ICS 令牌 THEN System SHALL 使用足够长的随机值，只保存哈希，并支持撤销。
3. WHEN 外部日历叠加启用 THEN System SHALL 只读，并且 bot 无任何工具能读取叠加数据。
4. WHEN 展示 bot 填写的文字 THEN System SHALL 按纯文本渲染，并标注来源于 bot。

### 非功能需求 5：国际化

1. WHEN 新增界面文案 THEN System SHALL 同时提供中英文条目，并通过现有 i18n 目录检查脚本。

### 非功能需求 6：提示词与缓存

1. WHEN 目标管理开启时生成基础提示词 THEN 总字符数 SHALL 不超过本规格实施前的数值（目标降级精简的篇幅抵消待办新增的篇幅）。
2. WHEN 新增 bot 工具 THEN 工具参数说明 SHALL 放在工具描述里按需加载，不放进基础提示词。
3. WHEN 提示词变更部署 THEN System SHALL 只产生一次前缀缓存重建，不引入每轮变化的内容。

## 成功定义

- 所有者打开活动视图，能看到每个 bot 在做什么，且 bot 不登记目标也不丢失可见性。
- 单次安排在目标管理和日历默认可见。到点提醒或汇报按上下文带上相关事实和建议。
- "需要我"是唯一的待处理入口：收件箱步骤、受阻的请求、待办、需跟进、无人跟进都在其中，且每件事只出现一次。
- 各种由人执行的事项（任意场景）都有处安放，新增一种场景不需要改代码；没有有效所有者消息引用的创建永远先是建议（所有者可对信任的例程设置自动接受规则）。
- 代码里没有场景标识符、没有按来源类型的分支、没有业务策略数值的字面量；同一条路径能承载至少两个不同的示例场景。
- 桌面端设置里有独立的"目标管理"页，位于"模型"与"语音消息"之间；所有相关设置都在其中，"通用"页只剩一行跳转入口、没有可编辑的重复项；界面里不写任何业务数值。
- 打开任一已拆分的目标，一眼能看出每个任务的先后、依赖、实际进度，以及哪些任务在等未来的某个时间。
- 排到未来的 bot 任务在到点前不启动，到点后恰好启动一次；`action` 任务错过计划不会静默执行；运行中的任务可以约定"某时间继续"且不被误判为完成。
- 所有者能在日历里看到所有来源的安排，并能订阅到自己的日历应用。
- 没有 `dueAt` 的任务永不显示逾期，界面不出现任何预测日期。
- 基础提示词总长度不超过实施前，现有目标、计划、状态派生和审批相关测试保持通过。
