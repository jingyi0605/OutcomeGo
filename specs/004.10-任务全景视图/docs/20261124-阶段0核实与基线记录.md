## 2. 任务 0.1：请求进展的续跑与来源（只读部分）

下列结论来自读代码，没有运行，没有在真实环境验证。

**唤醒回合是否开始请求追踪：** 取决于回合的 `origin`，不取决于是不是「唤醒」。

- `independentOrigins = ["routine", "outcome"]`（`request-progress.ts`）。这两种来源的回合不进入请求进展；其余所有来源（`user`、`background_revival`、`handoff_resume`、`agent` 等）逻辑上都可以成为请求根。
- 请求追踪的启动点是 `Task` 派发：`subagent/service.ts` 里两处调用 `ensureRequestForTask`（新建和继续）。`ensureRequestForTask` 在调用方回合的来源是 `outcome` 时返回 `null`，不追踪；在 `requestForRun` 里对 `routine` 同样返回 `null`。
- 例程通过 `WakeParent` 唤醒父级时，使用 `origin: "background_revival"`（`automation-results.ts`）。所以被例程唤醒的父级回合，如果再调用 `Task` 派发工作，会开始请求追踪。**这只是代码推断，没有实测。**

**续跑机制：**

- `waiting` 加 `checkAt`：`requestNextCheckAt` 持久化在 `Run` 上；`dispatchRequestChecks` 在到期时把状态转回 `working`，并通过 `enqueueWake`（`origin: "background_revival"`、`type: "request.check"`）排一个核对回合。幂等键 `request-check:<root>:<revision>`。
- 调度位置：worker 的启动恢复（`worker.ts` 630、631 行）和每分钟的 `dispatchRoutinePass`（711、712 行）都会调用 `dispatchRequestChecks` 和 `recoverRequestProgress`。运行收尾（2168 行）对 `routine / outcome / outcome_thread` 之外的来源调用 `settleRequestProgress`。
- 自愈：`settleRequestProgress` 在「状态 `working`、无存活 worker、无已记录的下一次检查」时最多 3 次提醒；第 3 次把状态改为 `blocked`、`blockSource = "runtime"`。

**对设计 §10.2 第 19 项（「必须建例程」能否放宽）的初步结论：待定。**

- 工具描述 `ReportRequestProgress` 明确写着 "No routine is needed for this request's saved check."，也就是对用户请求的 `waiting` 续跑，机制上不需要例程。
- 但基础提示词里「建议建例程」的措辞并不是「未完成请求必须建例程」。实际存在两处：`ROUTINES_SECTION` 里 "Be aggressive and proactive about routines … create a routine instead of doing the thing once, asking the user to remind you later, or trying to stay awake"；以及 `native-outcome-records` 里「通过例程执行时，先用 `TrackOutcome` 登记，目标和例程两个都建，目标在先」。设计 §3.5 说的「强制 bot 建例程」更接近前者的倾向，是**提示词倾向**，不是代码强制。
- 是否可放宽，取决于续跑在真实环境里是否可靠，这需要任务 0.1 的第 2 步（调试环境真实对话）。**该步骤尚未做，需要所有者同意。**
