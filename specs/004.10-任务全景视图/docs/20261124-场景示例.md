# 场景示例（非规范性）

日期：2026 年 11 月 24 日

关联文档：[requirements.md](../requirements.md)（需求 D 部分）· [design.md](../design.md) §2.5、§4.6

## 这份文档的地位

- **这里的内容不是需求。** 邮件、拜访、巡检、手动待办只是用来说明"通用机制如何被使用"的例子。
- **代码、数据模型、提示词、工具描述里不得出现这些场景。** 新增一种场景不需要改代码，只需要所有者写一段对话指令、例程提示词或技能。
- 这些示例的另一个用途是**验证机制足够通用**：测试里用其中任意两个，走同一条代码路径，结果必须一致（需求 D4.2）。

## 通用流水线（所有示例共用）

触发（所有者消息 / 例程的定时或事件触发 / 唤醒）→ pi agent 回合推理 → 工具调用（`CreateTodo` 或 `SuggestTodo`，带 schema）→ 服务端校验（格式、权限、来源门、幂等）→ 持久化 → 读时推导展示状态 → 所有者操作。

服务端在所有示例里做的事完全相同；差异全部来自 agent 的推理和所有者写的内容。

## 示例一：收到一件需要处理的邮件

| 环节 | 谁做 | 做了什么 |
| --- | --- | --- |
| 触发 | 所有者配置的例程 | 事件触发（005.4 的插件事件）。例程是所有者自己创建的 |
| 判断 | agent | 按例程提示词里所有者写的标准，判断这封邮件是否需要所有者处理 |
| 产出 | agent | 调用 `SuggestTodo`：标题、一句概括、紧急度、`sourceRef = { kind: "邮件", id: <线程标识>, label: "某人 · 某主题" }`、建议的日期 |
| 校验 | 服务端 | 例程回合只能 `SuggestTodo`；检查长度和格式；`dedupeKey` 去重；强制 `suggested` |
| 分诊 | 所有者 | 在"需要我"的分诊区接受、延后或忽略；如果信任这个例程，可以点"以后自动接受来自此例程的建议"，之后同一例程的建议直接成为待办（自动接受规则，只能由所有者创建） |
| 回复 | 所有者与 bot | 点"交给 bot"，bot 在对话里用现有草稿审批卡起草回复，由所有者审批后才会发送 |

所有者写的例程提示词大致意思（**这是所有者配置的内容，不属于代码**）：

> 每当有新邮件，判断是否需要我亲自处理。需要的，用待办建议提交，概括不超过一句话，紧急度按内容判断；不需要的，不要提交任何东西。

## 示例二：待拜访的客户

| 环节 | 谁做 | 做了什么 |
| --- | --- | --- |
| 触发 | 所有者 | 在对话里说"记一下，周四下午要去拜访某某" |
| 判断 | agent | 判断这是所有者明确要记录的事，提取时间 |
| 产出 | agent | 调用 `CreateTodo`：标题、`scheduledAt`、标签（自由文本），并引用所有者那条消息的 ID（不转述原话） |
| 校验 | 服务端 | 引用的消息存在、由所有者发出、属于同一对话、在有效期内，所以成为 `open`；即使创建发生在多步流程的后续步骤也一样，页面上显示服务端读出的那条所有者消息 |
| 准备 | 所有者与 bot | 点"交给 bot"，让 bot 准备资料 |
| 完成 | 所有者 | 拜访后点完成，可附一句备注 |
| 后续 | 所有者与 agent | 所有者在对话里让 agent 根据备注提出后续事项，走建议路径 |

## 示例三：周期性的系统巡检

| 环节 | 谁做 | 做了什么 |
| --- | --- | --- |
| 触发 | 所有者配置的例程 | 定时触发，例程本身已有时区和夏令时处理 |
| 执行 | agent | 巡检由例程执行，运行情况出现在活动视图，不为每次运行建待办 |
| 判断 | agent | 正常则什么都不提交；发现异常才调用 `SuggestTodo`，紧急度由 agent 声明，来源 `id` 带上本次巡检的标识 |
| 校验 | 服务端 | 同示例一：只能建议，格式校验，去重 |
| 展示 | 服务端 | 同一分区内按紧急度排序；不因紧急度高而排到所有者自己的待办之前；是否对高紧急度事项打断通知由策略 `todo.highUrgencyNotify` 决定，默认关闭 |

注意：同一类事每次要用不同的来源 `id`，否则被当作重复而不再出现。这一点写在工具描述的格式说明里，由 agent 遵守，代码不判断。

## 示例四：随手记的待办

| 环节 | 谁做 | 做了什么 |
| --- | --- | --- |
| 触发 | 所有者 | 桌面端顶部一行输入，或在对话里说一句 |
| 产出 | 所有者 / agent | 桌面端直接 `open`；对话里由 agent `CreateTodo` 并引用所有者消息 ID |
| 展示 | 服务端 | 按日期读时推导为"今天""本周""无日期" |

## 同一路径、不同场景的对照

这张表是需求 D4.2 的测试依据：四个场景在服务端走完全相同的代码路径。

| 服务端看到什么 | 示例一 | 示例二 | 示例三 | 示例四 |
| --- | --- | --- | --- | --- |
| 回合来源 | 例程 | 所有者对话 | 例程 | 桌面端或所有者对话 |
| 工具 | `SuggestTodo` | `CreateTodo` | `SuggestTodo` | 桌面端接口或 `CreateTodo` |
| `sourceRef.kind` | 一个不透明字符串 | 无 | 另一个不透明字符串 | 无 |
| 初始状态 | `suggested` | `open` | `suggested` | `open` |
| 紧急度 | agent 声明 | 缺省 | agent 声明 | 缺省 |
| 代码里的分支 | 无 | 无 | 无 | 无 |

## 测试夹具的要求

- 夹具只使用不透明的占位值（例如 `kind = "fixture-a"` 和 `kind = "fixture-b"`），不使用真实场景词。
- 至少两组夹具在来源类型、标签、标题文字上都不同，断言它们的状态、去重、过期、展示结果一致。
- 评审清单：待办相关代码、数据模型、提示词模板、工具描述中，没有场景标识符，没有按来源类型、标签或标题内容的分支，没有业务数值字面量。
