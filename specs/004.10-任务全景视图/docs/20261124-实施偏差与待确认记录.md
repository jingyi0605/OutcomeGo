# 实施偏差与待确认记录

日期：2026 年 11 月 24 日

范围：实现 Spec 004.10 的过程中，代码现实与规格不一致、或规格没有覆盖而我做了解释的地方。**这份文档会随阶段持续追加。** 需要改规格的项只记录，不擅自改规格，等所有者决定。

关联文档：[requirements.md](../requirements.md) · [design.md](../design.md) · [tasks.md](../tasks.md)

## 阶段 1

### D1-1 设计 §2.2 没有覆盖「排期时间已到、依赖仍未完成」

- **现象：** §2.2 表里，「等待依赖」要求 `scheduledAt` 为空，「排队中」要求没有未完成依赖，「已排期」要求 `scheduledAt` 在未来。一个 `queued` 任务如果排期已到点、依赖却没完成，三行都不匹配。
- **我的处理：** 归为「等待依赖」（`deriveWorkItemDisplayState`）。理由：这时真正拦住它的是依赖，而不是排期。
- **是否要改规格：** 建议在 §2.2 补一行。**待所有者确认。**

### D1-2 例程最近一次执行为 `queued`

- §2.2 的例程行只列了「运行中、失败、已跳过、已暂停」，没有说 `queued`。
- **我的处理：** 与 `running` 一起归为「运行中」，因为它表示一次执行正在进行；否则会让正在进行的执行不出现在活动视图。**待确认。**

### D1-3 例程暂停与失败、运行中的优先级

- 规格没有说一个已暂停的例程，最近一次执行失败时显示什么。
- **我的处理：** 执行状态优先（运行中、失败、已跳过），其次才是已暂停。避免暂停掩盖失败。副作用：已暂停且上次失败的例程，会一直以「失败」出现在活动里，直到有新的执行。阶段 4 做活动查询时需要决定是否对例程活动项加时间窗口。**待确认。**

### D1-4 「核对中」不写死 3 次

- §2.2 写的是 `0 < reconciliations < 3`。
- **我的处理：** 判断为 `reconciliations > 0`。上限 3 只存在于 `request-progress.ts` 的运行时逻辑，第 3 次会直接把状态改为 `blocked`，所以 `working` 且次数 ≥ 3 在正常情况下不会出现；这样推导里不复制那个数字，也不会和运行时逻辑漂移。

### D1-5 运行分段只收已开始的运行

- 设计 §5.10 说「最近 20 段运行 `{ id; startedAt; completedAt; status }`」，没有说排队中、未开始的运行算不算。
- **我的处理：** `startedAt` 为空的运行不算一段（它没有真实开始时间；用创建时间代替会违反 C2.2）。这样 `runIds`（所有运行）和 `runSegments`（已开始的运行）数量可以不同，这是预期的。

### D1-6 `scheduledAt` 在 1.3 时还不在 `WorkItemView` 上

- 任务 1.1 明确「不加任何排期字段」，`scheduledAt` 在任务 2.1 才加入契约。
- **我的处理：** 时间线用局部类型 `TimelineWorkItem = WorkItemView & { scheduledAt?: string | null }` 接收它。2.1 加字段后自动生效，无需再改时间线。
- **风险：** 在 2.1 之前，真实数据里不会有「延后至 X」。阶段 2 完成后要回归这一点。

### D1-7 时间线放在「支撑记录」折叠区内

- §5.6 没有规定在详情页的位置。我放在 `records` 区、`Execution progress` 折叠区之前，默认收起，没有改详情页首屏结构。
- 如果希望时间线更醒目（例如直接显示在首屏），需要所有者决定，那会改动详情页的主结构。

### D1-8 延后的未来时间只作文字标注

- 轴只覆盖已发生的时间（最早开始到现在），延后的恢复时间用文字写在行尾，不按时间画到轴上，避免暗示预测。阶段 3 做计划条时再决定是否把未来排期画上去。

## 阶段 2

### D2-1 策略字段的取值范围由我定

- 设计 §2.6 的表只给了初始值，没有给范围。`TASK_POLICY_FIELDS` 里每个整数键的 `min`/`max` 是我定的**格式与规模上限**，只用来挡明显错误的输入，不表达业务偏好（例如宽限时间 0 至 10080 分钟，延后天数 1 至 3650 天）。所有者可调整。**待确认。**

### D2-2 策略按点分键扁平存储

- 设计只说「按键合并」。我把 `taskPolicy` 存成 `{"schedule.graceMinutes": 60, …}` 的扁平 JSON，而不是嵌套对象，这样一个键一个值，合并和删键（恢复初始值）可以用一条 JSONB 语句原子完成。

### D2-3 迁移不能从空库重放

- 仓库的第一个迁移（`202611070001`）只建了 2 张表，没有完整基线，也没有 `migration_lock.toml`。新库靠 `db push` 一次建全，迁移文件只用于升级已有的库。所以「空库重放全部迁移」的验证做不了，我改为「把库退回升级前的形状，塞数据，再执行迁移文件」。

### D2-4 `featureSettingsView` 总是返回 `taskPolicy`

- 没有任何覆盖值时返回空对象 `{}`，而不是省略字段。对旧客户端无影响（多出的字段会被忽略）；新客户端靠它判断「没有覆盖」。

### D2-5 `plansEqual`、`normalizePlanTask` 原先逐字段枚举（规格没提）

- 设计 §5.1 只说「校验并保存」，没有提到这两处是逐字段拷贝/比较。不改的话，排期字段会在保存前被丢掉，只改排期的保存会被当成「计划没变」而抛 `plan_unchanged`。我已改，并用测试固定（「只改排期不是 plan_unchanged」「同一时刻不同写法算相同」）。

### D2-6 2.2 必须与 2.3 一起发布

- 在到点闸口实现前，消息层不读取 `scheduledAt`，未来的 `startAt` 不会推迟任务启动。发布顺序上这两个任务不可拆开。

### D2-7 锁定任务的排期比较以任务行为准

- 设计 §5.1 第 5 步说「已开始或已结束的任务保持原值，若请求试图修改则整体拒绝」，没说「原值」是计划 JSON 里的还是任务行里的。我取任务行：所有者在任务 2.6 之后可以单独改排期而不回写计划（待确认项 14），行才是实际生效的值。副作用：重规划原样回传「旧计划里的排期」，在所有者改过期之后会被当成修改而拒绝（`plan_task_locked`）。**这与待确认项 14「改期不回写计划，重规划比对时保留所有者的修改」直接相关，需要所有者在做 2.6 时一起确认。**

### D2-8 `enqueueOutcomeTurn` 里取的是进程时钟，扫描 SQL 用的是数据库时钟

- 设计 §5.2 没规定谁的时钟。闸口用进程的 `new Date()`（与该函数其他代码一致，且要写入日志），扫描 SQL 用数据库 `now()`。两者有偏差时，最坏情况是闸口多拦一轮（下一轮分钟级扫描再放行）或扫描多选了一条被闸口再次拦下的任务，**不会重复放行也不会丢任务**。如果部署环境时钟偏差大，延迟会等于偏差。

### D2-9 把「闸口在容量检查之前」落成可测的行为

- 设计说闸口放在容量检查之前「使排期任务不占并发名额」。读代码后发现容量检查只是对**其他**任务的只读计数，排期任务本来就不会被计入，所以闸口挪到后面，名额数也不变。真正的区别是容量检查前那把 bot 级咨询锁：闸口在后面，每个排期任务的每次放行尝试都会去争这把锁，与同 bot 其他放行串行。所以我测的是「未到点任务不会等待这把锁」（持锁后调用，设 `lock_timeout`），这才是能把「闸口位置」守住的断言；单纯断言「名额没被占」守不住它（我第一次的变异检查证明了这点）。

### D2-10 测试夹具必须走真实的开始意图写入路径

- 手写一条 `requestHash: "fixture"` 的 `processing` 记录，会让放行时抛 `idempotency_conflict`（哈希对不上），夹具看起来正常、放行却失败。所以夹具都先调用一次 `enqueueOutcomeTurn`（任务那时还没到点，被闸口拦下并写下记录），再把时间改到过去。我最初的 worker 夹具和 messaging 里「100 个未到点任务」的夹具都是手写记录：前者放行时抛了 `idempotency_conflict`，后者看似通过却因此没有约束力（去掉 SQL 排除条件后仍然全绿），两处都已改成走真实路径，并用变异检查重新确认能检出。
