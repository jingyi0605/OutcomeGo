# 外部日历叠加验证结论

日期为 2026 年 11 月 25 日。对应 [任务 8.3](../tasks.md)、[需求 C12](../requirements.md) 和[设计 §5.9](../design.md)。

## 结论

代码路径可行。宿主可以在没有 bot 回合的情况下调用已选账号的 `list_calendars` 和 `list_events`。真实 OAuth 登录、远端运行时和授权撤销仍待测试账号验收，8.3 保持 `IN_REVIEW`。

## 本地证据

- `apps/server/src/services/plugin-service.ts` 的 `callHostTool` 直接委托 `PluginTransport.callHostTool`。`apps/server/src/services/plugin/transport.ts` 的 stdio 分支以连接 ID 准备独立的运行配置，再调用 `/v1/mcp/connections/:id/call`。该路径无需 `runId`、`botId`、对话或 `PluginInvocation`。它也没有为 stdio 工具实施读取权限筛选，因此叠加入口应固定允许 `list_calendars` 与 `list_events` 两个工具。
- 在隔离 PostgreSQL 库中建立两个带不同 `alias` 的测试连接，调用真实 `PluginTransport.callHostTool` 和 `calendarTools`，以进程内桩替换 computer 和 Google HTTP。断言两个连接分别使用各自的 `OUTCOMEGO_PLUGIN_ACCOUNT_ID`，`list_calendars` 和带明确日历 ID、时间范围的 `list_events` 都发出 GET。模拟 HTTP 401 产生要求重新授权的 MCP 错误结果。整个验证没有创建 bot 回合。
- 账号与日历是两级标识。连接由 `(installationId, connectorKey, alias)` 唯一识别，应用应保存连接 ID 与该连接返回的日历 ID。插件使用相同连接的 OAuth 状态和独立运行环境。`list_events` 接受明确的 `calendarId`，省略时使用所选账号的 `primary`。真实授权失效可能表现为刷新失败后的 `needs_auth`，或刷新前收到的 `isError` 及 401 提示。403 还可能表示范围或日历 ACL 不足。
- `packages/plugins/google-calendar/plugin.json` 声明的凭据也适用于现有写入功能。只读边界需要由宿主入口的固定工具列表保证。调用结果仅供已鉴权的所有者视图消费。只显示忙时应在返回视图结果前丢弃标题等细节。

## 待所有者批准的第三方验证

授权范围是测试环境、一个专用 Google Calendar 账号和该账号内一份只含合成事件的日历。需允许测试环境登录 Google OAuth、经已部署 computer 向 Google Calendar API 发起读取，以及对该专用测试连接撤销授权。通过现有插件设置绑定账号，使用其连接 ID 调用宿主 `list_calendars`，再使用列表返回的日历 ID 及覆盖合成事件的窄时段调用 `list_events`。核对返回事件、连接 ID 及无 bot 回合。撤销测试连接的 Google 授权后重复读取，确认获得可提示重新连接的错误，并检查其他日程来源仍可查询。真实 Google 请求和撤销授权均未执行。
