## 0. 使用方法（给所有者）

1. 分三批启动。每批的开始条件写在各会话的「开始条件」里，条件没满足就不要启动。

| 批次 | 会话 | 开始条件 |
| --- | --- | --- |

| 第 3 批 | F 日历界面、H 移动端 | F：E 的 7.1 已合并。H：C、D 的待办接口与界面已合并 |

2. 每个会话完成后，把它的汇报贴回复核会话。复核会话读代码、重跑测试后再合并，不以会话自述为准。
3. 阶段 0（0.1 到 0.4）要在调试环境发起真实对话，不在这 8 个会话里，由你和复核会话另行安排。

### 1.3 硬性约束（来自规格，违反就是返工）

架构约束（需求 D，最重要）：
- 一切由 pi agent 推理，服务端只校验格式、权限、来源和幂等。代码、数据模型、提示词、工具描述里不得出现具体场景（邮件、拜访、巡检、客户、发件人等）的标识符，也不得按来源类型、标签、标题内容分支。来源引用 `{kind,id,label}` 对服务端是不透明字符串。
- 业务数值不写进代码，也不写进界面：全部走策略设置 `taskPolicy`，集中定义在 `packages/contracts/src/task-policy.ts` 的 `TASK_POLICY_FIELDS` 元数据（服务端校验与设置页渲染共用）。代码里只允许保留格式与规模上限。
- 测试用与场景无关的占位夹具，且至少两组不同夹具走同一路径、结果一致。

其他：
- 展示状态读时推导，不存储；不新增任务状态；不改 `recomputeOutcomeStatus` 与目标状态派生。
- 排期、延后、待办都不得扩大 bot 权限；`TrackOutcome`/`CloseOutcome` 的输入输出保持兼容。
- 基础提示词总长度不得超过阶段 0 基线：「目标管理开启（默认参数）」27,328 字符，同时「开启 + 规划角色」27,545、「开启 + 直接文本回复」25,797 也不得变长（测量方式见 `docs/20261124-阶段0核实与基线记录.md` 第 3 节）。参数说明放工具描述里，提示词和工具描述不用具体场景举例。
- 仓库规则：技术文档用中文并带日期文件名；代码标识符、注释、文档字符串用英文；提交信息用中文，只用「前端：」「修复：」「IOS：」三种前缀（新增功能用「前端：」，缺陷修复用「修复：」，iOS 客户端改动用「IOS：」），提交署名按你会话自身的规则；不要对已有文件执行格式化（`biome format --write` 会造成无关改动）；界面文案同时给中英文。

### 1.5 工作方式

每个任务：读它的「开始前先看」→ 先写验证项里的测试 → 实现 → 做变异检查（临时破坏守卫，确认对应测试会变红，再还原）→ 跑相关测试与类型检查 → 回写 `tasks.md`（状态改 DONE 才能勾选 `[x]`；没在真实环境验证过的写 IN_REVIEW 并写清「没有验证」的项；BLOCKED/CANCELLED 写原因）→ 提交到自己的分支（一个逻辑单元一个提交）。不做任务「先不做什么」里列出的事，不做无关重构。

命令：根目录 `bun run typecheck`、`bun run check:architecture`、`bun run check:i18n`；单包 `bun test --pass-with-no-tests`（`apps/desktop` 用 `bun test --pass-with-no-tests --isolate`）。开始前在未改动的基线上跑一遍相关包，记录既有失败，之后只对比新增失败。`check:architecture` 当前会因上面那批 i18n 缺项失败，这是既有的。

### 1.6 必须先问所有者的事

重建或同步远端 computer；在调试环境发起真实对话；对共享数据库做破坏性操作；push、合并分支进 OutcomeGo、发布；规格与代码现实冲突需要改规格时。

### 1.7 汇报格式

每个会话结束时汇报：完成的任务编号和提交号；运行了哪些命令及结果（失败的原样贴出，不要说成通过）；每个新增测试做了哪些变异检查；与规格的偏差和原因；新发现的风险；改了哪些不在你名下的文件；分支落后 OutcomeGo 多少个提交（`git rev-list --left-right --count OutcomeGo...HEAD`）；没验证过的项；需要所有者决定的事。没验证过的就说没验证。
