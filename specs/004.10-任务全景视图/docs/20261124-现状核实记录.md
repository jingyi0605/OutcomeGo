## 5. 未核实项

- **请求进展的续跑是否可靠、bot 对 `ReportRequestProgress` 的遵从度**：只读了代码，没有实测。任务 0.1、0.2 专门验证。
- **由例程唤醒的回合（`background_revival` 来源）能否使用请求进展**：`independentOrigins` 只排除 `routine` 和 `outcome`，所以从逻辑上可以，但没有验证。
- **全局查询 `requestProgress` 非空行是否需要部分索引**：只确认了现有索引只覆盖 `requestNextCheckAt`。
- **所有者身份模型**：`User` 模型存在，`TodoItem.ownerId` 与现有所有者和 bot 归属如何对应，实施前需核对。
- **所有者向 bot 发消息的现有服务路径**：设计 §4.8 假定存在，没有定位具体函数。
- **agent 能否在上下文里拿到触发消息 ID，以及 `ReadTranscript` 结果是否带每条消息的 ID**：请求进展的对账提示里出现过 `Original message: <消息 ID>`，说明消息 ID 对 agent 可见，但上下文里的触发消息和 `ReadTranscript` 是否都提供，没有核实。所有者消息引用依赖它。
- **所有者消息的判定在多人或群聊对话里是否成立**：当前按单一所有者设计，没有核实群聊场景。
- **`google-calendar` 的事件能否作为 `plugin` 触发器来源**：005.4 只证明了"宿主调用插件声明的轮询工具"。任务 6.6 和 8.3 专门验证。

## 6. 设计依据（外部项目，已读来源）

这些项目大多围绕编程任务，只借鉴通用思路，不照搬：

- **展示状态读时推导，不存储**：Agent Orchestrator 的架构文档把"观察外部事实、更新持久事实、推导展示状态"作为核心，并写明"展示状态永不存储"。对应 §2.2 和属性 6。
  来源：<https://github.com/OrchestratorInc/agent-orchestrator/blob/main/docs/architecture.md>
- **展示状态与存储状态分开**：Paperclip 的产品定义里，agent 的任务只在有运行排队或进行中时才显示"进行中"，执行结束后按情况显示"受阻""待评审""监控中"或"待办"，存储的生命周期状态仍控制执行和恢复；"监控中"的任务显示下次检查时间。支持不新增任务状态。
  来源：<https://github.com/paperclipai/paperclip/blob/master/doc/PRODUCT.md>
- **agent 创建的任务默认不进入任务列表**：同一份文档里，agent 创建和系统创建的任务默认隐藏，"我的任务"里默认不含渠道任务、例程任务和 agent 创建的任务，需勾选才显示。对应 A9 的默认隐藏和"目标降级"的取向。
- **任务看门狗**：Paperclip 的 Task Watchdog 只在整棵任务树都停下且没有任何存活的后续路径时才唤醒，用停止状态的指纹避免重复提醒，核实型而非执行型。本规格选择更简单的做法，只呈现请求进展已有的自愈结果，不新增看门狗。
  来源：<https://github.com/paperclipai/paperclip/blob/master/doc/TASK-WATCHDOG.md>
- **多 agent 视图的信息优先级与密度**：Orca 的研究文档建议每个 agent 先展示状态，其次原因、在做什么、最后活动、耗时；状态用颜色、图标和文字并用；动画只用于需要关注的状态，并遵守减少动态效果的偏好；通知分级（等待和出错打断，完成提示，进行中静默）；数量少时用卡片，多时用表格。对应 A5、A9 和时间线的状态表达。

- **自动处理优先，重试若干次后才升级给人**：Agent Orchestrator 的 CI 失败自动回给负责的 agent，重试 2 次后才升级通知。对应"无人跟进"只呈现自愈结果。
