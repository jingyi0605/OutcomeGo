## 2. 工具和数据流

新增 `packages/contracts/src/outcome-chat.ts`，共享 14 个工具的输入 Schema、说明和 JSON Schema：

- 规划：`PlanOutcome`、`GetOutcomePlan`。
- 目标：`CreateOutcome`、`ListOutcomes`、`GetOutcome`、`ReviseOutcome`、`StartOutcome`、`CancelOutcome`。
- 注意事项：`ListOutcomeInbox`。
- 探索：`ListExploreIdeas`、`GetExploreIdea`、`CreateExploreIdea`、`ProposeExploreIdea`、`DiscardExploreIdea`。

普通主 Bot 从现有 `cursor` 动态工具目录发现这些工具；直接工具列表不增加 14 个常驻定义。服务端仍先验证当前 Run 的 Bot、conversation、channel、delivery 和运行状态，再由新增 `OutcomeChatTools` 调用既有 Planning、Outcome、Inbox 和 Explore 服务。默认规划/探索 Bot 和审计主体来自持久化 Run，不从模型输入读取。后台 Routine、Outcome 子线程和委派 Bot 的管理入口被拒绝；已有 `RequestOutcomeDecision` 和 `RequestHumanAction` 保持原限制。

`ListOutcomes` 增加可选 `query`，按标题/描述不区分大小写搜索，可与状态及 cursor 同时使用。原接口不传 query 时保持原形状和默认分页。`GetOutcome` 可另读真实历史 revision 和指定 WorkItem 的分页 transcript。所有写操作复用既有幂等键、事务、状态转换、revision 冲突检查和事件，不新增数据库模型或独立状态机。

新增服务适配器通过 `Effect.either` 保留实际 `ApiError`，避免把过期编辑、未批准启动、Explore 终态等业务错误包装成通用内部错误。

## 3. 用户确认与使用方式

典型流程：

1. 用户描述目标，Bot 调用 `PlanOutcome`，返回实际三维候选项和 planId。
2. Bot 使用返回的选项 ID 或用户自定义文字调用 `CreateOutcome`。这只是建议草案，返回真实 Outcome ID、`pending_approval` 和应用详情链接，不启动执行。
3. 用户可在聊天中要求修改；Bot 读取当前 revision 后用 `ReviseOutcome` 提议完整的新契约。
4. 用户通过现有 Desktop 契约确认界面批准实际内容。聊天回复或模型生成的 widget 不替代该记录。
5. 用户明确要求开始时，`StartOutcome` 检查确切 `expectedRevision` 已批准，再创建独立 Outcome WorkItem/Run。重复同一请求不会再开一个初始任务。
6. 用户之后可询问状态、结果、历史或注意事项；Bot 读取服务端事实。取消使用既有取消服务并保留历史。

未注册代替用户批准、Review PASS、人工回执或任意状态写入工具。Android/iOS 普通聊天可以表达同样的意图；未新增移动端原生规划/批准/验收表单。外部工具仅在用户明确指定该存储系统时使用，TodoWrite 和请求进度不冒充原生 Outcome。
