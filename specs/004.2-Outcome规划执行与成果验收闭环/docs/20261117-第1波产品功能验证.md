### 豁免的确定性规则

对应需求 9.4、design §25、父 D03/D07：当前请求没有 waiver ID，不能信任客户端提交一个“已批准”标记。

- 当前仍为 required 的条款不能直接提交 `WAIVED_BY_APPROVED_CHANGE`。
- 当前为 optional 时，只有当前 revision 已批准、有同一 Outcome 的已批准 base revision、原条款确为 required、当前/base 中该文字都唯一且 ordinal/verificationMethod 相同、变更摘要明确包含该条款文字，才记录批准变更豁免。
- 原本就是 optional、未批准或无 base、缺少明确变更摘要、重复文字导致身份不确定，均拒绝，返回 `review_incomplete`。
- 测试覆盖唯一、已批准的真实变更，以及 required/原本 optional/重复文字的拒绝；不增加 DTO 或 schema 字段。

## 持久事件消费与跨线交接

本线选择订阅持久 `outcome.output.recorded`，不在 Worker 中导入 Server：

1. `OutcomeEvidenceConsumer.start()` 在 Server 启动后扫描持久 Event 积压；正常运行用已有 `EventWakeup` 唤醒，并定期回退查询。
2. Output 候选按 outputId 事务幂等；预审按 workItemId 事务幂等；消费记录使用冻结的 `outcome-event:<handler>` scope。查询用 `NOT EXISTS` 选取没有持久回执的相关事件，sequence 只用于分页顺序，不能作为已提交水位。
3. 生成 Evidence 与推理相互独立，推理在事务外；原 revision 在模型调用期间被替换时，Evidence 仍绑定实际执行的原 revision，不迁移到新 revision。
4. `stop()` 取消等待和推理信号，等待循环退出后才断开 Prisma；重启从没有消费回执的持久事件继续，重复投递不会重复候选。
5. 另读 `outcome.work_item.updated(to=completed)` 触发预审，不写新的事件主题或状态。
6. 审查确认 sequence 在事务提交前分配，旧的高水位实现会漏掉晚提交事件。确定性测试固定事务 A 先分配低 sequence 后等待、事务 B 分配高 sequence 并先提交：旧代码在 A 提交后仍产生 0 条候选（应为 2），修复后生成 2 条且再次读取为 0 项待消费。消费是否完成只由持久回执判断。
7. Consumer 与 SnapshotService 使用 `pendingOutcomeEvidenceEventSql`（固定 SQL 别名 `event`）和 `OUTCOME_EVIDENCE_EVENT_SCOPE="outcome-event:output-evidence"`，精确覆盖 Output 与 completed WorkItem 事件。回执 key 为 envelope `eventId`，无该字段时为 `sequence` 字符串。回执只在业务 handler 完成且未取消后写入；handler 异常不能提前确认。
8. 真实数据库回归在两个待消费事件之后写入 100000 个无关事件，然后实际调用 `SnapshotService.pruneEvents()`：旧实现删除 Output 输入，断言失败；消费已接纳 helper/prune 后输入保留。最终用例再注入 handler 异常，确认两种身份都没有回执且第二次 prune 仍保留；重试生成两条 Output Evidence、再次 drain 为 0，随后 prune 删除已完成事件。未模拟 SnapshotService，也未关闭全局清理。

### 同键并发幂等回归

对应需求 7.4：仅事务外乐观读不足以保护同 key 的并发批准或修订。测试用屏障强制两个请求都先读到“无回执”，原实现的后到请求会在可变状态校验处失败；`410ca8976` 在事务内取得 scope/key 锁并重读回执后才执行业务逻辑。批准和修订两个确定性回归从失败转为通过，逐字段返回同一响应，批准事件只有一条、revision 只增加一次；原不同 key 冲突和回滚测试继续通过。

### 跨线验收阻断

design §25 禁止仍有有效 open Decision/HumanAction 时接受成果。该整合修复由 integrator `d5008544b` 独占，涵盖同 Outcome 锁内当前 revision、未过期 open/presented Decision 和未关闭 HumanAction。集成人员报告真实独立 Decision 用例修复前 2 失败、修复后 4 通过及组合检查通过；本线最终 48 项没有冒充独立复核此整合 guard。组合验收应包含该提交，本线独立服务分支不代表已包含全部跨线 schema/装配/阻断逻辑。

`outcome.review.required`：运行组首次完成由线 1 结算器产生；本线 Review 未达到接受条件时产生，payload 为 `{criterionIds,workItemIds}`。

`outcome.accepted`：本线 `/reviews` 在同一事务内写 `acceptedAt`、`{revisionId,reviewIds}` 事件并调用 `recomputeOutcomeStatus`。事件代码从 `a909e2d43` 可用，真实自动结算入口需要线 1 的实现合入。

### 给线 1 / 集成人员

- `OutcomeService.startRun(outcomeId,input,actor)`、`transcript(outcomeId,workItemId,query?)` 由线 1 提供，路由文件仅本线拥有。
- 合并后的装配应为 `new OutcomeService(prisma,messaging,runs,withdrawSupersededDecisions)`，`runs` 必须是 `RunService`，不能替换成会影响同 Bot 其他工作的停止入口。
- 本线独立编译时 app-service 仅传 prisma，运行时可选端口未实现时明确返回不可用。真实执行/取消/只读 transcript 联调由整合后的代码验证，不能把替身结果写成真实 Run 通过。
- 最终交接时负责人确认集成分支已装配真实取消和路由 transcript；该组合检查由集成记录独立保存。本线没有在独立分支启动 live API 或浏览器补录，外部验收继续保持 PENDING，不把接口已装配等同于本线已执行真实端到端回放。

### 给线 3

- `createRevisionInTransaction(tx,outcomeId,input:CreateContractRevisionInput,actor):Promise<OutcomeDetail>` 为绑定方法，调用方拥有事务与幂等。
- 普通 `createRevision` 复用同一实现，禁止嵌套调用开启新事务的方法。
- `onRevisionCreated` 回调在 currentRevision 切换后、同一事务内执行；结合线 1 构造参数后放在第四位。集成人员应注入线 3 独立 helper `withdrawSupersededDecisions`；本线不复制 Decision 撤回规则。
- `getInTransaction(tx,outcomeId)` 仅做同一事务内的详情读回。

### 给线 4：唯一验收入口

使用 `POST /api/v0/outcomes/:id/reviews`，请求沿用 `SubmitOutcomeReviewInput`：`expectedRevision`、逐条 `criterionId/result/evidenceIds/comment/userConfirmed?`、可选 `newEvidence`、`clientRequestId`。

- 人工回执先保存当前 revision、criterionId、workItemId 和 `credibility=human_confirmed` 的 Evidence，再把其真实 ID 提交到本入口。
- 本线在 Review 事务内对 `submitted`/`review_pending` 人工 WorkItem 使用 `transitionWorkItem` 进入 `accepted` 或 `rejected`；没有关联证据或条款仍未确认时不自动接受。
- 线 4 第 2 波还须完成回执完整性校验，以及人工接受后原 `waiting_human` Agent 子线程的同事务续跑；本次没有实现该第二入口或提前调用未完成工具。

### 给移动端

响应没有额外外壳：列表为 `OutcomeListPage`，详情为 `OutcomeDetail`；日期 ISO 字符串。无 DTO 字段变化，错误仍为 `{error:{code,message,details}}`。
