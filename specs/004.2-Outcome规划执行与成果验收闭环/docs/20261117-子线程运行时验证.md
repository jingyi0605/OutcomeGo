## 3. 实现与调用约定

- `WakeInput.outcomeWorkItemId` 同时进入 Run 和 InboxEvent；origin 为 `outcome`。上下文 scope 为 `outcome`、scopeId 为 WorkItem ID，租约为 `outcome:<workItemId>`；Outcome 容量 2 与 Routine 容量 4 分开。Outcome 与主对话都不通过对方的中断路径。
- `computerUse` 在 worker claim 的 `computer-screen:<parentBotId>` 锁下检查有效子线程租约。Outcome 竞争父 Bot 桌面时串行，既有普通线程之间行为不变；没有新增锁表。
- 入队只复用 `enqueueWake`；根 clientId 为 `outcome-run:<outcomeId>:<revision>:<workItemId>`，续跑 ID 必须稳定且包含原因和序号。初始项领取时才进入 running；临时不可运行进入 retry_pending，永久不可运行进入 failed。
- 容量等待意图复用 `IdempotencyRecord`，scope 为 `outcome-turn:<workItemId>`；processing 保存 `{input}`，同一事务成功入队后 completed 保存 Run 结果。原有事实表保存状态，不复制一份 WorkItem 状态。写入 30 天 `expiresAt`，没有新增自动清理器；待消费意图不能按 TTL 静默删除。重放和 drain 当前均不检查到期时间。
- `dispatchQueuedOutcomeWorkItems` 先限制为有 processing 意图的项，再取前 100；跨 Outcome try-lock 保持 Outcome → WorkItem 顺序。周期恢复按 ID 轮转扫描，避免只回看前 100 个完成项。
- `settleOutcomeWorkItem(tx,runId,runtime?)` 的第三参数为 `{messaging,workspaceRoot?}`。两参数只结算持久化事实；生产的三个调用点是 worker `execute`、`fail`、`recoverOutcomeWorkItems`，全部显式注入 runtime；没有其他生产调用方。文件扫描和下一项派发需要 runtime；周期恢复可补齐两参数结算留下的文件/派发工作。
- 结算与 shell/子 Agent 续跑路由共用 Outcome → WorkItem 锁；路由验证、回执/完成事实和续跑 Run 保持在调用方同一个事务内提交。已有子任务/后台命令或 queued/running Run 时不完成；waiting_decision/waiting_human 不覆盖。最终 Run 按 startedAt 优先选实际最后执行项，排除被合并的回执。
- 最终 assistant 结果与 Routine 使用相同来源；文件只枚举 `outcomes/<outcomeId>/<workItemId>/` 下的普通文件。Output 的 `final:<workItemId>` / `file:<workItemId>:<path>` 去重和事件同事务。失败/取消/中断分别映射 failed/cancelled/needs_review。
- Outcome 不拥有主请求进度，不产生主请求 `request.check` 或普通请求恢复。真实 `SubagentService.task` 派发测试覆盖这条路径；不是只手工插入 Subagent。
- Outcome `WakeParent` 将当前 WorkItem 置 needs_review，当前 Run ID 的 `AutomationResult` 保存终止移交 marker，等待主对话空闲，不打断。显式 recovery 恢复同一 WorkItem；旧 marker 继续挡住旧回调。返回既有 `{woken,run_id,automation_run_ids}`。
- `OutcomeService(prisma,messaging?,runService?,onRevisionCreated?)` 保留第四位置 hook；cancel 在 cancelledAt 后于同一事务调用 hook。`startRun(outcomeId,input,actor)` 返回 OutcomeDetail；`transcript(outcomeId,workItemId,{before?,limit?}?)` 返回 `{total,next_before,note,rows}`。读取只使用持久化投影和既有脱敏，不暴露 reasoning、promptFingerprint 或完整私有工具载荷。
- cancel 先提交取消事实，再在事务外停止精确运行组；重复同一取消请求会再次尝试未完成的物理停止。`RunService.cancelOutcomeWorkItems` 本身也拥有目标项事实栅栏：按 Outcome → WorkItem 锁序，只把传入的未终态 Agent 项置 cancelled 并重算；既有终态保持、重复无额外转换、不写整个 Outcome.cancelledAt。在根 Run 已完成或没有 rootRunId 的情况下，直接 Stop 仍先封住回调/drain；兄弟项继续运行。新 API 为 `POST /v1/bots/:id/background-shells/stop-runs`，body `{runIds:string[]}`，response `{stopped,runIds}`。旧 `/background-shells/stop` 无 body 行为不变。
- 子 Agent 归属在同一个 parent lifecycle 锁和子行锁下重新读取与预留，停止当前属于该组的绑定及尝试，再释放锁进行外部取消。运行 ID 来自不可变 `SubagentAttempt.parentRunId`、原始 initial/resume/continuation Inbox 身份及持久化 steering scopeUpdates；不查询整个 child Bot 的全部 Run。即使 child 已重绑定，也能发现旧尝试并重试精确停止。新绑定/新 Run/新命令/新租约不在取消快照内。
- 新旧父 Bot 和 child Bot 都只调用 run-scoped shell 停止；旧 computer 404、运输失败或不确认返回 `503 outcome_stop_incomplete`、`retryable:true`，不降级到 Bot-wide stop。只清理属于快照且已经终态的租约。
- 当前生产 `Task` 明确拒绝嵌套子 Agent（`subagent/service.ts` 的 `nested_subagent_forbidden`），但取消仍按已访问集合穷尽历史图，没有保留任意 4 层上限。6 层持久化历史链和重复取消都验证通过。
