## 1. 实现

- `OutcomeChatCards` 沿用真实 `sendVisible` 的生命周期/渠道/分支检查，以富消息 metadata 和原位更新事件发布卡片，无 schema 变化。规划调用实际经过分析和生成，在推理屏障后才显示建议就绪；保存目标后根据服务返回的实际目标 ID 和状态显示待批准、待启动、执行、需要处理、待验收、已验收、取消或失败。
- 完全相同的工具输入复用卡片 client ID；服务器串行锁定卡片更新，晚到的进行中更新不能覆盖已完成阶段。分析/生成不产生逐阶段推送；既有 Bot 最终消息路径保留。服务器操作失败会留下失败卡片，非法参数不创建伪进度。
- Desktop 卡片默认仅显示摘要、当前阶段、下一步和打开目标入口。规划建议与成果正文主动展开；显示成果不能推断为最终用户验收。带目标 ID 的卡片使用既有只读 API 读取当前事实；网络错误明确显示保存快照及重试，长时间未确认的生成停止活动动画并提示核对。
- 分析呼吸、生成扫描、执行旋转、就绪/成果短暂入场均使用主题 token；`prefers-reduced-motion: reduce` 禁用卡片动画和过渡，状态文字始终存在。新文案沿用 English source key/中文 catalog，使用系统语言选择。
- 详情第一层显示目标、友好状态、简短概览、当前动作及实际存在的成果/计数；空执行/成果/证据分区不展示。背景、完整契约、执行、成果、证据、验收、历史和诊断按需展开，运行 ID/来源进一步折叠。结果卡正文按需展开。
- 批准按钮只在用户打开完整契约后出现，完整目标/验收标准/范围边界仍可逐条审阅。新 revision 清除旧确认并要求重新打开审阅。首次打开后保持表单挂载，折叠不会丢弃输入或验收选择。历史回执继续读取实际原 revision，不能用待批准的新 revision 替换。
- 平台提示和目标工具返回的 nextStep 要求用卡片承载完整记录，补充文字仅保留摘要及下一动作，避免重复整份契约和背景。既有历史聊天内容保留。
