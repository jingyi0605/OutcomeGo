# 需求文档 - Outcome 规划角色与任务分配

状态：Draft

## 简介

目前一个目标批准后只生成一个任务，由契约里的执行 bot 完成；规划线程也绑定在这个执行 bot 上。结果是：规划质量受限于执行 bot 的模型；复杂目标无法拆分给多个 bot；成果交付后用户要自己面对逐条验收项和原始产出。

目标管理面对的不只是代码编写：资料整理、文档编写、运维任务、现实任务（需要真人到现场）、项目管理都是目标。它们的"产出"各不相同（一份文档、一张整理好的表、一次生产环境变更、一份现场回执、一份排期），验证方式也不同（人工审阅、确定性检查、外部记录、人工回执）。本 Spec 的规划、分配、审查都不能默认"产出是代码、可以反复修改"，必须按任务的性质区别对待（见需求 11）。

本 Spec 引入两个可选角色，均由现有 bot 担任：

- **规划角色**：用高级模型写契约、拆分任务、指定每个任务的执行 bot，并在执行失败时调整未开始的任务。
- **审查角色**：先检查每个任务的结果，只有严重错误和遗漏才驳回（每个任务最多一次，让原 bot 修改）；成果交付后再对每条验收项给出初步意见和一份精简摘要，用户只对初验结果做决策。

普通 bot 不再负责规划：它们提交用户的原话，执行被指派的任务，更新进度，提交证据。批准契约与最终验收仍然只能由用户完成。

## 术语表

- **System**：OutcomeGo 服务端、computer 运行时与桌面端、移动端
- **规划角色**："以哪个 bot 的身份运行"加"用哪个模型"。推荐设为主 bot 加一个独立的高级模型，使规划回合共享主 bot 的资料、记忆、persona、技能和文件；未设置时回退到目标自己的 bot 与全局模型（004.8 行为）
- **审查角色**：同上，用于审查类回合；未设置时沿用后台一次性预审（004.2 行为）
- **Bot 模型**：用户为单个 bot 设置的 `providerId`、`modelId`、`reasoning`，作用于该 bot 的所有运行；空表示使用全局模型
- **生效模型**：一次运行实际使用的模型，按优先级取第一个可用的：子 agent 沿用的父运行模型 > 角色回合的独立模型 > Bot 模型 > 全局模型
- **独立模型**：角色回合使用的 `providerId`、`modelId`、`reasoning`，只作用于该角色的线程回合，不改变全局模型，也不改变 bot 的其他运行
- **提交 bot**：接收用户请求并提交目标的 bot，即 `Outcome.botId`；在本 Spec 中语义为"提交者与默认执行者"
- **任务计划（Plan）**：规划角色为某个契约修订写下的任务列表，保存在该修订上
- **计划任务（PlanTask）**：任务计划里的一项，含标题、指令、执行 bot、依赖、覆盖的验收项
- **任务（WorkItem）**：批准后按任务计划创建的执行单元（`OutcomeWorkItem`）
- **指定分配**：由规划角色为每个任务指定执行 bot，被指定的 bot 在依赖满足后被唤醒执行
- **初验**：审查角色对每条验收项给出的 `likely_pass` / `likely_fail` / `unclear` 建议，只是建议，不是验收
- **初验摘要**：审查角色写给用户的精简结论和需要用户关注的问题
- **环境说明**：用户在目标管理设置里维护的一段长文本，描述自己的环境（账号与服务、项目与目录、bot 分工、偏好、禁区），只给规划类和审查类回合使用；不含凭据
- **规划说明**：规划角色随任务计划保存的短文本，写明设计依据、对环境的假设和已知风险
- **任务级审查**：任务完成后、放行下游任务之前，审查角色对该任务结果做的一次检查，结论只有"通过"和"驳回"
- **驳回**：审查角色认为任务结果存在严重错误或遗漏，要求原 bot 按审查意见修改；每个任务最多一次
- **任务性质（`nature`）**：规划角色为每个计划任务声明的类别，取值只有两个。`deliverable`：任务的结果是一份可以检查、可以修改的成果，例如文档、整理好的资料、调研结论、方案、表格、排期、代码。`action`：任务对外部系统或现实环境执行了操作，例如变更生产环境、发送通知、部署、预订、付款；重做可能重复产生影响，所以不适合自动返工
- **人工任务**：需要真人完成的现实任务，沿用 004.4 的 `executorType = human` 任务与人工动作卡；它不是 `nature` 的取值，不经过任务级审查
- **严重错误 / 遗漏**：严重错误指结果与必需验收项或边界明显矛盾、关键事实错误；遗漏指必需验收项要求的产出或证据缺失。优化建议、格式、措辞、结构、风格、"更完整或更好的做法"都不属于
- **未开始任务**：状态为 `queued` 且还没有入队 Run（`rootRunId` 为空）的任务，包括等依赖的和等并发名额的

## 范围说明

### In Scope

- 规划角色与审查角色的设置、解析与回退
- 普通 bot 提交目标时只交用户原话，由规划角色写契约
- 规划角色保存任务计划：任务、指定 bot、依赖、覆盖的验收项
- 批准后按任务计划创建任务；依赖满足才唤醒对应 bot
- 执行 bot 只处理被指派任务，能读到依赖任务的产出
- 任务失败时唤醒规划角色重规划；规划角色只能调整未开始的任务
- 审查角色做任务级审查：可驳回任务结果，每个任务最多一次，只针对严重错误和遗漏
- 审查角色做整体初验，用户在初验结果上做决策，可一键采纳初验通过项
- 规划角色与审查角色的回合并发上限（各 5）
- 每个 bot 单独设置模型：Bot 模型、生效模型的优先级、只有用户能设置、桌面端设置界面
- 规划与审查角色的环境理解：环境说明、规划说明、自包含的任务指令、可指派 bot 清单、提交 bot 的名称与 id
- 桌面端设置与展示；Android、iOS 展示计划与初验摘要并支持采纳

### Out of Scope

- 任务池抢单、租约与抢占（本 Spec 只做指定分配）
- 审查角色代替用户做最终验收；任何机器人批准契约或验收成果
- 多次自动返工：审查角色对每个任务最多驳回一次，返工后的结果不再被驳回；整体初验不通过时由用户决定返工或发消息
- 跟踪型目标（`TrackOutcome`）经过规划角色
- 规划角色直接创建人工任务：人工任务继续由执行中的任务通过动作卡请求（004.4），未来需要预先规划人工步骤时另起 Spec
- 规划角色或审查角色授予任何动作授权：凭据、对外操作的批准仍然走 004.3 的 Decision
- 执行 bot 主动请求重规划的专用工具（只做"任务失败触发"，见设计 §8.2）
- 每个目标单独覆盖规划角色或审查角色（只做全局设置，见设计 §8.2）
- 按 BA、前端、后端等固定职能拆分 bot；拆分依据只有互相独立的任务
- 按目标或按任务临时覆盖 bot 的模型；移动端设置或显示 bot 模型（本版只在桌面端）；后台一次性推理（记忆整理、成果简报）按 bot 选模型
- 读取其他 bot 的私有记忆、复制主 bot 的对话历史给规划或审查角色（沿用现有的隐私边界，见需求 12.1）
- 自动从主 bot 的记忆生成环境说明（本版由用户维护，起草辅助见设计 §8.2）
- 初验失败后的重试入口（本版失败时提示，用户直接逐条验收）
- 提交 bot 随目标附带的背景说明（`SubmitOutcome.background`，后置；本版规划角色靠共享记忆、环境说明和读取提交 bot 的对话获取背景）

## 需求

### 需求 1：设置规划角色与审查角色

**用户故事：** 作为用户，我希望指定哪个 bot 负责规划、哪个 bot 负责审查，以便让高级模型做判断，其他 bot 只管执行。

#### 验收标准

1. WHEN 用户在目标管理设置里选择一个可运行的 bot 作为规划角色 THEN System SHALL 保存该设置，并对之后新创建的目标线程生效。
2. WHEN 用户选择一个可运行的 bot 作为审查角色 THEN System SHALL 保存该设置，并对之后进入待验收的目标生效。
3. WHEN 规划角色或审查角色未设置 THEN System SHALL 保持现有行为：规划线程用目标自己的 bot（004.8），预审用后台一次性 LLM（004.2）。
4. WHEN 被设置为角色的 bot 被删除或不可运行 THEN System SHALL 在设置页提示，并对新回合回退到未设置时的行为，不阻塞用户。
5. WHEN 目标管理开关关闭 THEN System SHALL 不创建线程、不暴露角色相关工具与设置入口。
6. WHEN 同一个 bot 同时有多个目标的规划类回合（`plan`、`owner_message`、`replan`）THEN System SHALL 最多同时运行 5 个，其余排队；审查类回合（`review`、`review_task`）同样最多 5 个，两类分别计数。
7. WHEN 规划或审查回合占用并发名额 THEN System SHALL 不占用该 bot 作为执行 bot 时每个 bot 并发 2 的任务名额，反之亦然。
8. WHEN 用户为规划角色或审查角色设置独立模型 THEN System SHALL 校验该模型已配置且可用后保存；规划类与审查类回合以该模型运行，不影响全局模型，也不影响同一个 bot 的主对话和其他运行。
9. WHEN 角色回合创建 THEN System SHALL 把当时生效的模型记录在回合上；回合运行期间用户修改设置，不改变这个回合已使用的模型。
10. WHEN 角色回合开始时所设模型不可用 THEN System SHALL 回退到优先级里的下一级（该 bot 的 Bot 模型，再到全局模型）运行，在回合记录里标注"独立模型不可用，已回退"，并写明回退到哪一级，并在设置页提示，不阻塞用户。
11. WHEN 角色 bot 设为主 bot 并配置独立模型 THEN System SHALL 让该回合沿用主 bot 的 persona、`Bot.instructions`、个人记忆、共享记忆、技能、文件与连接器，仅模型不同；不复制、不导出这些资料。

### 需求 2：bot 只提交目标，不写契约

**用户故事：** 作为用户，我希望任何 bot 收到我的目标请求后只负责提交，以便规划由规划角色统一完成，不因传话丢失信息。

#### 验收标准

1. WHEN 已设置规划角色，且某 bot 在对话中为用户创建标准目标 THEN System SHALL 要求 bot 只提交用户原话和自己作为提交 bot，由规划角色的 `plan` 回合写契约。
2. WHEN 用户在桌面端、Android、iOS 新建目标或把探索想法转为目标 THEN System SHALL 创建目标并把用户原文交给规划角色，同一 `clientRequestId` 只创建一次。
3. WHEN 规划角色未设置 THEN System SHALL 保持 004.8 行为（bot 可直接写契约）。
4. WHEN 目标是跟踪型（`TrackOutcome`） THEN System SHALL 不经过规划角色。
5. WHEN 提交 bot 的提示词要求"逐字提交用户原话" THEN System SHALL 将该要求写入平台提示词；服务端不声称能验证 bot 没有改写。

### 需求 3：规划角色保存任务计划

**用户故事：** 作为用户，我希望规划角色把目标拆成可分配的任务，以便复杂目标能由多个 bot 并行或按顺序完成。

#### 验收标准

1. WHEN 规划角色调用 `SavePlan` THEN System SHALL 校验并把任务计划保存到当前契约修订，不改变契约内容哈希，不要求用户重新批准契约。
2. WHEN 任务计划里存在重复的 `key`、指向不存在 `key` 的依赖，或依赖成环 THEN System SHALL 拒绝并返回具体字段错误，规划角色可在同一回合修正。
3. WHEN 任务指定的 bot 不存在或不可运行 THEN System SHALL 拒绝并返回该任务的 `key`。
4. WHEN 某条必需（`required`）验收项没有被任何计划任务覆盖 THEN System SHALL 拒绝并列出未覆盖的验收项。
5. WHEN 任务数量超过上限 THEN System SHALL 拒绝并说明上限。
6. WHEN 规划角色为契约修订 N+1 保存计划 THEN System SHALL 只关联到该修订；旧修订的计划保持只读。
7. WHEN 回合结束时契约已保存但没有计划 THEN System SHALL 在目标详情提示"规划角色没有保存任务计划"，并允许用户继续发消息；用户批准后按回退规则执行（需求 4.4）。
8. WHEN 计划任务没有声明任务性质（`nature`） THEN System SHALL 拒绝并返回该任务的 `key`；`nature` 没有默认值。

### 需求 4：批准后按计划创建并分配任务

**用户故事：** 作为用户，我希望批准后任务自动分给指定的 bot 并按依赖顺序执行，以便我不用逐个派活。

#### 验收标准

1. WHEN 用户批准契约，且当前修订有任务计划 THEN System SHALL 在同一事务中创建全部任务，每个任务记录指定 bot、依赖和计划 `key`。
2. WHEN 任务没有依赖 THEN System SHALL 立即排队并唤醒该任务指定的 bot。
3. WHEN 任务有依赖 THEN System SHALL 先让它等待；所有依赖任务都 `completed`，并且（已设置审查角色时）这些依赖任务已通过任务级审查或完成了返工后，才排队并唤醒，依赖任务指定的 bot 与它不同时同样放行。
4. WHEN 用户批准契约，且当前修订没有任务计划 THEN System SHALL 沿用 004.2 行为：创建一个 initial 任务交给契约里的 `executionBotId`。
5. WHEN 同一批准请求重复提交 THEN System SHALL 不重复创建任务，也不重复唤醒。
6. WHEN 某个依赖任务失败或取消 THEN System SHALL 不唤醒依赖它的任务，并触发重规划（需求 6）。

### 需求 5：执行 bot 只处理被指派任务

**用户故事：** 作为执行 bot，我只需要处理分给我的任务，并看到完成它所需的上游结果，以便不被其他任务干扰。

#### 验收标准

1. WHEN 任务被唤醒 THEN System SHALL 把任务指令、与该任务相关的契约摘要（目标、被覆盖的验收项、边界）和依赖任务的产出摘要交给指定 bot。
2. WHEN 执行 bot 更新进度 THEN System SHALL 沿用 `ReportOutcomeProgress`，只写该 bot 自己的任务。
3. WHEN 执行 bot 试图保存契约、保存计划、批准或验收 THEN System SHALL 拒绝：这些工具不在任务回合暴露。
4. WHEN 某目标有任务指派给 bot B，而 B 不是提交 bot THEN System SHALL 允许 B 通过 `GetOutcome` 读取该目标的事实（沿用现状：`GetOutcome`、`ListOutcomes` 不按 bot 过滤，本 Spec 不新增可见性限制）。
5. WHEN 执行 bot 完成任务并提交产出与证据 THEN System SHALL 沿用现有产出、证据记录和 `completed` 状态规则，并放行依赖它的任务。

### 需求 6：执行中的重规划

**用户故事：** 作为用户，我希望任务失败时由规划角色重新安排后续任务，而不是整体卡死，以便我只处理真正需要我决定的事。

#### 验收标准

1. WHEN 任务在 004.5 的重试用尽后进入 `failed`，或进入 `needs_review` THEN System SHALL 排队一个规划角色的 `replan` 回合，触发者为系统，触发说明包含失败任务与原因。
2. WHEN 规划角色在目标批准后调用 `SavePlan` THEN System SHALL 只允许新增任务，以及修改或移除未开始任务；已经入队 Run、运行中或已结束的任务必须原样出现且不被改动，否则拒绝。
3. WHEN 规划角色需要改变契约内容（目标、验收项、边界） THEN System SHALL 要求通过 `SaveOutcomeContract` 保存新修订，并走 004.2 的重新批准流程；未开始任务按 004.2 规则取消，新修订需要重新保存计划。
4. WHEN `replan` 回合结束时失败任务仍无处理 THEN System SHALL 在目标详情保留失败信息和规划角色的回复，等待用户发消息或决定，目标状态按 6.6 派生。
5. WHEN 回合由系统触发 THEN System SHALL 不允许规划角色取消目标。
6. WHEN 当前修订存在 `failed` 任务 THEN System SHALL 按以下顺序派生目标状态：（a）有推进中的任务（`queued`、`running`、`retry_pending`、`needs_review`，不含"被失败依赖阻塞的等待任务"），或有排队、运行中的 `replan` 回合时为 `running`；（b）否则，且最大序号的失败任务之后没有未失败、未取消的任务时为 `failed`；（c）否则按现有规则（可进入 `review_pending`）。目标处于 `failed` 时用户可以发消息让规划角色处理；规划角色新增的替代任务开始后目标回到 `running`。"被失败依赖阻塞的等待任务"指：状态为 `queued`、尚未入队 Run，且它的某个依赖（或该依赖的返工任务）已 `failed` 或 `cancelled` 的任务。

### 需求 7：可选审查角色做初步验收

**用户故事：** 作为用户，我希望成果交付后由审查角色先检查一遍，以便我不用自己逐条核对产出。

#### 验收标准

1. WHEN 已设置审查角色，且已批准的目标有成果并进入 `review_pending` 或 `decision_pending` THEN System SHALL 排队整体初验回合（`review`）；同一修订、同一批成果只排一次。待决策时只核对现有记录，不阻塞或替代用户作决定。
2. WHEN 整体初验回合运行 THEN System SHALL 只开放 `GetOutcome` 与 `SubmitPrereview` 两个目标管理工具，服务端按回合用途校验，越权调用被拒绝（设计 §3.3.9）；审查角色因此不能保存契约或计划，不能写验收结论，在该回合里不能驳回任务。审查角色仍保留与其他后台回合相同的通用工具，"只读已记录的产出、不重新执行"是提示词约束，不是技术限制。
3. WHEN 审查角色调用 `SubmitPrereview` THEN System SHALL 对每条验收项记录 `likely_pass` / `likely_fail` / `unclear`、理由和引用的证据，并保存初验摘要与需用户关注的问题。
4. WHEN 初验结果写入 THEN System SHALL 按现有格式记录为 `ai_prereview` 证据，不改变目标状态，不产生 `OutcomeReview`。
5. WHEN 审查回合失败 THEN System SHALL 在目标详情提示"初验失败"，不阻塞用户；用户直接按验收项逐条处理（本版不提供重试入口）。
6. WHEN 审查角色未设置 THEN System SHALL 保持现有后台一次性预审，且已设置审查角色的目标不再同时运行一次性预审。
7. WHEN 审查提示词生成 THEN System SHALL 要求对照验收项和 `boundaries.excluded` 检查：产出是否真的满足验收项、是否超出边界或加入了没要求的功能、报告中的验证声明是否有证据支持。
8. WHEN 整体初验生成 THEN System SHALL 同样约束：`likely_fail` 只能用于必需验收项没有满足；非必需验收项和优化建议只能写进摘要的备注部分，不得进入"需用户关注的问题"，不得折叠或抬高用户要处理的项数。
9. WHEN 审查角色核对一批成果 THEN System SHALL 让它在同一轮逐项给建议、引用证据并写一段面向用户的结论；若有合适的已核实数字，同轮提交带原始引用的图表点。系统直接排版，不再用另一次推理写报告。无可用审核结论时，通用汇总必须标注未经审核（设计 §2.3.7、§3.3.3，任务 6.6）。

### 需求 8：用户只对初验结果做决策

**用户故事：** 作为用户，我希望先看到一份精简的初验摘要，只处理有疑问的项，以便减少我要看的信息量。

#### 验收标准

1. WHEN 目标有已完成的初验 THEN System SHALL 在验收界面首屏显示初验摘要、`likely_fail` 和 `unclear` 的验收项及其理由；`likely_pass` 的项默认折叠。
2. WHEN 用户点击"采纳初验通过项" THEN System SHALL 对当前修订里所有 `likely_pass` 的验收项，以用户身份提交验收（`userConfirmed = true`），并复用现有验收校验。
3. WHEN 用户对某项不同意初验 THEN System SHALL 允许单独把该项标为通过、不通过，或发起返工，操作与现有验收一致。
4. WHEN 契约或成果批次变化 THEN System SHALL 不把旧结论或旧建议当成当前结果，且在服务端拒绝从旧初验采纳；新一批初验完成后，桌面端 Bot 对话和驾驶舱复用同一份报告（设计 §2.3.8、§3.3.5，任务 6.6）。
5. WHEN 用户未点击采纳或验收 THEN System SHALL 不把目标标为已验收；审查角色的任何输出都不能使目标进入 `accepted`。
6. WHEN 移动端打开有初验的目标 THEN System SHALL 显示同样的初验摘要并支持采纳。

### 需求 9：权限、可观测与回退

**用户故事：** 作为用户，我希望新增的角色不降低安全边界，也能看到每个角色做了什么，以便出问题时能追查。

#### 验收标准

1. WHEN 任何线程工具或任务工具调用序列执行 THEN System SHALL 不产生已批准的修订或已验收的目标，除非来自用户界面的批准或验收接口。
2. WHEN 目标被取消 THEN System SHALL 要求回合触发者是用户。
3. WHEN 规划、重规划、审查回合运行 THEN System SHALL 在目标详情的"Agent 记录"里显示回合用途、状态、时间和最终回复，并可打开执行记录。
4. WHEN 计划保存、重规划触发、任务级审查结论、初验提交发生 THEN System SHALL 追加对应事件（事件名见设计 §3.3.11），带幂等键与触发者；任务创建、依赖放行与任务进入运行沿用现有的任务事件，不新增。
5. WHEN 两个角色都未设置 THEN System SHALL 与 004.8 的行为一致，现有测试不需要改动语义。

### 需求 10：审查角色驳回任务结果

**用户故事：** 作为用户，我希望审查角色在下游任务使用某个任务的结果之前先挡住严重问题，让原 bot 修改一次，以便错误不向后传播，同时不被无休止的返工拖慢。

#### 验收标准

1. WHEN 已设置审查角色，且某个由计划创建、`nature = deliverable` 的任务 `completed` THEN System SHALL 排队一个任务级审查回合（`review_task`），在它出结论前不放行依赖该任务的任务。`nature = action` 的任务、无计划回退时的单个 initial 任务、返工任务、人工任务都不排任务级审查。
2. WHEN 任务级审查回合运行 THEN System SHALL 只开放 `GetOutcome` 与 `ReviewTaskResult` 两个目标管理工具，服务端按回合用途校验，越权调用被拒绝（设计 §3.3.9）；审查角色可以读取该任务的指令、产出、证据，以及它覆盖的验收项和契约边界。
3. WHEN 审查角色判定"通过" THEN System SHALL 放行依赖该任务的任务，不产生用户可见的打扰。
4. WHEN 审查角色判定"驳回" THEN System SHALL 要求至少一条发现，每条发现必须同时给出：类型（严重错误或遗漏）、被违反的依据、理由（一两句话说明产出的哪里与依据不符）。依据只能是以下两种之一：该任务覆盖的**必需**（`required`）验收项；契约里已写明的边界（`included` 或 `excluded` 的某一条）。引用了非必需验收项、该任务未覆盖的验收项、或不存在的边界的驳回，一律被拒绝。
5. WHEN 审查角色认为产出"多做了没要求的事" THEN System SHALL 仅在它违反契约 `excluded` 边界的某一条时允许作为严重错误驳回；否则只能写进备注。
6. WHEN 驳回被接受 THEN System SHALL 创建一个返工任务（`kind = rework`，`reworkOfWorkItemId` 指向原任务），交给原任务的同一个 bot，指令包含原指令和审查发现；依赖该任务的任务等返工任务 `completed` 后才放行；返工任务 `failed` 或 `cancelled` 时下游保持等待，并按 6.1 触发重规划，由规划角色或用户处理。
7. WHEN 同一个任务已经被驳回过一次 THEN System SHALL 拒绝再次驳回；返工任务不再经过任务级审查，剩余的疑虑由审查角色写进整体初验的摘要。
8. WHEN 任务级审查提示词生成 THEN System SHALL 写明：默认通过，拿不准就通过；只对照该任务覆盖的必需验收项和契约边界判断；只读已记录的产出与证据，不重新执行任务；以下一律不是驳回理由：格式、排版、措辞、命名、结构、风格、"更完整、更详细或更好的做法"、额外的检查或内容、非必需验收项、审查角色自己新增的要求。这些只能写进备注。提示词不得使用只适用于开发场景的术语作为通用说明。
9. WHEN 审查角色提交备注 THEN System SHALL 只把备注作为整体初验的素材，永远不写进返工任务的指令，也不发给执行 bot；备注有长度上限，不得写成"必须修改"。
10. WHEN 任务级审查回合失败、超时或审查 bot 不可运行 THEN System SHALL 视为通过并放行下游任务，同时在目标详情标注"未经审查"，不阻塞执行。
11. WHEN 任务被驳回或返工 THEN System SHALL 在目标详情的任务列表里标注"已被审查驳回一次"，并展示审查发现；用户无需为此做任何操作。
12. WHEN 用户取消目标或契约被新修订替换 THEN System SHALL 取消尚未开始的返工任务（沿用 004.2 的取消规则）；已在途的审查回合允许自然结束，其写入因目标已终结或修订已替换被拒绝（`review_task_stale`）。
13. WHEN 审查约束被调整或上线使用 THEN System SHALL 保留每次驳回的发现和依据，便于事后统计驳回率并收紧约束；本 Spec 不设自动熔断。

### 需求 11：不绑定目标类型

**用户故事：** 作为用户，我的目标可能是资料整理、文档编写、运维任务、现实任务或项目管理，我希望规划、分配和审查按任务的性质区别对待，而不是把一切都当成"写代码"来套，以便不同类型的目标都能顺畅完成。

#### 验收标准

1. WHEN 规划角色拆分任务 THEN System SHALL 通过提示词要求它按目标类型的自然单元拆分（资料整理按来源或主题，文档按章节或交付物，运维按变更步骤并标明风险，项目管理按工作包），不得默认套用"设计、实现、测试"之类的开发流程；每个任务必须声明 `nature`，拿不准时选 `action`（更保守：不自动审查、不自动返工）。
2. WHEN `nature = action` 的任务 `completed` THEN System SHALL 不排任务级审查、不自动返工；它的结果由证据（外部记录、确定性检查）、整体初验和用户验收覆盖。
3. WHEN 审查角色判断涉及外部系统或现实世界的事实 THEN System SHALL 只把外部记录、确定性检查和人工回执当作证据；执行 bot 自己的陈述（`agent_report`）只能证明"产出里写了什么"，不能证明"外部世界发生了什么"。缺证据时标 `unclear` 并说明缺什么，不得标 `likely_pass`，也不得因此驳回。
4. WHEN 验收项的验证方式是 `deterministic_check` THEN System SHALL 要求审查角色只核对确定性检查证据是否存在且结论为通过，不重新执行，也不用自己的判断替代；验证方式是 `human_review` 时对照验收项陈述给出建议。
5. WHEN 任务因现实任务等待人工回执（`waiting_human`） THEN System SHALL 不排任务级审查；人工任务沿用 004.4 的动作卡、回执和 owner 验收，不由审查角色审查或替代。
6. WHEN 规划、重规划或审查回合运行 THEN System SHALL 不产生任何动作授权；凭据与对外操作的批准继续走 004.3 的 Decision。
7. WHEN 提示词、界面文案、错误信息说明规则 THEN System SHALL 不使用只适用于开发场景的术语（代码、测试、构建、提交、防御性处理等）作为通用说明；任务列表用中性名称显示任务性质（"成果类""操作类"）。
8. WHEN 验证本 Spec 的审查约束 THEN System SHALL 使用覆盖多种目标类型的样例（至少：资料整理、文档编写、项目管理、运维操作、现实任务，以及作为其中一类的代码编写），不得只用代码样例。

### 需求 12：规划与审查角色理解用户的环境

**用户故事：** 作为用户，我希望专门的规划 bot 和审查 bot 能像我最熟悉的主 bot 一样理解我的环境（我有哪些账号、服务、项目、bot 分工、偏好和禁区），以便它们做出符合我实际情况的计划和审查，而不用我每次重新解释。

#### 验收标准

1. WHEN 规划或审查回合运行 THEN System SHALL 让该 bot 获得现有的上下文：用户共享记忆（`shared_profile`、`shared_journal`）、它自己的记忆与技能、队友清单。本 Spec 不新增读取其他 bot 私有记忆的能力，也不复制主 bot 的对话历史。
2. WHEN 用户在目标管理设置里填写"环境说明" THEN System SHALL 保存它（上限 8000 字），并把它作为只读背景段加入规划类和审查类回合的系统提示；执行任务回合不自动携带它。
3. WHEN 不同来源的环境信息互相冲突 THEN System SHALL 通过提示词规定优先级：用户当前的话，其次是更新的共享记忆事实，最后是环境说明；规划角色发现冲突且会影响计划时，向用户确认，不自行猜测。
4. WHEN 提交 bot 通过 `SubmitOutcome` 提交目标 THEN System SHALL 在首个规划回合的上下文里给出提交 bot 的名称与 id，并提示规划角色需要时可以用 `ReadTranscript` 读取它与用户的对话（沿用现有能力：只读可见消息、已脱敏）；用户原话逐字保存并送达。提交 bot 随目标附带背景说明的字段后置（设计 §8.3）。
5. WHEN 规划角色保存任务计划 THEN System SHALL 通过提示词要求每个任务的指令自包含：背景、涉及的资源位置（路径、账号名、资料引用）、约束、完成标准；不得假设执行 bot 知道用户的环境，凭据不写进指令。执行 bot 只获得规划角色写进指令的那部分环境信息。
6. WHEN 规划角色保存任务计划 THEN System SHALL 允许附带规划说明（上限 2000 字：设计依据、对环境的假设、已知风险）；规划说明保存在计划里，审查回合和用户都能读到，审查角色据此理解规划角色的判断依据。
7. WHEN 规划回合的上下文生成 THEN System SHALL 提供可指派 bot 清单：名称、id、描述、生效模型（Bot 模型，未设置则为全局模型）；设置页提示用户在 bot 描述里写明各自擅长什么。
8. WHEN 用户在目标线程里透露与环境有关的新事实 THEN System SHALL 通过提示词要求规划角色把它写入共享记忆，而不是只写进自己的角色记忆，使其他 bot 同样受益（沿用现有记忆规则）。
9. WHEN 用户保存环境说明 THEN System SHALL 在设置页提示不要写入密码、令牌等凭据（凭据继续走 Bitwarden 授权）；不做服务端拦截。
10. WHEN 规划角色或审查角色就是用户的主 bot THEN System SHALL 同样适用以上规则；这是推荐配置：主 bot 以独立模型担任，天然共享全部资料与记忆（见需求 1.11）。本 Spec 不要求它们是独立的新 bot；若设为另一个新 bot，则按本需求 12.1 到 12.9 补足环境理解。

### 需求 13：每个 bot 单独设置模型

**用户故事：** 作为用户，我希望每个 bot 可以使用自己的模型，以便让擅长写代码、写前端、联网检索的模型各司其职，而不是所有 bot 共用一个全局模型。

#### 验收标准

1. WHEN 用户在 bot 设置里为某个 bot 选择模型（提供方、模型、推理强度） THEN System SHALL 校验该模型已配置且可用后保存；清空表示使用全局模型。
2. WHEN 一次运行创建 THEN System SHALL 按优先级决定生效模型：子 agent 沿用父运行的模型 > 角色回合记录的独立模型（需求 1.8） > 该 bot 的 Bot 模型 > 全局模型；并把生效模型记录到该运行（沿用 `Run` 现有的模型字段）。
3. WHEN bot 设置了模型 THEN System SHALL 让它作用于该 bot 的所有运行：主对话、自动化、目标线程回合、执行任务；记忆整理、成果简报等后台一次性推理仍用全局模型，本 Spec 不改。
4. WHEN 运行期间用户修改 bot 或全局模型设置 THEN System SHALL 不改变已创建运行的模型。
5. WHEN 生效模型不可用（提供方凭据失效、模型被移除） THEN System SHALL 回退到优先级里的下一级，在运行记录里标注原因，并在设置页对该 bot 提示，不阻塞用户。
6. WHEN bot 调用 `UpdateProfile` 或编辑自己的 `settings.json` THEN System SHALL 不改变任何 bot 的模型：模型字段不在这两条路径的可写范围内；只有用户通过设置界面（bot 更新接口）能修改。
7. WHEN 规划回合生成可指派 bot 清单 THEN System SHALL 沿用需求 12.7：显示每个 bot 的生效模型，让规划角色按模型特点分配任务。
8. WHEN 没有任何 bot 设置模型、也没有设置角色独立模型 THEN System SHALL 与现在行为一致，所有运行用全局模型。
9. WHEN 升级到包含本需求的版本 THEN System SHALL 不把 `Bot.inferenceProvider` / `Bot.inferenceModel` 上已有的旧值当作用户设置（这两列目前没有任何代码读写；核实后若存在非空值，迁移时清空）。
10. WHEN 子 agent 由某个 bot 派出 THEN System SHALL 沿用父运行的模型，不使用子 agent 自己 bot 上设置的模型（沿用现有行为，`apps/worker/src/worker.ts:1901-1908`）。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 用户提交目标或发送消息 THEN System SHALL 立即返回（回合排队，不等待规划完成）。
2. WHEN 规划角色同时有多个回合 THEN System SHALL 按容量排队，用户消息优先于系统触发的 `replan` 回合。
3. WHEN 同一目标有多个互相独立的任务同时完成 THEN System SHALL 并行审查，不串行等待。

### 非功能需求 2：可靠性

1. WHEN 服务重启 THEN System SHALL 沿用 004.5：排队保留，运行中的规划、重规划、审查回合续跑或失败，任务按现有恢复规则处理。
2. WHEN 依赖放行与任务完成并发发生 THEN System SHALL 保证每个任务只被唤醒一次。
3. WHEN 任务计划保存与用户批准并发发生 THEN System SHALL 以批准时读取到的计划为准，且计划变更对已创建的任务不回溯。

### 非功能需求 3：可维护性

1. WHEN 新增角色或工具 THEN System SHALL 通过线程角色和回合用途扩展，不新增并行的调度路径。
2. WHEN 排查问题 THEN System SHALL 能从事件和回合记录还原"谁规划了什么、谁执行了哪个任务、审查给了什么意见"。

## 成功定义

- 设置一个高级模型的规划 bot 后，用户在任意 bot 里提交一个中等复杂的目标，得到包含多个任务、指定不同 bot、带依赖的计划，批准后按依赖顺序执行完毕。
- 某个任务失败后，规划角色在不打扰用户的情况下重新安排未开始的任务，或把需要用户决定的事写清楚。
- 设置审查角色后，用户在验收界面只需处理初验标出的有疑问项，其余可一键采纳；全程没有任何机器人批准契约或验收成果。
- 任务结果里的严重错误或遗漏在下游任务使用它之前被挡住并修改一次；优化类意见没有引发返工；同一个任务不会被驳回第二次。
- 规划与审查回合并发上限为 5，执行任务的并发上限仍为 2，两者互不占用。
- 给两个执行 bot 分别设置不同的模型后，各自的任务按各自的模型运行，运行记录里能看到；清空后回到全局模型；没有给任何 bot 设置模型时，行为与现在一致。
- 用户在设置里写好环境说明后，一个全新的规划 bot 做出的计划，能正确使用用户环境里的资源、遵守其中的禁区，并把必要的背景写进每个任务的指令，执行 bot 不需要追问环境。
- 一份文档编写目标和一份运维变更目标各走一遍：前者的成果任务经过任务级审查，后者的操作任务不被自动返工；两者的提示词和界面里都没有只适用于代码的说法。
- 两个角色都未设置时，行为与 004.8 一致。
