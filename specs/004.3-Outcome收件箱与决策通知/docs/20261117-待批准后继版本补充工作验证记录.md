## 真实缺陷与修正边界

已批准且实际 started 的 N WorkItem 请求包含 supplement 的 Decision 后，创建 pending N+1，再选择原 Decision 的 plan_only 选项。原 requester 按冻结策略仍有效，但新建 supplement 尚无自己的 startedAt/Run，原共享 predicate 拒绝为其保存 enqueue 意图，导致整个 resolve 事务回滚。

新实际集成测试在修改生产代码前得到 **0 PASS / 1 FAIL**，原错误为 `409 contract_revision_not_approved: A newer approved revision replaced this execution snapshot`。这是后继仍未批准情况下的错误拒绝，不归入既有失败基线。

只修改 `packages/messaging/src/outcome-decisions.ts` 的同一个共享有效执行 predicate。非当前 N 仍必须是最新已批准快照，当前 successor 必须为 draft/pending；新增一个由持久化事实证明的派生分支：

- WorkItem 使用既有 `kind=supplement`，引用 exact sourceDecisionId。
- 来源 Decision 必须 resolved，Outcome/revision 相同，冻结选项为 plan_only，supplement title/instructions 与创建的 WorkItem 完全一致。
- 真实 requester 是同 Outcome/revision/Bot 的 agent，已实际 started，存在精确关联的真实 Outcome Run started 证据。
- supplement 的 dependsOn 包含该 requester；没有依赖链接的相似 WorkItem 不能通过。
- requester 可以已经 completed。其启动事实在依赖满足后仍然成立，才能调度 supplement；不要求 requester 继续非终态。

没有新增客户端 flag、状态、enum、schema 或生产测试替身。原依赖完成检查、并发容量、队列持久化和真实 Worker claim 均保留。N+1 实际批准后，外层共同围栏拒绝旧 N 的 started 分支和 derivative 分支；同一共享判定自动作用于 enqueue/drain/claim/recovery/控制查询，不另加一套调度逻辑。
