## 故障恢复证据

- 在 Decision 与 Event 已提交后删除通知意图，再删除 required Event，重新执行默认 dispatcher.drain：从永久 Decision 恢复一次通知，重复 drain 不重复。
- 一个事务插入 Decision 但延迟提交，先执行 drain，再提交并执行第二次 drain：晚提交仍恢复，没有 sequence 高水位丢失。
- 第一次恢复注入数据库失败，普通 badge push 仍送达；下一次 drain 从事实补齐 Decision 通知。
- 101 条缺少 DM 的旧事实不会阻塞后面的可投递事实；DM 后建后两个 bounded pass 补齐旧事实。
- 通知 A 已读或 A 创建时没有设备，60 秒内产生 B：B 拥有有效意图，实际 dispatcher 只发送一次 B。
- 人工 WorkItem 使用真实 transitionWorkItem 从 in_progress 到 submitted/review_pending，原请求者保持 waiting_human：Outcome 仍为 human_action_pending，但 Inbox 返回一个 acceptance_pending 卡。
- 同 WorkItem 的旧 Decision 已过期，不先 GET/expire，直接提交新事实：旧 slot 释放，新卡可创建。

## API 与跨线交接

Decision API 第一波稳定：`GET/POST /decisions/:id` 只标记 presented；`POST /resolve` 的输入为 optionId/customText、整数 expectedContractRevision 和 clientRequestId；请求中的 actor/effect/status 被忽略。鉴权通过后从 session User 生成 actorRef，禁用鉴权时为 owner:local。相同 ID/请求重放 stored response；不同客户端并发只有一个结果；历史 revision 返回 409 decision_revision_conflict，详情含当前卡。

线 4 接口：选项 snapshot 的 `manualAction` 对齐 `HumanActionInput`；调用冻结 `HumanActionPort.createFromDecision(tx,{outcomeId,decisionId,requestedByWorkItemId,card})`，返回 `{workItemId,cardId}`，调用方事务尚未提交。未装配时 `manual_action_unavailable`/503，Decision 不被解决，不创建半对象。需要集成真实端口后才启用该效果；本线不实现第 2 波人工工具。

线 1：plan_only 在真实环境调用 enqueueOutcomeTurn，同一 WorkItem，reason=decision_resolved，clientId=`decision:<id>`；固定测试替身只在测试中注入。生产真实函数尚未集成时抛错并回滚，不能假装续跑。

线 2/集成者：把 withdrawSupersededDecisions 装配到 revision 更新与 cancel 事务。helper 在本线 resolve 和读取路径已有调用；外部事务即时关闭由对应所有者整合。Review 不应越过独立 open Decision，审查发现已交集成者。main.ts 路由注册与 messaging exports 需保留其他线的并集。

事件流审计发现实际 SnapshotService 全量返回 Event，与父设计默认不发 outcome.* 不一致；已交集成者处理过滤与游标。Decision 恢复不依赖该事件保留。第一波必要共享唤醒保留 notification.created、channel.read、notification.presence.changed、snapshot.required；不要求发送 outcome.* 正文。

任务 1.3、1.4 仍 TODO；三端 UI、点击和未登录后的 pending deep link 回放属于第三波，设备验证 PENDING。scope/acceptance 选项需要服务端完整 contract snapshot，自定义输入默认保留当前 revision 的 plan_only 效果。
