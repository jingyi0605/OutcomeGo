## 实现和接口

`createOutcomeDecision(tx, input, actor, requestSnapshot?)` 位于 `packages/messaging/src/outcome-decisions.ts`。调用者拥有事务；使用同一 Outcome 锁、稳定输入摘要幂等键、过期 active slot 清理、冻结选项和目录内事件。Server 工具与 Worker recovery 共用此构造，不复制业务插入。

`createOutcomeDecisionTool(prisma, decisions)` 位于 `apps/server/src/services/outcome-decision-tool.ts`。Run、Bot、WorkItem 和 revision 均从持久化上下文推导。同事务创建 Decision、将原 WorkItem 置为 `waiting_decision`、写事件及重新计算状态。computer 只在 Outcome 子线程提供工具；返回 `waiting_for_user` 后请求结束当前回合。普通主对话、Routine 和 event 工具列表快照保持原值。

resolve 继续使用 caller transaction 内的真实 revision writer、`enqueueOutcomeTurn` 与 `HumanActionPort`。`plan_only` 的原 WorkItem 在同一子线程续跑；supplement 使用既有 `kind="supplement"` 创建一个真实 agent WorkItem，依赖原 WorkItem，保留 `queued`，通过真实 enqueue 记录持久化待调度意图；不新增状态。scope/acceptance 效果仍要求当前 base revision，不对旧版本重复编辑 pending successor。

共享 `isOutcomeDecisionRevisionActive(tx, outcomeId, revisionId, requesterAgentWorkItemId?)` 及对应 SQL 在创建、withdraw、resolve、Inbox 与通知当前事实检查中使用：

- 当前指针沿用原有规则。
- 非当前 N 只在当前 successor 为 `draft`/`pending_approval`、N 为最新已批准快照，且对应 agent WorkItem 实际 started、存在相同 Bot/WorkItem 的真实 Outcome Run started 证据时有效。
- N+1 实际批准后，新的旧 N 控制和 resolve 返回 revision conflict；已启动旧回合完成历史 Output 的运行层规则不由本线扩展。
- 人工 review 选择由 L4 使用同一 predicate 和真实 human/requester 上下文完成；不能由旧 N review 全局验收 pending N+1。

新增 `packages/messaging/src/outcome-inbox-notifications.ts`：

- `consumeOutcomeInboxEvent(tx, sequence: bigint)`：消费 required/review/human/accepted/closed 目录事件，receipt 为 `IdempotencyRecord(scope="outcome-event:inbox", key=eventId)`；receipt 与通知意图同事务。
- `reconcileOutcomeInboxNotifications(prisma)`：在现有 Dispatcher 启动和周期 drain 前运行，覆盖 Decision、待验收、待人工、已完成永久事实。无新 timer、无 worker.ts 修改、无 Event 高水位。已有 DM 和缺少通知 key 的资格检查在 LIMIT 前完成；事务内再次检查事实。
- `outcomeNotificationIsCurrent(tx, payload)`：最终推送前复核实时事实，已关闭/过期/实际被替代的控制不能再提醒。
- `unreadOutcomeNotifications(tx)`：提供固定脱敏字段、未读、当前、偏好允许且未隐藏/归档的通知数组，最多 100 条，按 notification sequence 倒序。

待验收事实使用设计 §17.1 的 `review.required:<outcomeId>:<contractRevision>:<criterionGroup>`。criterionGroup 是排序 criterion IDs 和当前 ready agent WorkItem IDs / 最新人工 receipt IDs 的确定摘要。原结果一旦有非 cancelled 的返工后继便退出 ready 集合；返工完成的新结果形成新组，因此已读 A 后会出现新未读 B，而重复 Event 和重复 settlement 保持同 key。待验收 Inbox 卡仍按 Outcome 合并，read 状态与该当前组的通知一致；独立待 review 的人工 receipt 不被返工状态覆盖。

现有 `GET /api/v0/notification-state` 保留原 `notificationRouting`、`cursor`、`badgeCount`、`readStates`，追加 `outcomeNotifications: OutcomeNotificationPayload[]`。客户端应结合该数组与 routing 生成提醒；不能仅凭 `notification.created` 就展示，因为事实写入先于偏好抑制。通知不包含自定义输入、业务标题、证据或结果正文；原 message/reaction 行为不变，未开放原始 `outcome.*` 客户端流。
