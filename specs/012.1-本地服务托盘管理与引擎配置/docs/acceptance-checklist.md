# Spec 012.1 联调与实机验收清单

本清单覆盖 Windows 11（`managed-wsl` / `external`）与 macOS（`managed-lima` / `external`）桌面端与 CLI 的端到端验收项，逐项对应 `requirements.md` 需求 1–7 与 `design.md` §7.4 验证映射。

## 一、任务栏托盘菜单增强与状态同步（需求 1）

- [ ] **T-1.1 部署完成立即同步**：一键本地部署完成后，不重启桌面端，右键托盘立即显示“本地服务：运行中”，不再滞留于“正在启动本地服务”。
- [ ] **T-1.2 右键限时刷新**：在命令行手动执行 `outcomego stop` 后超过 10 秒再右键托盘，1.5s 内弹出菜单并准确显示“本地服务：已停止”与“启动本地服务”。
- [ ] **T-1.3 本地模式完整菜单**：确认菜单依次包含「打开 OutcomeGo / 状态摘要 / 服务管理… / 启动或停止 / 重启本地服务 / 开机自动启动本地服务（复选框）/ 打开日志目录 / 退出 OutcomeGo」。
- [ ] **T-1.4 直达服务管理**：关闭主窗口（隐藏至托盘），右键点击“服务管理…”，主窗口唤起并自动跳转至「设置 → 服务器 → 本地服务管理」且滚动高亮该区域。
- [ ] **T-1.5 远程模式极简菜单**：切换连接至远程服务器后，右键托盘仅显示「打开 OutcomeGo」与「退出 OutcomeGo」。
- [ ] **T-1.6 忙碌互斥态**：点击“重启本地服务”期间，再次右键托盘确认启停、重启、自启切换项均置灰禁用。

## 二、本地容器视图、指标与单容器运维（需求 2）

- [ ] **T-2.1 概览与核心容器**：进入「设置 → 服务器 → 本地服务管理」，正确展示引擎类型、版本、端口、安装目录及 5 个核心容器（`server`、`worker`、`computer`、`postgres`、`computer-memory-init`）。
- [ ] **T-2.2 实时指标与折叠初始化任务**：核心容器异步展示 CPU % 与内存用量/上限；展开“一次性初始化任务”可见 `migrate`、`*-init` 及其退出码。
- [ ] **T-2.3 引擎停止空态**：停止本地服务后，容器区显示友好空态与“启动本地服务”按钮，无未捕获异常。
- [ ] **T-2.4 单容器重启（含 `computer` 协同）**：单独重启 `worker` 正常恢复；重启 `computer` 时弹出联动确认提示，确认后 `computer` 与 `computer-memory-init` 同步重建且 `/health` 恢复健康（无 `memory-init helper did not become ready` 循环）。
- [ ] **T-2.5 脱敏日志弹窗**：点击“查看日志”，验证 100 / 200 / 500 行切换、关键词筛选、手动刷新与一键复制；确认日志中的密码、Token、API Key 与代理密码均已替换为 `[REDACTED]`。
- [ ] **T-2.6 后台暂停轮询**：切换出设置页或隐藏窗口至托盘后，确认不再高频触发容器状态与 `docker stats` 轮询。

## 三、开机自启动独立配置（需求 3）

- [ ] **T-3.1 Windows 计划任务开关**：在 Windows 11（`managed-wsl`）切换“开机自动启动本地服务”，用 `Get-ScheduledTask -TaskName OutcomeGo-ManagedEngine` 核实任务实时增删，且托盘复选框与设置页开关实时一致。
- [ ] **T-3.2 macOS LaunchAgent 开关**：在 macOS（`managed-lima`）切换“开机自动启动本地服务”，核实 `~/Library/LaunchAgents/com.outcomego.managed-engine.plist` 实时创建/移除，且指向稳定 CLI 路径（`~/.local/bin/outcomego`）。
- [ ] **T-3.3 启停与自启解耦**：开启本地服务自启后手动点击“停止本地服务”，确认计划任务/LaunchAgent 未被删除；关闭本地服务自启后手动点击“启动本地服务”，确认不会偷偷重新注册自启任务。
- [ ] **T-3.4 外部引擎只读**：在 `external` 引擎下确认“开机自动启动本地服务”为只读置灰并展示清晰说明。
- [ ] **T-3.5 桌面端登录自启与静默托盘**：开启“登录系统时启动 OutcomeGo 桌面端”与“启动时最小化到托盘”，注销重登或使用 `--autostart-hidden` 启动，确认应用仅常驻托盘不主动弹出主窗口。

## 四、性能与资源配置（需求 4）

- [ ] **T-4.1 当前值回显与预设档位**：打开「性能与资源配置」，核实宿主机内存/CPU/磁盘空间及当前容器配置准确回显；切换“轻量 / 均衡 / 高性能”档位自动填入合法参数。
- [ ] **T-4.2 边界校验与重建**：验证 `desktop >= computer`、`computer < 1g`、非法 CPU 步进被前端即时拦截；确认修改 `computer` 内存/CPU 与 `worker` 并发后仅重建对应服务并生效（`compose.local.yaml` 生成与清理正常）。
- [ ] **T-4.3 macOS Lima VM 调整**：在 `managed-lima` 下修改 VM 内存/CPU，确认重启后生效；模拟失败可自动回滚原 `lima.yaml`。
- [ ] **T-4.4 Windows `.wslconfig` 安全写入**：在 `managed-wsl` 下勾选显式确认更新 `.wslconfig`，确认同目录生成 `.wslconfig.outcomego.bak` 备份、原其他节与注释完好保留，且默认不擅自执行 `wsl --shutdown`。

## 五、代理服务器配置与一键测通（需求 5）

- [ ] **T-5.1 模式切换与系统代理探测**：切换“直连 / 跟随系统代理 / 手动代理”，在系统开启代理时“跟随系统代理”能正确探测并展示 HTTP/HTTPS/NO_PROXY 摘要。
- [ ] **T-5.2 回环代理映射与一键测通**：在宿主机开启本地代理（如 `127.0.0.1:7890` 并开启 Allow LAN），输入 `127.0.0.1:7890` 点击“测试代理连接”，4 项探测（代理 TCP、模型 API、GitHub、ghcr.io）返回状态与耗时且未改写当前配置；若关闭 Allow LAN，界面给出明确的局域网连接与防火墙排查指引。
- [ ] **T-5.3 保存应用与全链路生效**：点击“保存并应用代理”，验证：
  - `proxy.json` 保留原始 `127.0.0.1` 回显且权限为 `0o600`；
  - `.env` 写入映射后的宿主机地址、`OUTCOMEGO_HOST_PROXY_TARGET` 以及包含全部内网保护条目的 `OUTCOMEGO_NO_PROXY`；
  - 托管引擎 `/etc/systemd/system/docker.service.d/outcomego-proxy.conf` 已写入并生效；
  - 服务端模型请求、网页搜索、`computer` 出网及托管引擎拉取镜像均经代理成功，同时容器间通信（`server ↔ postgres ↔ computer`）完全正常。
- [ ] **T-5.4 凭据安全**：配置带密码代理后，确认任务管理器/ps 命令行、`proxy status --json`、日志弹窗及诊断包均不含明文密码；留空保存保留原密码，勾选清除可移除密码。
- [ ] **T-5.5 切回直连**：切换为“直连”并应用，确认 `.env` 代理变量与托管 Docker daemon drop-in 均被清理干净。

## 六、国际化与兼容性回归（需求 6、7）

- [ ] **T-6.1 中英文切换**：在设置中切换 `zh-CN` 与 `en-US`，核对托盘菜单、本地服务管理各分区、日志弹窗、错误提示与 CLI `--language zh-CN` 输出均无遗漏原文。
- [ ] **T-6.2 旧 `.env` 与远程兼容**：确认不带新增变量的旧 `.env` 下 `deploy/compose.yaml` 正常工作，且远程服务器连接流程无回归。
